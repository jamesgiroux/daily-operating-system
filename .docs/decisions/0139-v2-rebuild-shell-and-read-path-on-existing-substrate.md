## Context

Nineteen weeks in (first commit 2026-01-29; 2,570 commits, 140 ADRs), the record splits asymmetrically: zero substrate ADRs have been superseded while the shell superseded itself repeatedly (ADR-0053 → 0055 → 0077 in six days; ADR-0034 deprecated; ADR-0052's enums invalidated in ten days), and 0 of 31 `docs/solutions/` captures trace to substrate-internal failures while eight write-path interventions in fourteen weeks (ADR-0133) trace to the shell's data path.

The measured scaling chain (case doc §3, figures verified 2026-06-11, provenance corrected post-red-team): a worst subject of 2,143 claims; ~311k signal events ≈ 60% of a 397 MB database; trust recompute that is O(accumulated claims) per touch on the 2 remaining unbounded call sites (`intel_queue.rs:3583`, `invalidation_jobs.rs:449` — a bounded paged variant already exists at `trust_recompute.rs:65`); ~16 background producers funneling into one write gate that an enrichment persist holds for its entire transaction (DOS-866 starvation class, incidents 2026-06-10/11; note `commit_composition` runs its own transaction helper outside the gate, `services/compositions.rs:221`); a legacy foreground read path of ~10 IPC round trips plus a 30-query assembly, with the composition path performing an unbounded depth-3 claim read and **committing a composition row on the cache-miss path of a page load** (`abilities-runtime/src/abilities/account_overview.rs:148-152`; 60 s in-memory cache, `composition_render_orchestrator.rs:52`). The headline 8.8 s account click was measured 2026-05-27 **on the legacy `get_account_detail` path, pre-DOS-866** — the live composition-backed page no longer calls it. The product premise is compounding context; the chain above grows with accumulated context — but whether targeted substrate fixes dissolve the latency without read models is an open empirical question this ADR commits to answering (see the checkpoint below).

This is a read/write architecture failure, not a SQLite bug: analytical, graph-shaped UI reads run against the same store a continuous enrichment pipeline writes to, and no intervention to date separated the workloads. A landscape scan of the mid-2026 toolscape (case doc §4 — demoted from "independent derivation" per red-team: same author, conclusion-aware) is consistent with the direction: typed-component dispatch (A2UI/AG-UI/MCP Apps) validates ADR-0130 composition; the memory-layer commoditization literature names staleness/salience/trust — our claims substrate — as the unsolved differentiators; the experience paradigm trend is push-first/post-chat; and the platform (Tauri 2 + Rust + React + SQLite) survives scrutiny. The scan supports the keep decisions; the rebuild decisions rest on the internal evidence above, not on trend convergence.

## Decision

DailyOS v2.0 rebuilds **everything between the store and the user's eyes** — the surface taxonomy and the read path — on the existing v1.x substrate. v2.0 changes how the product reads and renders, not what it knows.

**The boundary (case doc §5).** Crosses intact: abilities-runtime crate, claims schema + `services/` layer, composition substrate, trust-as-opacity rendering model, design system, DB hardening including the DOS-866 fixes, the app as control plane (packaging + native push), and the ADR/learnings corpus + ladder process. Dies, each with a named successor: the 26-route mission-control taxonomy, all hand-wired page data paths, the legacy display grammar (intelligence-JSON as display source) and remaining detail-page generations, two of three feedback write paths, tab views inside surfaces, the parity layer, and dual same-purpose components.

**Three architecture commitments:**

1. **Briefing-first surface taxonomy.** The D-spine briefing (±7-day window) is the front door; entity surfaces are drill-downs; the page inventory is deliberately small; lists/triage are redesigned as consumption surfaces. A chat escape hatch ships in v2.0 — available everywhere, primary nowhere — riding the existing ability-invocation surface.
2. **Blocks are the only rendering system.** One display grammar (producer-shaped block payloads), one feedback path (ADR-0138 writer), salience-driven layout, trust carried per block via `claim_refs` + `provenance_ref`. **Deletion is an acceptance criterion** on every conversion: a surface's migration is not done while its predecessor compiles.
3. **Read/write separation with materialized read models — gated by the checkpoint below.** The UI subscribes to materialized projections; pages never fetch imperatively, never read unbounded claim sets, never write on load. Enrichment persists in capped, phased batches (DOS-866 shape) on the write side. **Default mechanism (revised 2026-06-11 post-red-team, superseding the same-day framework-first gate answer): owned Rust materialized projections + reactive subscription, built behind the existing service contracts.** A framework (LiveStore-class / TanStack DB-class) is adopted only if its L0 shows it beating the owned design on measured criteria — noting the red-team-verified facts that LiveStore has no native Tauri adapter and that event-sourcing frameworks exist to solve multi-device sync, a constraint this single-user single-device product does not have. The read/write separation is the commitment; the mechanism must be earned.

### Re-measurement checkpoint (gates commitment 3)

Before any read-model work starts: land DOS-866 (phased persist + caps) plus three named substrate fixes — switch the 2 remaining unbounded trust-recompute call sites to the existing paged variant, bound the producer claim read (depth/limit), and remove the composition commit from the read path (these run as their own substrate L0 per the sequencing rule). Then **re-measure the entity-click latency on the same replica, on the live composition path**, against a numeric target: **entity detail interactive < 500 ms p95 at current context volume (≈7.4k claims / 48 accounts)**. If the target is met, commitment 3's read-model build must re-justify on product grounds alone at its L0 (reactive subscription, salience-driven recomposition) — the performance argument is dead and may not be cited. Commitments 1 and 2 stand on the product case regardless of this checkpoint's outcome.

**Sequencing rule.** Any v2.0 work item proposing changes to claim semantics, the writer queue, the abilities contract, or the composition model beyond consuming them is out of scope and runs its own L0 as substrate work. DOS-866 ships regardless of v2.0.

## Consequences

- All current surface-track projects are superseded; the Linear sweep (supersede/keep/backlog) executes as a separate gated deliverable.
- Three block-type families that don't exist (list, triage/action-dispatch, report) become explicit v2.0 design work (James + Claude collaborative), scoped before waves, not discovered mid-wave.
- The parity layer retires: one producer contract per surface serves Tauri and MCP; parity becomes a unit test on the producer.
- **Pricing (restated honestly post-red-team):** ~10–15 engineer-weeks is the **surface-conversion line only** (audit §6). Separate labeled estimate lines, priced at their L0s before wave planning: the read-model workstream (if the checkpoint opens it), the three new block families' design+build, and the chat escape hatch (minimum shape: free-text → ability dispatch → block-grammar rendering; transport exists, the feature does not). The design phase is timeboxed. The repo's own record (three DOS-852 retrofit failures, the W5 parity spiral) calibrates a realistic program total at 2–3× the surface-conversion line; sequencing decisions should anchor on that, not the headline.
- **Customer-zero protections (added post-red-team):** per-surface rollback rule — the old route stays addressable until the new surface survives N days of daily use; an old/new output-equivalence check per conversion (temporary fixture diff is acceptable); the parity layer retires per-surface *after* the conversion it polices, never before; MeetingDetail and DailyBriefing conversions each get an explicit James L4 hands-on gate before their predecessors are deleted.
- **Sequencing (James, 2026-06-11, post-premise-red-team — supersedes "rides along"):** the 2026-05-29 examination's moat instrumentation (2 weeks on the shipped app: does judgment-ranked output change user behavior vs. a recency dump?) runs **before wave execution**, on the app *after* the checkpoint's prerequisite fixes land so latency doesn't contaminate the readout. The v2.0 design phase (page inventory, block families, D-spine briefing) proceeds **in parallel** — it is collaborative design time, not build time. Wave execution starts after the instrumentation readout, and the briefing-first designs cite it.

## Alternatives considered

- **Shell-only rebuild (the superseded boundary draft).** Rejected: the scaling chain lives in the read path; a new shell on the old data path inherits the 8.8 s click.
- **Keep patching per-page / per-write-layer.** Rejected as the *long-term strategy* by the record: eight write-path interventions in fourteen weeks, three detail-page generations, 11 dual systems — the class-sweep rule (CLAUDE.md) applied at architecture scale. Post-red-team nuance: the targeted substrate fixes themselves are not rejected — they are **prerequisites** (the checkpoint requires them to land and be measured first); what is rejected is treating each as the last.
- **Substrate rewrite (files-as-truth, app deprecation, WP-primary).** Rejected per the 2026-05-29 adjudication: transactional store stays truth; the app stays the control plane; the differentiated layer gets the iteration, not the plumbing.
- **Platform migration (Electron, native Swift, new UI framework).** Rejected by the greenfield test itself: both viable 2026 stacks keep Tauri 2 + Rust + React + SQLite; single-writer SQLite is designed around, not escaped.
