DailyOS - v1.4.6 - Wave Plan

Make DailyOS selective without making new authority.

Salience, surfacing, triggers, and recommendation blocks stay claim-backed, ability-backed, and quiet by default.

v1.4.6 turns trustworthy intelligence into selective recommendations: what matters, why it matters now, and what the user should consider doing next. This revision reconciles the original plan with the current Engineering Ladder and the ability producer model that landed after the first draft. W2 may continue as service-local surfacing and trigger plumbing, but future surfaces must consume a recommendation ability projection rather than W2 tables.

Target: v1.4.6 Revision: 2026-05-26 reconciliation Waves: W0-W5 Parallel agents: 3 peak Source: Linear + v1.4.6-waves.md

Source and scope

A recommendation is a claim, not a parallel product state.

v1.4.6 consumes the claim substrate, trust bands, signal policy registry, ability runtime, WordPress block producer pattern, and producer-remediation lessons from v1.4.4 through v1.4.7.

  • Canonical markdown: .docs/plans/v1.4.6-waves.md
  • Current W2 packet: .docs/plans/v1.4.6-salience-recommendations/L0-packet-W2-DOS-331-DOS-334.md
  • Scope tier: project wave plan is Wave; W2 is Standard with Amendment 3 add-on.
  • Origination: Extension. This extends existing claim, salience, signal, trust, ability, and WP surface substrate.
  • Trust topology: local-to-local single-user. No new MCP, SurfaceClient, remote, or multi-user exposure ships in W2.
  • Non-goal: no direct table-backed recommendation surface, no proactive notification policy, no LLM ranking, no new trust primitive, and no Tauri React surface work.
  • K-in basis: v1.4.4 WordPress surface migration, v1.4.4a ability-backed Tauri cutover, v1.4.5 workspace memory, v1.4.7 MCP abilities-first plan, and the abilities-runtime producer remediation plan.

Reconciliation

Two old assumptions are now superseded.

The original plan used an older review panel and was written before ability producers became the surface authority pattern. This revision makes both constraints explicit.

Area Old assumption Current rule
Review process Codex challenge + domain reviewer + Codex consult; code-reviewer/domain-reviewer at L2; separate L5 drift. Use the 2026-05-23 Engineering Ladder: scoped L0, mandatory K-in, bounded L2 router, advisory path-alpha, L4 before L2 for surfaces, and L5 folded into L3 for v1.x.y.
Surface authority W3 could render recommendation state through a React component or direct surface contract. W3 is WordPress / SurfaceClient block work over an ability-backed recommendation projection. Blocks never read W2 tables as authority.
Producer boundary Recommendation, salience, surfacing, and trigger outputs were discussed as one system state. Recommendation claims are durable producers through commit_claim; salience, surfacing, and trigger rows are derived evidence or audit state unless promoted through an ability producer.
v1.4.7 coupling v1.4.6 release blocked on a specific v1.4.7 portfolio-attention consumer. v1.4.6 publishes stable schema-versioned read contracts; v1.4.7 can consume them or remain on an approved fallback path without blocking v1.4.6.

Producer matrix

Durable assertions and audit rows have different jobs.

W2 remains valid only because it is framed as derived policy and audit state. The first user-visible consumer must be an ability projection.

Wave details

Execution boundaries that matter.

W2 boundary

Proceed with services/recommendations/{surfacing,triggers,why_this_now}.rs, v271-v272 migrations, and service signal facade calls. quiet is a first-class auditable surface class; external is out of W2 scope. Do not touch services/claims.rs, commit_claim, trust recompute, or surface/MCP readers.

W2 L0 amendment

The current W2 packet now declares Standard + Amendment 3 scope, Extension origination, local-to-local topology, producer classification, a field-by-field trigger-log privacy matrix, and the current L2 router expectation.

W3 producer gate

Before a block renders recommendations, the lane identifies the ability projection that returns recommendations, surfacing state, trust, provenance, caveats, and receipt refs. If missing, W3 blocks.

W4 telemetry

Engagement is a ranking input only. It never feeds trust scoring, and W4-C carries security review, retention, opt-out, and delete-on-opt-out tests.

W5 evaluation

The eval harness lives under tests/v146_eval and validates high-signal, low-signal, stale, noisy, missed-important, and user-corrected cases.

Compatibility

v1.4.6 publishes stable schemas for future consumers. v1.4.7 portfolio attention may consume them or stay on its approved fallback; that status is recorded, not used as a release blocker.

Suites

S/P/E fire by need at L3.

S

Security

Privacy-safe signal payloads, actor-filtered provenance, no direct surface authority, telemetry opt-out, and no raw source/prompt/output text in audit rows.

Owner ce-security-reviewer

Pass zero blocker privacy or authority bypass findings

P

Performance

Migration safety, indexed surfacing/trigger queries, and bounded projection fan-out for block consumers.

Owner ce-performance-oracle

Pass no unbounded hot-path or migration regression

E

Edge cases

Budget overflow, cooldowns, noisy feedback, material-new-evidence overrides, typed empty/degraded producer states, and missed-important fixtures.

Owner ce-testing-reviewer

Pass all required fixture axes green

Pacing

No wave starts until the prior wave clears L3. W3 and later user-facing work must complete L4 evidence before L2 review.

Bounding

Path-alpha findings file to the maintenance project unless they violate acceptance criteria, ADR contracts, or PR-touched behavior.

Migration slots

v1.4.6 owns v269-v288. W1 used v269-v270; W2 uses v271-v272; later waves claim contiguous remaining slots after rebase.
