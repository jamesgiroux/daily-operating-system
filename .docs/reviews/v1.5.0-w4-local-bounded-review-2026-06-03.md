# v1.5.0 W4 Local Bounded Review - 2026-06-03

**Scope:** Local pre-L2 bounded review of W4 against `.docs/plans/v1.5.0-w4-l0-packet.md`.

**Status:** REQUEST_CHANGES resolved locally. This is not a substitute for the official external L2 review.

## Findings

### W4-0 token issuer/resolver behavior was under-proven

**Severity:** Blocking for W4 local pre-L2.

W4-0 requires the meeting identity path to be tokenized, fail closed, and avoid leaking raw meeting/calendar identifiers into composition ids. The initial W4 test coverage proved token shape and non-echo behavior for one helper, but did not directly prove the service-issued token route, the resolver route, sanitized calendar-route input, unknown-token fail-closed behavior, or stale-token fail-closed behavior.

### W4-0 token issuer error echoed raw ids

**Severity:** Blocking for W4 local pre-L2.

The token issuer kept raw meeting/calendar identifiers out of successful composition ids, but its missing-meeting error returned `Meeting not found: {requested_meeting_id}`. That could expose the same local id or sanitized calendar-route id through command errors, diagnostics, or frontend error state.

### W4-4 projected composition was not refreshed after preserved mutations

**Severity:** Blocking for W4 local pre-L2.

W4-4 requires existing Meeting Detail and Daily Briefing mutation/feedback controls to keep working and force-refresh or invalidate projected composition after successful mutations. The initial W4 diff rendered projected Daily Briefing and Meeting Detail composition, but successful action, transcript, prep, agenda, attendee-visibility, entity-chip, and feedback paths only refreshed legacy DTO state or parent data. That allowed the new composition surface to show stale producer output after a user changed the underlying meeting or briefing state.

### W4-0 meeting snapshot trusted caller-supplied raw ids

**Severity:** Blocking for W4 local pre-L2.

W4-0 requires raw meeting ids to resolve only inside the Tauri producer invocation after a server-issued `meeting_token` is parsed. `get_projected_composition` followed that path, but the User ability remained reachable through the generic Tauri ability invocation surface. A direct call to `dailyos/meeting-detail` could provide a valid-looking `meeting_token` and an unrelated raw `meeting_id`, and the service-owned snapshot reader would return the raw meeting row under the wrong token subject.

## Resolution

- Added meeting token service regressions proving service issue/resolve behavior, sanitized calendar-route equivalence, no raw id/calendar echo in emitted tokens, unknown-token fail-closed behavior, and stale-token fail-closed behavior.
- Changed the token issuer missing-meeting error to the generic `Meeting not found` and added coverage proving it does not echo raw route/calendar ids.
- Added a token-to-row guard in the service-owned Meeting Detail snapshot reader so any caller-supplied raw `meeting_id` must match the issued `meeting_token` before meeting data is returned.
- Added Daily Briefing projected-composition refresh after action completion, lifecycle confirmation/correction, entity changes, and the explicit briefing refresh action.
- Added Meeting Detail helpers for projected-composition force refresh and combined DTO/projection reload.
- Routed transcript, prep, agenda, attendee visibility, entity-chip, feedback, and action mutation success paths through the projected refresh path.
- Added Daily Briefing test coverage proving action completion calls projected composition `refetch({ forceRefresh: true })`.
