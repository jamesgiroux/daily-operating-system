## §0 — L0 Scope Header

- **Threat topology:** local-to-local single-user. W2 writes local user layout preferences through first-party Tauri commands and app services. It does not expose a new remote actor or MCP channel. Security concerns that still apply: service-owned writes, path/scope validation, sensitivity-safe rendering, and avoiding unknown-block payload leakage.
- **Origination class:** Extension. W2 adds a surface-side layout overlay over accepted ADR-0130 `Composition`; it does not change composition authorship, claim storage, or producer semantics.
- **Scope tier:** Wave. W2 touches UI edit mode, layout persistence, a SQL migration, Tauri commands, design-system patterns, and proof/L4.
- **Review-scope rule:** L0 blockers are acceptance criteria, ADR-named contracts, write-path safety, or W2-introduced regressions. Edge-case hardening outside those bounds is path-alpha/maintenance.

## §1 — Why W2 Exists

W1 proved the Account Detail vertical: substrate-authored `Composition`, safe projection, React block rendering, and routed Account page integration. W2 adds the user-facing payoff: the user can customize the Account surface in context without changing the substrate-authored composition or any claims.

The layout overlay is the new contract. It answers "which projected blocks are shown, in what order, and in which variant for this entity type?" It is a presentation preference over a produced composition. The overlay never edits `Composition`, never edits claim payload, and never turns hidden blocks into dismissed claims.

### W2-A — Layout Overlay Persistence

- **Do:** Add registered SQL migration **275** for a local preference table, tentatively `composition_layout_overlays`.
- **Do:** Store overlays keyed only by:
  - `entity_type` (`account`, `project`, `person` now; Account is the only active W2 UI consumer)
  - `surface_key` (`entity_page` for W2)
- **Do:** Keep version fields out of identity. `overlay_schema_version` describes the JSON format; `layout_revision` is service-owned presentation revision/cache state returned by get/save/reset. Neither is part of the primary key.
- **Do:** Store a bounded JSON payload with:
  - section/block ordering
  - user visibility toggles
  - block variants
  - inline label overrides when backed by feedback-allowed edit routes
  - updated timestamp
- **Do:** Route all mutations through `services/`; commands may validate inputs and call services but must not write directly.
- **Do:** Validate entity type, surface key, block ids, section ids, variants, and payload size server-side. Unknown ids from stale overlays are ignored with a diagnostic, not written through.
- **Do:** Make migration 275 replay-safe with idempotent DDL and validate it against the replica DB before treating the dev build as ready for W2 proof.
- **AC:** Rust tests prove create/read/update/reset, invalid payload rejection, migration idempotence, bounded payload size, and persistence across service calls.

### W2-B — First-Party Commands And Reactive Hook

- **Do:** Add first-party Tauri commands:
  - `get_composition_layout_overlay`
  - `save_composition_layout_overlay`
  - `reset_composition_layout_overlay`
- **Do:** Add a React hook, tentatively `useChapterLayout`, that loads the per-type overlay, merges it with `ProjectedComposition`, applies optimistic updates, and refetches/reset cleanly.
- **Do:** Keep cache identity honest: overlay changes must update the open page immediately without pretending the producer recomposed. The composition version remains substrate-owned; `layout_revision` is separate presentation state.
- **Do:** Guard overlapping optimistic mutations with a latest-wins client mutation sequence. Older save/reset responses may be logged or refetched, but must not rollback or overwrite a newer local layout.
- **AC:** Hook tests cover first load, optimistic save, failed save rollback, reset, failed older save after a newer mutation, older reset response after a newer save, pending mutation during Account route switch, account-to-account reuse for the same entity type, and stale overlay ids disappearing when the projection changes.

### W2-C — Visibility Precedence And Core Blocks

## §3 — Data Model Sketch

Migration 275 creates local preference storage. Proposed shape:

```sql
CREATE TABLE IF NOT EXISTS composition_layout_overlays (
  entity_type TEXT NOT NULL,
  surface_key TEXT NOT NULL,
  overlay_schema_version INTEGER NOT NULL DEFAULT 1,
  layout_revision INTEGER NOT NULL DEFAULT 1,
  overlay_json TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (entity_type, surface_key),
  CHECK (overlay_schema_version = 1),
  CHECK (layout_revision >= 1)
);
```

Service DTOs validate the JSON shape before write. The table stores user presentation preferences only; no claim text, source labels, PII, provenance envelopes, or unknown block payloads.

Overlay application is deterministic and pure on the frontend:

```text
ProjectedComposition + LayoutOverlay -> RenderableCompositionView
```

The producer output and composition version stay unchanged. Overlay changes update only presentation order, visibility, and variant. `layout_revision` is returned to the UI for cache/mutation ordering; it is not a producer composition version and is not part of overlay identity.

## §4 — Intelligence Loop Check

| Question | W2 answer |
|---|---|
| Claim model | Layout overlay rows are user presentation preferences, not claims. Claim-backed inline edits still route through existing feedback/correction flows. If W2 needs to persist a user statement about the account, it is claim feedback, not overlay JSON. |
| Provenance + trust | Overlay does not alter trust, provenance, source freshness, or sensitivity. Hidden blocks remain hidden by presentation choice only; trust rendering for visible blocks continues to come from projected block metadata and rendered provenance. |
| Signals + invalidation | Overlay changes should emit local preference/update telemetry or composition-layout invalidation only if needed for UI refresh. They must not bump claim versions or producer composition versions. |
| Runtime + surfaces | Tauri Account page consumes overlay through first-party commands and `useChapterLayout`. MCP/headless surfaces are unchanged in W2. Future Project/Person surfaces consume the same per-type overlay shape after W3. |
| Feedback loop | Inline claim edits use existing correction semantics. Hide/show/reorder/variant choices are layout preferences and do not penalize source reliability or create suppression tombstones. |

## §8 — Open Questions For L0

1. Should W2 store overlay order at section level, block level, or both? Proposed: both, but apply section order first and block order within sections.
2. Should inline label overrides live in overlay JSON at all, or should W2 restrict inline edit entirely to claim feedback? Proposed: overlay label overrides only for section/display labels, not claim text.
3. Is ADR-0136 "Layout Overlay as Surface-Side Presentation Preference" sufficient for W2's overlay/claim/composition boundary? Yes; accepted after L0 cycle 2 passed.
4. Does W2 need a new command namespace under `commands::composition_layout`, or should it extend `commands::abilities`? Proposed: new command module with services-owned mutations to keep projection reads separate from preference writes.
