The actual problem

Two real things broke. Everything else is downstream of them.

Today’s storm has one cause inside one transaction (a runaway backfill row) and one amplifier outside it (five high-frequency writers that bypass the queue). Fix those two and the storm class closes. The rest of the substrate is fine.

Cause · one pathological row inside one transaction

runtime_evidence_backfill slice 12 entered BEGIN IMMEDIATE on the writer queue and held it for 10+ minutes. The slice is fine in general — slices 1–11 ran ~2s each. Slice 12 hits an action at offset 110 that triggers one of three things: an exponential withdraw_claim chain (an action with many historical claims, each withdrawn in its own nested transaction), an unbounded claim_corroborations LEFT JOIN inside projection_claim_preflight with no covering index, or a runaway shadow_canonicalization_record against thousands of candidate inputs. These are correctness bugs inside the claim substrate, not architecture bugs in the queue.

Amplifier · five high-frequency writers competing for the WAL lock

While slice 12 holds the writer queue’s connection, five other writers fire on their own cadences against their own independent SQLite::Connection handles obtained via ActionDb::open(…). Each one waits busy_timeout = 5,000ms on BEGIN IMMEDIATE, fails with “database is locked,” and tries again. The queue’s serial guarantee covers its own connection only, not the database file.

The audit found ~850 total write sites across src-tauri/src/. ~259 already route through state.db_write. ~195 use ActionDb::open() but most are read-only. The twelve rows above are the confirmed write bypasses. Closing them closes the storm class for everything we’ve observed.

The anti-pattern hiding in executor.rs

Lines 632 and 1052 both carry the comment “Own DB connection to avoid starving foreground IPC commands.” The reasoning is inverted. A separate SQLite::Connection doesn’t dodge the writer queue — it competes with the writer queue’s connection for the WAL write reservation. Two callers both invoking BEGIN IMMEDIATE is exactly the contention pattern that produces “database is locked.” The author was being polite to the queue and feeding the storm at the same time.

This comment is worth capturing as a K-out learning: opening a separate connection does not avoid contention; it creates it. The right way to be polite to foreground commands is to use WritePriority::Background (deferred) or to break the work into smaller transactions that release the writer between slices — both of which are the “earn the rest” work, not today’s work. Today’s work is just to remove the inverted-model bypass and route through the queue.

Caller-dependent · services/claims_backfill.rs

The file contains 40+ conn_ref() write sites and with_transaction blocks. As a service module, it’s designed to receive a db: &ActionDb from a caller. Whether each write bypasses depends entirely on the caller’s context: safe if invoked from state.db_write(|db| ...), bypass if invoked from a fresh ActionDb::open(). A caller audit is part of Change 2 — the fix is to enforce one entry path.

The plan

Five PRs. ~400 lines. Each one independently shippable.

Ordered from highest leverage to lowest. Change 1 unblocks the running app today. Changes 2–3 close the storm class. Changes 4–5 keep it closed.

Change 1 · Correctness

Find and fix the slice-12 hang itself.

~50–150 LOC · src-tauri/src/services/action_claims.rs, services/claims.rs, services/intelligence.rs

Diagnose first; fix second. Add per-row logging in backfill_action_open_loop_claims_batch so we know which action ID is pathological. Inspect that action’s claim history. The fix is one of three known patterns depending on what we find.

  • Add log::info! before each action loop iteration with action.id and active-claim count
  • Replay the storm; capture the offending action ID
  • If exponential withdraw_claim chain: cap claim withdrawal at N per pass, defer the rest
  • If unbounded claim_corroborations JOIN: add covering index on (claim_id, data_source)
  • If runaway shadow_canonicalization: bound candidate set or move outside the per-row transaction
  • Regression test: a single action with 100+ historical claims completes its slice in < 1s

Change 2 · Hot-bypass sweep

Route the twelve confirmed bypasses through state.db_write.

~300–400 LOC · one PR per site · mechanical · parallel-codex eligible

Each site from the audit table becomes a state.db_write closure. The transformations are local and well-typed. Parallel-codex can land most of these from the table as input. No ordering required between them. The executor.rs sites all carry the same inverted-model comment — remove the comment and route through the queue in the same PR.

  • Critical: pty.rs:387 — write_json_kv + read_json_kv take &AppState; record_ai_usage awaits state.db_write
  • Critical: intel_queue.rs:1185 — apply_enrichment_side_writes + upsert_assessment_from_enrichment move inside state.db_write
  • High: processor/transcript.rs:2072 — transcript writes use state.db_write for the commit phase
  • High: capture.rs:290 — capture path takes &AppState, routes through queue
  • High: self_healing/scheduler.rs + quality.rs — coherence updates routed through queue
  • Workflow: executor.rs archive flow — lines 633, 658, 690, 702 routed through queue; strip the “own DB connection” comment
  • Workflow: executor.rs inbox + today flows — lines 807, 1053 routed through queue
  • Backfill: workspace_backfill.rs:226 — fresh open replaced; callers pass &AppState and use state.db_write for the upsert paths
  • Audit: services/claims_backfill.rs caller audit — trace every public-fn caller; confirm each invocation is from a db_write closure

Change 3 · CI gate

Forbidden-pattern lint on ActionDb::open + writes.

~50 LOC · new .github/workflows/db-bypass-check.yml + scripts/check-db-bypass.sh

A grep-based gate that blocks PRs introducing ActionDb::open(…) followed by INSERT, UPDATE, DELETE, or with_transaction in the same function. Maintains a small allowlist for the known legitimate fresh-open paths (db_backup.rs, doctor.rs, migrations, startup). New bypasses require an allowlist entry, which is reviewable.

  • Allowlist file at .docs/decisions/db-fresh-open-allowlist.md — named sites with rationale
  • Grep pattern: ActionDb::open within 30 lines of INSERT|UPDATE|DELETE|with_transaction, minus allowlist
  • Runs on every PR touching src-tauri/
  • Failure message points to this plan and the foreground-db-contention L0 packet
  • Optional follow-up: clippy lint via a custom dylint if the grep gate proves too coarse

Change 4 · Error variants

Split DbError::Migration into two variants.

~30 LOC · src-tauri/src/db/types.rs + a handful of call-site updates

Today every busy/locked error inside a service helper gets wrapped as “Schema migration failed.” That label is wrong and it’s drowning real migration failures in runtime contention noise. Two variants, one rename, no behavior change.

  • Rename DbError::Migration → DbError::SchemaMigration
  • Add DbError::WriteContention(String) for busy/locked at runtime
  • Update wrapping sites in services/invalidation_jobs.rs and friends to emit the right variant
  • Telemetry can now distinguish “migrations are broken” from “writers are starving”

Change 5 · Deprecation signpost

#[deprecated] on ActionDb::open with a note pointing at db_write.

~10 LOC · src-tauri/src/db/core.rs

Once Change 2 lands, the remaining ActionDb::open sites are read-only or on the allowlist. Mark the function #[deprecated] with a note that says “use state.db_read or state.db_write; see db-write-queue-consolidation.html.” New callers see the warning in their IDE; reviewers see it in the diff. Belt and suspenders with Change 3’s CI gate.

  • Single #[deprecated(note = "…")] annotation
  • Allowlist entries suppress the warning via #[allow(deprecated)] with a comment naming the entry
  • Compiler+IDE catches new uses before CI does — cheaper feedback loop than the gate

Total scope

Across all five PRs, roughly 300–450 lines of real code change plus the gate workflow. No new types. No new queue infrastructure. No new dispatch logic. The existing DbService stays exactly as it is — one writer, two readers, dedicated threads, serialized SQLCipher key verification, busy-timeout pragmas, GLOBAL singleton. The plan is to use it consistently, not to replace it.

Earn the rest

Type-system split and cooperative-yield scheduler are named and gated, not built.

Two pieces of larger structural work were in the v1 draft of this plan. Both are on hold with explicit trigger criteria. If neither trigger fires, they don’t get built. ADR-0067’s “earn it” discipline, applied one level deeper.

Held · ReadDb / WriteHandle type-system split

A compile-time split between read-only and write-capable database handles makes bypass structurally impossible. It also touches hundreds of method signatures across the codebase. Today we can’t justify that scope — the five known bypass sites are concrete and the CI gate catches future ones cheaply.

Trigger to build it: if a sixth high-frequency bypass lands and the CI gate didn’t catch it, or if two more storms in this class fire within six months. Either of those proves the grep gate is too coarse and structural enforcement is worth the migration cost.

Held · Priority queue with cooperative yield

The v1 draft proposed a WritePriority enum and a YieldableJob path so long backfills release the writer between slices. Today this is unnecessary: the existing 15-second SLICE_PAUSE_MS between slices already gives the queue plenty of breathing room, and Change 1 fixes the per-row hang that turned slice 12 into a 10-minute writer hold.

Trigger to build it: if a backfill is observed holding the writer for > 5 seconds in any slice after Change 1 lands. The new db_writer.slot_held_ms telemetry (a side-effect of Change 4’s rename pass) will catch this. Without that signal, the yield infrastructure is solving a problem we don’t have.

Also out of scope

  • No second encrypted DB. Rejected at the foreground-db-contention L0 for sync / key-rotation / purge cost.
  • No CQRS or materialized read models. Those remain gated on read-side metrics, not write-side contention.
  • No async driver swap. Sync-on-dedicated-thread is fine.
  • No rewrite of the abilities runtime. Abilities accept a writer handle through context, whatever shape that handle has today.

Done means done

Acceptance criteria.

Each criterion is testable against real data. No surrogates.

  • AC1 · Storm reproduction safe. Replay the DOS-7 backfill-after-restore scenario; backfill completes; no “database is locked” warnings; PTY ai_usage flush never fails.
  • AC2 · Pathological action handled. The specific action ID found in Change 1 completes its slice in < 1s in a regression test.
  • AC3 · Hot bypasses closed. The twelve confirmed bypass sites in the audit table either route through state.db_write or are on the documented allowlist with rationale. claims_backfill.rs caller audit complete with every public-fn caller invoked from a db_write closure.
  • AC4 · Gate active. A test PR that introduces ActionDb::open followed by an INSERT fails CI. A test PR that adds an allowlist entry passes.
  • AC5 · Telemetry separates classes. DbError::Migration is no longer reachable from runtime busy paths. WriteContention labels every runtime busy/locked error.
  • AC6 · Deprecation visible. cargo clippy -- -D warnings still passes, but new ActionDb::open uses without #[allow(deprecated)] trigger an IDE warning.

Sequencing

Order matters between Changes 1 and 2. Everything else is parallel.

Change 1 first because it’s the running-app blocker. Change 2 second because closing the amplifiers prevents the next storm. Changes 3–5 can land in any order after that, or in parallel.

  • Day 0–1 · Change 1. Add diagnostic logging, replay storm, identify offending action, ship fix. L2 review by ce-correctness-reviewer + codex review.
  • Day 1–4 · Change 2. ~Twelve PRs in parallel via codex sweep. Each one routes one site through state.db_write. Group the six executor.rs sites into one PR (same anti-pattern, same fix). L2 review per PR; the executor PR also captures the inverted-model anti-pattern as a K-out learning.
  • Day 2–4 · Changes 3, 4, 5 in parallel. CI gate, error rename, deprecation annotation. Cheap. Mostly mechanical.
  • L0 review: the canonical 4-reviewer panel (codex challenge + ce-feasibility + ce-scope-guardian + ce-architecture-strategist). No 5th slot needed; the surface is small.
  • L3 review: codex challenge on integrated diff + ce-architecture-strategist. Storm-reproduction test in the proof bundle.
