# Light L0 Packet: Claim Trust Recompute Wiring

Date: 2026-05-22
Status: Draft for light L0 review
Branch: `account-fact-claim-producer`
Scope tier: Standard, with parallel L1 lanes. Escalate to Wave only if the first PR must implement full entity-specific trust footprints for every subject type.

## Problem

DailyOS now has real claim producers for surfaced account intelligence, but the runtime-wide trust recomputation path is not fully wired. Some surfaces can render claim-backed content, yet producer-created claims can remain unscored or over-conservatively flagged because the durable `claim_recompute` job path does not invoke the trust compiler.

The fix should not teach MCP, WordPress, or Tauri surfaces to read account schema fields directly. Surfaces should continue to consume claim-backed intelligence from the abilities runtime. Structured facts from source systems should be promoted into claims by services, then scored through the same trust path as other claims.

## Evidence

- `src-tauri/src/services/invalidation_jobs.rs::run_claim_recompute` loads active claims, then only recomputes account entity health. It does not call the trust compiler or persist claim trust scores.
- `src-tauri/src/intel_queue.rs::run_finalize_trust_recompute` contains a real trust recompute path, but production call sites for `FinalizeMode::TrustRecompute` appear absent or test-only.
- `src-tauri/src/services/claims.rs::initial_trust_score` seeds trust only for `ClaimType::UserNote`; producer-created claims generally start unscored.
- `src-tauri/src/services/claims.rs::update_claim_trust` already persists `trust_score`, `trust_computed_at`, and `trust_version`.
- `src-tauri/abilities-runtime/src/abilities/trust/mod.rs::compile_trust` already evaluates trust factor inputs and gates.
- `src-tauri/src/services/trust_extraction.rs::build_account_extraction_context` is account-specific, so person/project/meeting claim recomputation would currently need deliberate fallback or entity-specific footprint work.
- `src-tauri/src/services/intelligence.rs::commit_claim_shaped_intelligence_projection` creates several claim-shaped intelligence outputs, but its follow-on signal path does not appear to enqueue claim trust recompute.

## Design Direction

Add a service-owned trust recomputation path and make durable invalidation jobs call it.

Proposed service shape:

```rust
services::trust_recompute::recompute_claim_trust_for_subject(
    ctx,
    db,
    subject_type,
    subject_id,
) -> TrustRecomputeReport
```

The service should:

- Load active claims for the subject.
- Build the appropriate trust extraction context and target footprint.
- Call the abilities-runtime trust compiler.
- Persist trust results through `services::claims::update_claim_trust`.
- Emit trust-change signals only for meaningful band crossings or lifecycle transitions.
- Record skipped/unsupported subjects explicitly instead of silently succeeding.

`services::invalidation_jobs::run_claim_recompute` should call this service first. Account health recompute can remain as a secondary step if downstream account health still depends on the updated claim trust state.

Producer-trigger policy:

- Producer-created claims should enqueue a subject-level `claim_recompute` job after commit.
- The first pass can wire producer-specific enqueue points for account fact and intelligence projection producers.
- A later cleanup may centralize enqueue behavior in `commit_claim`, but that should follow an audit because `commit_claim` also handles repair, canonicalization, dismissals, tombstones, and feedback-driven updates.

Entity footprint policy:

- Account subjects should be fully recomputed because an account extraction context already exists.
- Non-account subjects should not silently no-op. Prefer a conservative generic footprint fallback so trust factors that do not require account-specific context still run. If the implementation cannot safely support that in the first PR, return an explicit skipped report and file the entity-specific footprint work.

Temporal policy:

- Use upstream `source_asof` when present.
- Fall back to observed or created time only when the source did not provide a true as-of date.
- Preserve timestamp uncertainty in factor inputs rather than fabricating precision.

## Acceptance Criteria

1. A durable `claim_recompute` job for an account subject with active unscored claims updates `trust_score`, `trust_computed_at`, and `trust_version`.
2. Account fact claims created by the producer or backfill are not left permanently unscored after recompute drains.
3. Claim-shaped intelligence projection claims, including summaries, current state, risks, wins, recommendations, stakeholder engagement, company context, commitments, and value delivered, use the same recompute path.
4. `run_claim_recompute` invokes service-owned trust recomputation. Account health recompute is not the only job behavior.
5. Recompute uses source/provenance inputs, including `source_asof` where available, and preserves uncertainty when only observed time is known.
6. Corroboration, contradiction, feedback, lifecycle, read-state, sensitivity, and source-withdrawal gates continue to flow through `TrustFactorInputs`.
7. Trust-change signal behavior avoids storms. Score-only micro changes should not recursively enqueue unbounded recompute work.
8. Non-account subjects are deliberately handled and tested. Silent success with no trust update is not acceptable.
9. Surfaces do not bypass the claim substrate by reading account schema fields directly.
10. All mutations remain service-owned; no new direct DB writes from command handlers or surface adapters.
11. Focused validation passes before PR: `cargo test services::account_fact_claims`, trust recompute service tests, invalidation job tests, and relevant abilities-runtime trust tests.
12. Full L1 validation target before merge remains `cargo clippy -- -D warnings`, `cargo test`, and `pnpm tsc --noEmit`.

## Non-goals

- Do not rewrite the trust compiler scoring model in this PR.
- Do not add remote or multi-user MCP authentication gates as part of this local trust work.
- Do not make MCP, WordPress, or Tauri query structured account tables as a shortcut around claims.
- Do not assign arbitrary high trust scores in producers.
- Do not commit customer-specific account names, domains, emails, or facts in tests, fixtures, docs, or commit messages.

## Open Questions For Light L0

1. Should recompute enqueue be centralized in `commit_claim` now, or should the first PR wire producer-specific subject-level enqueue points?

Recommendation: producer-specific enqueue first, then centralize after a `commit_claim` lifecycle audit.

2. Should non-account subjects score through a generic footprint in the first PR?

Recommendation: yes, if the footprint is conservative and explicit about missing context. That better matches the goal of trust recomputation working across claim types without pretending account-specific extraction applies everywhere.

3. Should account health recompute remain inside the `claim_recompute` job?

Recommendation: keep it as a secondary step for now if it depends on claim trust state. Split into a separate job later only if the coupling causes loops or confusing ownership.
