DailyOS · Substrate

Seven layers of lock discipline. Zero of throughput shaping.

An architectural reading of why the same class of failure keeps recurring at twenty entities, and what to build instead of an eighth gate.

Over fourteen weeks the team has shipped seven distinct write-discipline layers — helpers, a pool, a reverted pool, a crate split, a merged helper, a batch closure, a process-wide gate, and a typed writer. Each one was supposed to be the last. None of them has ever addressed two co-equal substrate gaps: background-write throughput competing with foreground reads, and atomicity boundaries mis-scoped around unrelated subject domains. The current beachball at twenty account entities is the sixth instance of the class.

This proposal stages a different move. Production hygiene first (WAL tuning, reader pool, per-subject-domain transaction decomposition with durable cursor, presence-aware admission) — as four measurement-gated waves, not one bundle. Production hygiene is overdue and unconditional through W0. The deeper architectural alternatives — subject-ref-hash partitioned writer queue (A☆) and in-memory claim graph (B) — are each earned by specific failure modes named in W1’s measurements: if multi-subject writer-hold dominates, A☆ is earned; if SQLCipher read-path CPU dominates, B is earned. C (separate cache service process) only earns when multi-surface need joins. The wave plan makes which alternative gets earned an observable claim, not a feeling.

Today, mechanically

8.8 s foreground latency is a missing pragma, an undersized pool, and a transaction shape — not a lock storm.

The lock-class storm IS resolved. PR #407’s WRITE_TRANSACTION_GATE logs zero contention. The current beachball is a separate, smaller, cheaper problem: SQLite WAL bloat starving the reader pool while it’s walking the WAL frame index, amplified by sequential reads inside one closure.

Four concurrent issues, ranked by leverage

  1. No wal_autocheckpoint override — db_service.rs:388-394 sets WAL mode but not the checkpoint interval. Default 1000 frames in PASSIVE mode means the WAL grows past checkpoint threshold under continuous writes (verified live: 18.6 MB right now, up from 12 MB when the performance oracle first measured), and readers must walk that frame index on every page lookup. At ~25 sequential queries in build_account_detail_result, that’s the bulk of the 8.8 s wall-clock.
  2. NUM_READERS = 2 as a magic constant in db_service.rs:40. With four concurrent foreground commands (account detail + linear status + audit log + context mode) fired by one navigation, two are running and two are queuing in the reader-thread mpsc channels. The synchronized “all four release within 32 ms” signature is the smoking gun.
  3. Per-entity transaction shape combines many claim types + side-effects in one boundary (atomicity-shape gap) — persist_enrichment_write_results_via_db_service at intel_queue.rs:2711 commits ~150 risks + 162 wins + 9 stakeholders + products + assessment + signal emissions in one transaction. Most rows are tied to the entity’s own subject_ref; stakeholder insights can switch to person subject_refs. The decomposition unit is claim-type and side-effect class, not strict subject-domain. Splitting reduces critical-section length and is independent of row-batching — both reduce writer-hold but address different structural problems.
  4. Per-claim transaction count — even within one subject domain, each claim’s commit_claim wraps its own transaction. ~150 risks × one TX each = ~150 BEGIN/COMMIT cycles. Plus 6 progressive snapshots + consolidated commit + 3–5 post-commit side-effects. ~10–12 gate acquisitions per entity, each one a separate BEGIN IMMEDIATE / COMMIT cycle. WAL grows at write-burst speed because each commit appends a checkpoint mark the PASSIVE checkpoint can’t process.

These three problems compound. Fixing any one in isolation will reduce magnitude but the symptom returns when the load increases. The cheap fix sequence (Alternative A below) closes all three at once and recovers most of the headroom — without committing to the larger architectural shift that the user’s framing correctly points toward.

The pattern

Six instances of one class. Seven attempts to fix the wrong abstraction.

The git history shows the same problem class returning under different surface symptoms. Each remediation has been a lock-semantics or serialization layer. None has ever shaped throughput — bounded the rate at which background work consumes the writer, given foreground commands priority, or removed the persistent store from the synchronous read path.

What every layer has in common

Every intervention shipped above is, structurally, about who is allowed to write and in what order. None of them constrains the rate of writes, prioritizes foreground over background, or removes contention by moving the foreground reader off the embedded database entirely.

The L0 packet on foreground DB contention came closest. It explicitly named “materialized read models / cross-render cache” as the Phase 2 answer, and explicitly deferred it pending measurements that prove Phase 1 insufficient. Today is that measurement. Twenty entities, 387 MB DB, 8.8 s foreground latency on a routine click. Phase 1 was necessary. It is not sufficient.

The 2026-04-20 revert is load-bearing context

The previous attempt to unify on a single pool (commit 72e7b036) was reverted the same day (8bfdfdd8) because it held a parking_lot mutex across a 240-second Glean .await call. Thirty-one threads parked. macOS beachballed worse than before. The team’s reasonable conclusion was “pool unification is dangerous,” and every subsequent fix has been incremental gate-tightening instead. That revert is why the conversation has gravitated toward more locks rather than fewer consumers. It is the lesson the new proposal must honor — do not put a lock in a path that crosses an LLM .await — without taking it as evidence that the topology itself can’t be improved.

Cross-domain

Linear, Notion, Slack do not put SQLite on the synchronous read path.

Across the closest comparable systems — Linear (MobX object pool over IndexedDB transaction queue), Notion (in-memory record store hydrated from SQLite, OPFS serialized through one SharedWorker), Obsidian (in-memory index persisted out-of-band), Slack (retreated from local caching entirely, then moved libchat to a separate process) — the persistent embedded store is a cache or replay log, not the live read path. The UI reads from memory.

That is the pattern DailyOS is not yet using. The team has been trying to make SQLite fast enough for the synchronous foreground path; the industry pattern is to take it off that path entirely. Linear’s Tuomas Artman talks and the Notion offline writeup are the canonical references; the Slack case is the cautionary tale (caching the world locally exceeded the contention it was meant to avoid).

The relevant SQLite-specific findings reinforce this:

  • WAL alone is not enough when you have a long-running writer. Commits still serialize, and PASSIVE checkpointing can’t truncate when writers/readers overlap. A dedicated checkpoint thread running PRAGMA wal_checkpoint(PASSIVE) every ~30 s is the standard mitigation.
  • SQLCipher CPU cost on reads is real. Every page read decrypts via AES; at 387 MB with cipher_page_size=4096 a full-table scan touches ~100 K pages through AES. Under concurrent load this is CPU starvation, not lock contention. Yet another reason “make foreground reads pure” only partially helps.
  • Reader pool sizing rule of thumb: N+1 where N = number of read-path latency tiers. For DailyOS: foreground UI / foreground sync command / background task / maintenance = 4 connections, strict ownership, never share connections across tiers.
  • Smaller writer-hold windows via claim-type / side-effect decomposition + row-chunked durable cursor. A 150-row enrichment held in one transaction combining many claim types + side-effects + assessment upsert is the floor for foreground write latency. Split the atomic boundary by claim-type and side-effect class (architectural), then row-chunk within a class by committing per ~100 rows, returning to the writer’s mpsc loop, and re-enqueuing the next chunk from the caller using a durable batch-offset cursor. Same correctness with smaller critical sections and explicit partial-commit recovery. Note: the DailyOS writer runs on a sync std::thread, not async; the chunking is caller-driven re-enqueue, not yield_now().await inside the writer.
  • Same-DB CQRS-lite has known SQLCipher pain. ATTACH for a read-only file doubles key rotation and sync complexity; the forum threads on this are uniformly negative for encrypted setups. In-memory layer outperforms it in every dimension we care about.

Alternatives

Four paths, ranked by “solves the user-visible problem at acceptable cost”.

A is mandatory production hygiene. A☆ (subject-ref-hash partitioned writer queue) is a separate architectural move that’s potentially much cheaper than B and addresses the recurring class more directly than yieldable writers do. B (in-memory claim graph) is earned only when A and A☆ leave reader-CPU as the residual bottleneck. C requires multi-surface need. The right alternative is the cheapest one that closes the user-defined issues — not the most architecturally complete.

Alternative A · Hygiene, staged

Production hygiene. Four measurement gates, not one bundle.

~600–1,200 LOC · staged + measured · reversible

WAL tuning, larger reader pool, yieldable writer, presence-aware admission, batched claim commits, and the bypass closure. This is overdue production hygiene for SQLite under background write load — not architectural completion. Treating A as a single bundle invites the “we did architecture, no need for B” trap. The fix: stage A as four sub-decisions, each gated on measurements that name whether the next sub-PR is even needed. A1–A2 are unconditional. A3, A4, A5 run only if the data after A1–A2 says so.

Changes

  • WAL pragmas: wal_autocheckpoint = 200, mmap_size = 256MB, cache_size = -64MB, journal_size_limit = 64MB
  • Dedicated checkpoint thread running wal_checkpoint(PASSIVE) every ~30 s
  • NUM_READERS: 2 → 4, with strict tier ownership (foreground UI / foreground sync / background / maintenance)
  • Per-subject-domain TX decomposition + row-chunked durable cursor: split the atomic boundary per domain, commit per ~100 rows, re-enqueue from caller (sync writer; no yield_now())
  • Presence-aware admission: pause non-urgent enrichment when Tauri window has focus AND last user input < 30 s
  • Parallelize build_account_detail_result sub-queries via tokio::join! across reader tiers
  • Close 16+ conn_ref().execute() single-statement bypasses found in the architecture map (route through queue)

Tradeoff

Total enrichment throughput drops 30–50%. A 150-row write goes from “1.5 s blocking” to “5 s in chunks with yields.” UI stays responsive. SQLCipher CPU cost remains.

Alternative A☆ · 1 week

Subject-ref-hash partitioned writer queue.

~600–1,000 LOC · substrate change · conditional on W1 measurement

Partition the single writer queue into N writer threads keyed by hash(subject_ref) % N. With 18 background workers operating on disjoint subject domains (accounts vs meetings vs people vs projects), A☆ eliminates app-level mpsc head-of-line blocking and improves writer fairness across subject domains. Note: SQLite WAL allows exactly one file-level writer, and DailyOS’s process-wide WRITE_TRANSACTION_GATE (db/core.rs:214-238) serializes every transaction. A☆ does NOT enable concurrent WAL writes — what it does is prevent account-A’s long enrichment from queueing meeting-B’s prep rebuild on the same mpsc channel. Each writer still reaches the SQLite gate independently and interleaves at BEGIN/COMMIT granularity.

Why it might suffice

  • If W1-A1 (per-subject-domain TX decomposition) shortens individual writer critical sections from seconds to tens of ms, then app-level mpsc HOL-blocking IS the bottleneck and A☆’s fairness win is real.
  • Reuses the existing PooledConnection infrastructure with minimal surface change — adds N writer instances instead of one.
  • Improves UX consistency: foreground writes don’t see arbitrary multi-second waits because some unrelated background entity’s mpsc is full of work.

Why it might not

  • If W1-A1 already shortens TXs to tens of ms, A☆’s residual marginal value at the SQLite layer may be small. The win is fairness, not throughput. The W1 hard gate measurement names whether this matters.
  • SQLCipher read-path CPU cost is unaffected. If the residual bottleneck is reader-CPU under encryption, A☆ doesn’t fix it; B is still earned.
  • Multi-subject claim mutations (entity-merge, batch reconciliation) need explicit cross-partition coordination via a dedicated writer that takes all partitions’ locks in canonical order — W2-B owns this audit.

Alternative B · 2–3 weeks

In-memory claim graph.

~3,000–5,000 LOC · substrate-tier · matches Intelligence Loop semantics

Materialize the active claim set + entity graph as an in-memory Rust structure (DashMap or Arc<RwLock<...>> with versioned snapshots). Foreground reads hit memory. Background writes update SQLite, then dispatch a delta to the in-memory store. Boot hydrates from SQLite. This is the Linear / Notion pattern applied to DailyOS’s claim substrate.

Why it fits DailyOS specifically

  • Claims have lifecycle, provenance, trust bands, sensitivity. All of which the in-memory model can carry as typed structures.
  • The Intelligence Loop’s 5-question integration check becomes the cache-coherence contract: every claim mutation already emits a signal → that’s your invalidation primitive.
  • SQLCipher CPU cost on reads disappears entirely — reads are in-memory pointer chases.
  • Open question: memory budget. 16 k active claims today × ~1 KB each = ~16 MB resident. At 100× scale that’s 1.6 GB. Need a working-set policy.

Tradeoff

Cache invalidation complexity. Harder debugging when memory and disk diverge. Doesn’t help non-claim queries (accounts, meetings, actions) unless they’re also mirrored.

Alternative C · 4–6 weeks

Separate cache service process.

~8,000–15,000 LOC · multi-surface architecture · only when needed

Dedicated Rust process owns SQLCipher (single writer, single reader pool), exposes a query/mutation API over Unix socket or shared memory. Tauri renderer talks to it. Background enrichment talks to it. MCP servers talk to it. DB is touched by exactly one process; renderer can never be starved by DB CPU.

When to consider

  • Multi-surface architecture becomes load-bearing (Tauri renderer + MCP service + WordPress surface all needing live claim access)
  • Substrate-tier vision matures: per project_dailyos_product_path_uncertain.md memory, DailyOS substrate may go OSS or layer onto WordPress. A separate cache service is a natural API boundary for that.
  • B’s in-memory layer grows IPC needs anyway — might as well skip the intermediate step.

Tradeoff

IPC serialization overhead on every read (50–200 μs). Process lifecycle management. Harder local dev. SQLCipher key handoff across processes is non-trivial. Overkill for solo-user macOS app at current scale.

Recommendation

The cheapest alternative that closes the user-defined issues wins. Earn each next step with measurement.

The user-defined issue is foreground responsiveness during normal app use under continuous background work at twenty entities. The goal is not architectural completion; the goal is no beachballs and acceptable foreground latency at acceptable cost. A is the floor. Beyond A, the data names which alternative (A☆ or B) is earned — and they don’t address the same residual bottleneck, so picking the right one matters. C is out until multi-surface need joins.

Decision tree

W0 — Production hygiene foundation. Unconditional.
WAL pragmas + checkpoint thread (W0-A), reader pool resize 2→4 + per-command queue/exec/writer-hold telemetry (W0-B), two ADRs + K-out doc (W0-C). Land all three in parallel. Then run the W0 measurement protocol (below).

W0 gate — the threshold to stop.
Under a 10–15 minute scripted peak load (20 entities, 3 concurrent Glean enrichments, all 18 background workers active, ~50 foreground IPC invocations distributed across the window): p95 get_account_detail < 200 ms, no main-thread interaction stall > 100 ms (Apple responsiveness guidance), zero writer-gate waits > 250 ms, WAL stays under 5 MB, growth-slope predicts no breach at 100 entities. If all five pass, W1 is unjustified. File the ADRs, K-out, and the Linear ticket for the 50/100/200-entity re-measure (mandatory before W0 closes), and stop.

W1 — Earned hygiene extensions. Conditional on W0 gate missing.
Three lanes, each gated by a specific signal from W0’s telemetry:

  • W1-A (per-subject-domain TX decomposition + row-chunked durable cursor) — earned if writer execution_ms p95 > 500 ms during enrichment bursts. Two-PR structure: (a) split persist_enrichment_write_results_via_db_service into per-subject-domain transactions (the architectural fix); (b) row-chunking within a single domain with a durable batch-offset cursor, idempotency keys, and crash property tests. Requires a new ADR explicitly amending ADR-0104’s atomicity contract.
  • W1-B (presence-aware admission) — earned if foreground p99 > 3× p50 during user-active windows, measured across at least 5 sessions. Tracks last_user_input_at across mousemove, keypress, scroll, and focus-within (broader than mouse alone).
  • W1-C (bypass closure + CI gate) — unconditional, mechanical. Confirmed bypass count is ~190+ via feasibility re-audit (filtering test files; codex’s earlier ~90 was a partial count; architecture map’s 16 was the high-frequency hot subset); the existing startup_background_db_access_lint_test.rs gate covers 5 startup files. W1-C migrates the high-frequency hot sites first (the original 16+) AND adds a forbidden-pattern CI gate on conn_ref().execute* outside an explicit transaction allowlist. The remaining ~170 lower-frequency sites become forbidden-by-default; allowlist entries require review.
  • W1-D (ReaderTier enum migration) — earned if W0-B instrumentation shows tier confusion as a bottleneck. The 197 db_read call sites (not ~80) are too large to migrate unconditionally in W0; defer to W1 until the measurement names the need.

W1 hard gate — which downstream alternative is earned.
Re-measure. If p95 foreground < 200 ms under real load ⇒ stop; A1–W1 is sufficient. Otherwise diagnose the residual bottleneck:

  • If writer execution_ms p95 remains the dominant cost AND multiple subject domains contend concurrently → W2 (A☆) is earned. Partitioned writer queue is potentially much cheaper than B and is the cheapest substrate change that addresses the recurring class directly.
  • If reader-side latency dominates AND CPU on SQLCipher page decryption is the residual → WX (B) is earned. A☆ won’t close reader-CPU starvation; only moving the read path off SQLite does.
  • Both can be true at scale. If they are, W2 lands first (cheaper), then WX re-evaluates on W2’s residual measurement.

WX — In-memory claim graph (Alternative B). Conditional on reader-CPU as residual.
Out of scope for this packet’s implementation. Opens its own L0 with measurements from W1 (or W2) as trigger evidence. Must answer all five Intelligence Loop integration questions, not just the signal-invalidation leg.

C — Separate cache service process. Earned by multi-surface need, not latency.
Latency measurements alone do not justify the IPC overhead. C earns when a second surface (MCP service, WordPress layer, public substrate) joins the system and needs live claim access. Until then, C is overhead without payoff.

Measurement protocol (re-run after W0 close and W1 close)

Scripted peak load, 10–15 minutes: 20 entities, 3 concurrent Glean enrichments staggered to overlap, all 18 background workers active, ~50 foreground IPC invocations distributed across the window (account-detail navigation, meeting-intelligence open, refresh actions, audit-log opens). Durable telemetry (persistent rollups or SQLite-backed metrics table; not 256-sample in-memory windows). Capture: p50/p95/p99 of get_account_detail, get_meeting_intelligence, get_linear_status; writer execution_ms distribution per subject-domain; WAL file size sampled every 5 s; per-tier reader queue depth; gate-wait at the 250 ms threshold, not the 5 s warn threshold (instrument the gate to record waits above 50 ms); main-thread interaction stalls > 100 ms (from frontend perf marks).

Re-measure commitment is a Linear ticket, not prose

W0 close requires: a Linear ticket created and assigned for “Re-run measurement protocol at 50, 100, 200 entities,” with sequencing and target dates. If the ticket doesn’t exist, W0 is not done. This is the only way the “A treated as architectural completion” failure mode gets observable mitigation, not a calendar wish.

Wave plan

Two unconditional waves. One conditional. WX deferred to its own L0.

Standard DailyOS wave protocol: no wave starts until prior wave clears its gate, agents fan out within a wave on non-overlapping files, two revision cycles → L6. W0 is unconditional hygiene. W1 is conditional on W0’s measurement gate naming each lane’s earn signal. W2 (Alternative A☆, partitioned writer queue) is conditional on W1’s hard gate showing multi-subject writer-hold as residual bottleneck. WX (Alternative B) is a separate L0 packet opened only when reader-CPU dominates as residual.

Bounds

Honest risks and what this plan deliberately does not do.

Risks

  • A treated as architectural completion is the primary failure mode. The team lands W0, foreground latency drops, things feel better for a few days, and the 20/50/100/200-entity proof never runs. Mitigation: a Linear ticket for the 50/100/200 re-measure is a HARD gate on W0 close — W0 is not “done” until the ticket exists, is assigned, and has target dates. Growth-slope AC enforces that a 20-entity pass at point-in-time doesn’t obscure trajectory toward breach. The wave plan’s data-driven diagnosis at each gate (W2 vs WX) keeps “earned” observable rather than felt.
  • Hot-restart during landing can corrupt the DB (per 2026-05-25 lessons.md). W0-A (WAL pragma changes) and W1-A (transaction-cadence changes) are exactly the kind of edits where pnpm tauri dev’s hot-restart can terminate an active WAL writer mid-commit, producing real btree corruption even when later quick_check passes. Mitigation: land both PRs against a stopped dev app; test on a fresh DB or restored snapshot; never edit Rust DB files while the dev app is writing.
  • W1-A partial-commit recovery is contractual, not assumed. The yieldable batch cursor is a new substrate (not with_transaction_async) that explicitly relaxes ADR-0104’s atomicity guarantee. Each batch must be idempotent and durable; a worker crash mid-batch must leave committed claims with correct provenance and resumable from the offset cursor. Mitigation: crash property tests are part of W1-A’s AC, not optional; the new ADR explicitly names the atomicity relaxation; l2-bounded-reviewer gates on the crash semantics.
  • Forbidden pattern: holding any DB guard / writer permit / foreground flag across .await. The 2026-04-20 unify-pool revert (8bfdfdd8) was caused by a parking_lot mutex held across a 240-second Glean .await, parking 31 threads. Mitigation: ADR (writer queue responsibility) explicitly forbids any guard / permit / atomic flag from spanning an .await point; lint catches parking_lot::Mutex + .await in the same function body.
  • A’s checkpoint thread + WAL pragmas interact with SQLCipher. Need to verify checkpoint doesn’t race the key-verification path. Mitigation: run checkpoint on the writer thread (it already owns the encrypted handle).
  • Yieldable writer changes claim transaction semantics. If batch N commits and batch N+1 fails, the work is partially persisted. Mitigation: design batches so partial completion is recoverable — each claim has its own subject_ref; the worker can resume from the last committed offset. This is the same pattern runtime_evidence_backfill uses for its slice offsets.
  • Presence-aware admission can starve background work indefinitely on heavy-use days. Mitigation: aging mechanism — if a background entity has been deferred for >10 min, override the user-active check once and let it run.
  • Reader-tier ownership requires migrating every db_read caller. Scope: 197 sites (per feasibility audit, not ~80). Mechanical change. Mitigation: clippy lint that flags missing tier parameter; default-to-ForegroundUi for Tauri commands minimizes call-site changes.
  • A may not be enough. Possible. The decision gate names what we measure to find out. If A is insufficient at 20 entities, B’s in-memory layer is the documented next step.

Non-goals

  • No second SQLCipher DB file. Rejected at the foreground-db-contention L0 packet for sync / key-rotation / purge complexity. The in-memory layer (B) replaces this option.
  • No same-DB materialized projections. Same-DB CQRS-lite is a known anti-pattern in SQLCipher (key rotation across attached files, sync-from-live writer load). ADR-0062 says “compute live until profiling shows otherwise”; if profiling demands it, B (in-memory) is the projection, not a second SQLite table.
  • No type-system ReadDb / WriteHandle split. The db-write-queue-consolidation v2 deferred this behind “third storm proves the gate insufficient.” Current storm class is WAL-management + atomicity-shape, not bypass-permission. Hold the deferral.
  • No cooperative-yield scheduler or task-priority system. v1 of this proposal included one; L0 BLOCKED it. Presence-aware admission (W1-B) is the only admission-control primitive built here. A general scheduler is out of scope.
  • No new ADR-0067 amendment. ADR-0067 was right at the time; W0’s additions are the “earn it” outcome ADR-0067 named. Cite it, don’t rewrite it.

Invariants preserved (not non-goals — never up for negotiation)

  • Claim correctness. Batching transactions changes commit cadence, not contract. Each claim is validated, deduplicated, signal-emitted per existing rules. ADR-0126 memory substrate invariants hold.
  • SQLCipher key initialization order. ADR-0092 invariants hold; PRAGMA key first.
  • Service boundary. ADR-0101 contract holds; W1-C closes conn_ref().execute* bypass sites and adds CI enforcement.

Done means done

Acceptance criteria the implementation must meet.

Each criterion is testable against real data, with all 18 background workers active and Glean enrichment running on at least three entities concurrently. The decision gate after A passes or fails on these numbers.

  • AC1 · p95 get_account_detail < 200 ms under the 10–15 min scripted peak protocol (20 entities, 3 concurrent Glean enrichments, all 18 background workers active, ~50 foreground IPC invocations distributed across the window). p99 < 500 ms is the degraded ceiling, not the target.
  • AC2 · No main-thread interaction stall > 100 ms (Apple responsiveness guidance) during the scripted load.
  • AC3 · WAL file size stays < 5 MB across the 15-min enrichment burst. Continuous checkpoint thread proves itself.
  • AC4 · Zero writer gate-waits > 250 ms at user-active times (gate must be instrumented at the 50 ms threshold, not the 5 s existing log).
  • AC5 · Zero database is locked errors in any worker for 24 hours of normal use.
  • AC6 · Growth-slope criterion. Re-measure at 30 and 40 entities; fit a line through {20, 30, 40} datapoints; if the slope predicts p95 breach at 100 entities, open the WX L0 packet for B even if 20-entity passes. Trajectory matters, not just point-in-time.
  • AC7 · Linear ticket filed at W0 close: “Re-run measurement protocol at 50 / 100 / 200 entities” with sequencing + target dates. W0 is not done until the ticket exists and is assigned.
  • AC8 · ADRs filed. Writer queue responsibility ADR exists, names what the queue serializes and what it doesn’t, and the executor.rs:632/1052 “own DB connection” comment is removed. Reader pool sizing ADR exists. If W1-A ships, ADR amending ADR-0104 atomicity contract exists.
  • AC9 · K-out solution doc filed at docs/solutions/architecture-patterns/db-lock-storm-class-2026-05-27.md.
  • AC10 · W1-A crash recovery proven (if W1-A ships). Property test demonstrates that a worker crash mid-batch leaves committed claims with correct provenance and the resume cursor advances to the next un-attempted offset. Idempotency-key replay test passes.
  • AC11 · W1-C 90+ bypass sites closed. CI gate fails on new conn_ref().execute* outside named allowlist.
  • AC12 · W2 cross-partition audit landed (if W2 ships). Multi-subject-domain operations (entity-merge, batch reconciliation) explicitly serialize via the cross-partition coordinator. No deadlock detected in property tests across 1,000 randomized partition-locking sequences.

Stop criteria, in order of cost: If AC1+AC2+AC3+AC4+AC6 pass after W0, stop — W1 unjustified. If they pass only after W1, stop — W2 / WX unjustified. If they pass only after W2, stop — WX unjustified. If they still miss after W2 AND the residual is reader-CPU-dominated, open WX.

The point of these criteria is to make “the storm class is closed” an observable claim grounded in tighter thresholds (p95 not p99; 100 ms not 500 ms; 250 ms gate not 5 s; growth-slope not point-in-time) and a Linear-ticket commitment to re-measure at higher scale. No wave beyond W0 lands without the prior wave’s measurement gate proving it’s needed.
