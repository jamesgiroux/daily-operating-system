# L0 Codex Challenge - W3 Chrome Lane Cycle 1

Verdict: CONDITIONAL APPROVE

Must-fix before L1:

- Token alias premise: OK. `wp/dailyos/theme/theme.json:684-725` nests `settings.custom.dailyos.tokens`; `folio-height` at `wp/dailyos/theme/theme.json:690` emits `--wp--custom--dailyos--tokens--folio-height`. WP behavior: custom keys emit `--wp--custom--*`; nested levels are separated with `--`; camelCase becomes kebab-case. Cite: `https://developer.wordpress.org/block-editor/how-to-guides/themes/global-settings-and-styles/#the-naming-schema-of-css-custom-properties` lines 1238-1241, 1253-1280; `https://developer.wordpress.org/news/2023/08/adding-and-using-custom-settings-in-theme-json/` lines 116-126, 249-256. Keep AC #3.
- Palette premise: OK. Example source exists: `spice-turmeric` palette slug at `wp/dailyos/theme/theme.json:443-445`; WordPress preset format is `--wp--preset--color--{slug}` per WP docs above lines 1232-1236.
- Editor-context alias risk: add computed-style proof for frontend + Site Editor iframe. WP outputs `settings.custom` variables on frontend and editor per `https://developer.wordpress.org/news/2023/08/adding-and-using-custom-settings-in-theme-json/` lines 77-80, 116-120, but packet AC #19 uses `add_editor_style()` for alias CSS at `.docs/plans/v1.4.4-wp-surface-migration/L0-packet-W3-chrome-lane-pulled-forward.md:206`; editor styles can be scoped/re-written. Test `getComputedStyle(editorIframe.contentDocument.documentElement/body).getPropertyValue('--folio-height')`, not just enqueue handles.
- Runtime injection is frontend-only unless deliberately enqueued into editor content. `wp_enqueue_scripts` is frontend asset loading: `https://developer.wordpress.org/themes/core-concepts/including-assets/` lines 119-121, 247-255. Editor UI JS uses `enqueue_block_editor_assets` and not the content iframe: same doc lines 296-298. Editor content iframe assets use `enqueue_block_assets`: `https://developer.wordpress.org/block-editor/how-to-guides/enqueueing-assets-in-the-editor/` lines 95-98. Packet line `.docs/plans/v1.4.4-wp-surface-migration/L0-packet-W3-chrome-lane-pulled-forward.md:206` says chrome does not render in editor iframe; keep that explicit.
- Customizer preview: likely renders because preview is a frontend iframe and `wp_enqueue_scripts` fires, but live preview updates need `customize_preview_init`. Cite: `https://developer.wordpress.org/reference/hooks/customize_preview_init/` lines 72-76. Add acceptance note: Customizer initial render supported; live postMessage updates out of scope or separately wired.
- DOM mutation idempotency missing. Canonical `inject()` prepends/appends unconditionally at `.docs/design/reference/_shared/chrome.js:465-488`; no guard for existing `.FolioBar_folio`, `.FloatingNavIsland_navIslandContainer`, `.AtmosphereLayer_atmosphere`. Add guard/cleanup before mutation. Otherwise repeated execution from preview reloads, partial refresh, or future iframe asset routing duplicates chrome.
- Conditional enqueue risk: do not gate chrome enqueue only on `is_singular('dailyos_account')` / archive / front page. Packet expects graceful default for unmapped post types at `.docs/plans/v1.4.4-wp-surface-migration/L0-packet-W3-chrome-lane-pulled-forward.md:197,204`; global non-admin frontend enqueue is safer. `wp_add_inline_script()` must attach to an enqueued handle: `https://developer.wordpress.org/themes/core-concepts/including-assets/` lines 265-276.
- Future blockification cost must be quantified in packet. If future blocks preserve emitted class contracts (`FolioBar_*`, `FloatingNavIsland_*`, `AtmosphereLayer_*`, `Pill_*`) and body-data config keys, blockification is roughly 3 dynamic blocks + 1 wrapper pattern + parity tests, ~700-1100 LOC, ~2-4 days. If downstream selectors depend on runtime insertion order or wrapper placement from `.docs/design/reference/_shared/chrome.js:474-486`, cost becomes CSS/JS migration + visual QA, ~2x. Add invariant: downstream CSS/tests target class contract, not DOM insertion side effects.
- Pill selector collision: low risk. Plugin block selectors are `.wp-block-dailyos-pill .dailyos-pill`, `.dailyos-pill`, `.dailyos-pill__dot`, `.dailyos-pill--*` at `wp/dailyos/blocks/pill/style.css:5-47`. Chrome selectors are `.Pill_pill`, `.Pill_standard`, `.Pill_dot`, `.Pill_*` at `.docs/design/reference/_shared/styles/Pill.module.css:1-104`. `--pill-*` variables are scoped inside those class rules, not `:root`. Real issue is duplicated primitive ownership, not selector collision.
- Header template part: do not ship literal raw `<div class="dailyos-header-noop"></div>` from packet `.docs/plans/v1.4.4-wp-surface-migration/L0-packet-W3-chrome-lane-pulled-forward.md:214`. WP docs: template parts contain block markup and nothing else, `https://developer.wordpress.org/themes/templates/template-parts/` lines 101-115; block templates are block markup, `https://developer.wordpress.org/themes/templates/introduction-to-templates/` lines 111-123. Use valid empty Group block markup, e.g. `<!-- wp:group {"className":"dailyos-header-noop"} --><div class="wp-block-group dailyos-header-noop"></div><!-- /wp:group -->`, or explicitly use `core/html` and accept that it is not a Group block.
- Site Editor save behavior: saving a template part writes a `wp_template_part` database override that wins over the theme file. Cite: `https://developer.wordpress.org/themes/templates/template-parts/` lines 152-159; `https://developer.wordpress.org/block-editor/explanations/architecture/full-site-editing-templates/` lines 68-86. Add L4 check that edit/save/reload does not resurrect old header markup and document reset path for stale DB overrides.
- AC #20 wording overclaims "before first paint" at `.docs/plans/v1.4.4-wp-surface-migration/L0-packet-W3-chrome-lane-pulled-forward.md:219`. `chrome.js` injects on `DOMContentLoaded` or immediate execution at `.docs/design/reference/_shared/chrome.js:491-492`; footer-enqueued JS cannot guarantee before first paint. Reword to "before user interaction" or implement head/critical CSS strategy.
