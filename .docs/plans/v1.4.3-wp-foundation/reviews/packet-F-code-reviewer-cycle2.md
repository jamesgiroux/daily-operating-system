**Verdict:** CONDITIONAL APPROVE (surgical conditions, no BLOCK)

**Summary:** V1.1 substrate K-in is largely accurate and the parallel-substrate trap from V1.0 is cleanly remediated — every cited file:line resolves to real code. ## Top findings

### F-cycle2-1 — §5.4 atomic-tx wire-through composition is incompatible with `record_claim_feedback`'s own tx + guard (HIGH)

**File:** `/tmp/dailyos-w4/src-tauri/src/services/claims.rs:6700` + `:6714` + `:6717`. **Evidence quote:** at :6714 `let mut mutation_guard = MutationGuard::reserve(db, input.claim_id.clone(), ctx.clock.now())?;` runs BEFORE :6717 `let write = with_claim_transaction(db, |tx| {`. The function reserves its own guard and opens its own claim transaction. The packet's §5.4 pseudocode at lines 228–236 proposes `with_transaction(db, |tx| { mark_consumed_if_unclaimed(tx, ...); record_claim_feedback(ctx, tx, input) })` which assumes (i) `record_claim_feedback` takes a `tx` parameter (it takes `db: &ActionDb`) and (ii) the caller can compose a single outer tx around nonce-mark-consumed and the feedback write. Neither is true today. Additionally, the existing `verify_and_consume` at :640–:734 already marks consumed via `binding.try_mark_consumed(now)` against an in-memory `tokio::sync::Mutex` — there is no DB row for the nonce to UPDATE. **The "atomic single-transaction" framing the packet promises in §5.4, §6.10, §9.6 cannot be achieved without either refactoring `record_claim_feedback` to accept a caller-supplied tx (out of scope per Decision #2's CI gate) or accepting that atomicity is the composition of two non-joined critical sections (the in-memory nonce mutex + the claims tx + the MutationGuard).** Confidence: 100. **Surgical fix:** rewrite §5.4 to specify ordering ("verify_and_consume first → on success call record_claim_feedback → if record_claim_feedback fails, the consumed nonce stays consumed (intentional fail-closed)") and state explicitly that the existing in-memory `try_mark_consumed` race + the `MutationGuard::reserve` chokepoint together produce the equivalent-to-atomic behavior the security-auditor finding was asking for. Drop the misleading `with_transaction(db, |tx| ...)` pseudocode.

### F-cycle2-2 — Rejection reason vocabulary collides with existing enum (HIGH)

Either the existing wire shape changes (breaking W2/W3 callers + the existing PHPUnit/Rust tests that already check `Replayed`/`WrongUser`) or the packet's promised reason names never appear. **The implementer reads §5.5's audit-payload table promising `rejection_reason: "already_consumed"`, writes a test asserting it, and discovers the substrate emits `Replayed` instead.** Confidence: 100. **Surgical fix:** §5.5 table and §6.10 and §8.3/§8.4 AC must use the existing reason names (`Replayed`, `Expired`, `WrongUser`, `MalformedRequest`) — or §5 must explicitly call out that W4 renames these enum variants and lists every test/caller affected. The current packet does neither.

Either specify "tuple match in `compare_binding_tuple`" (consistent with how the other fields work) or accept the HKDF redesign cost; the packet conflates the two.

No schema change needed for audit-event storage. Confidence: 100.
