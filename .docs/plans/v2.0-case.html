DailyOS · v2.0

The Case for the Rebuild

Personal intelligence means context that only ever grows. The current shell's cost grows with it. v2.0 rearchitects everything between the store and the user's eyes — the surfaces and the read path — on the substrate the outside world just validated.

This document makes four arguments in sequence: the category we serve demands a shell whose performance is independent of accumulated context (§1); the 19-week journey shows the substrate crystallizing while the shell superseded itself (§2); the scaling chain, measured end to end, shows why no per-page patch can fix it (§3); and an unconstrained greenfield exercise against the mid-2026 toolscape independently re-derives the same boundary (§4). Then it names what v2.0 is (§5) and what it costs (§6). Supersedes the 2026-06-11 boundary draft; its keep/kill matrices fold into §5.

Gated + red-teamed 2026-06-11 · amendments applied Scope: shell + read path (checkpoint-gated) Data layer: owned Rust projections; framework must beat it at L0 Chat escape hatch: in scope

§1 · The category

Personal intelligence demands a different shell.

DailyOS is memory plus judgment. Memory that compounds is the product premise — which means context growth is not an edge case to tolerate; it is the success condition to design for. A shell serving this category has four non-negotiable properties, and the current shell has none of them structurally.

Consumption-first

"The AI gathers, compiles, organizes. You show up and consume the output" (PHILOSOPHY). Today 21 of 25 surfaces hand-assemble meaning via 1–28 imperative invokes each — the frontend is the operator, the exact failure MISSION attributes to the status quo.

Trust rendered uniformly

"Trust as a testable contract — no drift between surfaces" (PRODUCT-THESIS). Today the same claims render through two display grammars and corrections enter through three write paths; drift between surfaces is the standing state, not a risk.

Push-first proactivity

"It should just know" — before the user asks. Today's 26-route navigation taxonomy is a mission-control destination the user operates; the briefing is one route among many rather than the front door.

Performance independent of context

A memory product that slows down as memory accumulates punishes the user for using it. Today shell cost is proportional to accumulated claims — §3 measures the chain.

Surface inventory and thesis-alignment audit: .docs/plans/v2.0-shell-audit.md §1, §4 (measured at commit 0262d6bb; key numbers re-verified for this document).

§2 · The journey

Nineteen weeks of earned asymmetry.

First commit 2026-01-29. Since then: 2,570 commits, 140 ADRs, 31 documented problem→fix captures. The record splits cleanly in two — and the split is the case. Each shell patch was rational in the moment; the accumulation is the lesson.

Evidence Substrate (claims · abilities · services · trust) Shell (pages · layouts · data paths)
ADR supersessions No post-April substrate ADR superseded (~8 weeks stable; early-era substrate ADRs 0018 and 0092 were superseded — the asymmetry is recent-era, stated honestly). ADR-0101 → 0102 → 0105 → 0113 → 0125 → 0130 is a learning chain, each building on the last. Dashboard layout superseded twice in six days (ADR-0053 → 0055 → 0077); ADR-0034 deprecated after acceptance; ADR-0052's readiness enums invalidated within ten days by ADR-0081.
Failure record 0 of 31 docs/solutions/ entries trace to substrate-internal failures. Trust, claims, signals: zero bug-class captures. §3 · The scaling thesis

The shell cannot stay performant for one user with twenty accounts.

Every link in the chain below is measured, not estimated. Read top to bottom: each row grows with accumulated context, and the product's job is to accumulate context.

Link Measured state Why it grows with context
Claim accumulation 7,357 claims; worst subject carries 2,143 (1,874 active). The working figure of "693-claim subjects" understated reality 3×. Enrichment commits projection claims per dimension per run; nothing bounds a subject's claim count until DOS-866's caps land.
Signal amplification ~311,000 signal_events rows — 43 events per claim, ≈60% of the 397 MB database (table + indexes ≈ 237 MB). Every enrichment emits and propagates signals inside the gated transaction (services/intelligence.rs:2087).
Enrichment grind Trust recompute loads all active claims for a subject on the 2 remaining unbounded call sites (intel_queue.rs:3583, invalidation_jobs.rs:449; a bounded paged variant already exists at trust_recompute.rs:65); persist re-merges the full legacy snapshot; parent cascades multiply runs. Work is O(accumulated claims), not O(new information). The 2,143-claim subject makes every touching signal cost a full pass.
Write serialization One process-wide gate (db/core.rs:96), ~16 background producers, 120 s transaction timeout; an enrichment persist holds the gate for its entire transaction (intel_queue.rs:2713-2746) — the DOS-866 starvation class, twice incident-confirmed 2026-06-10/11. More context → more producers firing → longer holds → deeper foreground queue.
Read amplification Legacy account detail = ~10 IPC round trips + a 30-query backend assembly (services/accounts.rs:1582-1837). The composition path reads claims at depth 3 with no limit and commits a composition row on the cache-miss path of a page load (account_overview.rs:148-152; 60 s in-memory cache, composition_render_orchestrator.rs:52). Reads walk everything the writes accumulated — and add a write of their own on the hot path.
Net effect 8.8 s on a routine account click at twenty entities — measured 2026-05-27 on the legacy get_account_detail path, pre-DOS-866 (mechanism per the lock-storm capture: WAL bloat starving the reader pool, amplified by combined-domain transaction shape). Twenty accounts is the floor, not the ceiling. The same chain at twice the context is not twice as slow — the holds, cascades, and unbounded reads compound.

The framing that matters: this is a read/write architecture failure, not a SQLite bug. The UI runs analytical, graph-shaped reads against the same store a continuous enrichment pipeline writes to — and the eight interventions of ADR-0133's history each governed who may write when; none separated the read workload from the write workload. The red-team correction this case adopts: whether targeted substrate fixes (DOS-866 + bounding the two unbounded recompute call sites + a limit on the producer read + moving the commit off the read path) dissolve the latency without read models is an open empirical question — so the read-model commitment is gated on a post-fix re-measurement (ADR-0139 checkpoint: entity click < 500 ms p95 on the live path kills the performance argument). What no targeted fix changes: the structural pattern of eight one-at-a-time interventions, each supposed to be the last.

Measurements: replica DB (plain SQLite, read-only queries, 2026-06-11), docs/solutions/architecture-patterns/db-lock-storm-class-2026-05-27.md, .docs/plans/dos-866-l0-packet.md. File:line citations verified for existence; runtime-behavior corrections (cache gating, paged recompute, legacy-path provenance) applied per the 2026-06-11 red-team — synthesis at .docs/plans/v2.0-case-redteam-2026-06-11.md.

§4 · The greenfield test

Built today, unconstrained, it lands in the same place.

Method: set the repo aside and ask what a top team would build in mid-2026 — shells, data layers, AI-native experience paradigms, agent runtimes — then compare. Red-team demotion accepted: this is a landscape scan consistent with the direction, not an independent derivation (same author, conclusion-aware). It supports the keep decisions; the rebuild decisions rest on §1–§3.

2026 landscape finding Evidence DailyOS disposition
Declarative typed-component dispatch won generative UI A2UI (production in Gemini/Opal), AG-UI protocol (Microsoft/Google/Amazon adoption), MCP Apps (Claude, VS Code). Consensus: agent names a component from a typed, pre-approved registry; the model never generates markup. That is ADR-0130 composition — producers, block registry, typed payloads. We built the winning pattern before the specs existed. Keep; externally validated.
Memory commoditized; judgment didn't Vector + BM25 + entity fusion is table stakes (mem0-class). The field's own state-of reports name staleness, salience, provenance, and trust as the unsolved problems; no shipping competitor exposes trust-band semantics. Exactly the claims / trust / lifecycle / correction substrate. Keep; this is the moat, now with outside confirmation.
The experience paradigm went post-chat and push-first Google's Daily Brief, Siri AI's briefing surface ship push-first; ChatGPT Pulse attempted and paused (evidence cuts both ways). Convergent shape where it ships: briefing front door → structured drill-down → chat as escape hatch. The 26-route mission control is the wrong paradigm — not badly executed, wrong shape. Rebuild the surface taxonomy.
Local-first data layers went event-sourced / CQRS LiveStore (event log → materialized SQLite projections → reactive queries; no native Tauri adapter yet — red-team-verified correction of this case's research input), TanStack DB 0.6 (JS client layer), DuckDB reading SQLite for analytics. The pattern: background pipelines append; the UI subscribes. The frameworks' motivation is multi-device sync — a constraint this product doesn't have. The separation is right; the mechanism is owned Rust projections behind existing service contracts, framework only if it beats that at L0 — and the whole commitment is gated on the ADR-0139 re-measurement checkpoint.
Divergence check: the platform survives Both genuinely viable 2026 stacks keep Tauri 2 + Rust + React + SQLite; single-writer SQLite is designed around, never escaped. On-device models (Apple Foundation Models) handle classification/extraction for free; frontier calls reserve for synthesis. No framework migration. Greenfield does not indict the platform — only the read path and the taxonomy. On-device enrichment tiering banks as a v2.x lever.

The landscape scan is consistent with where the journey landed: keep everything below services/; rebuild everything between the store and the user's eyes. The scan corroborates the keep decisions — the moat and the composition model are what the field names as unsolved and converging respectively; the rebuild decisions stand on the internal evidence.

§5 · What v2.0 is

Three commitments on one boundary.

v2.0 changes how the product reads and renders, not what it knows. The boundary matrices below carry forward from the superseded draft, now justified by §1–§4 rather than asserted. Then three architecture commitments define the new side.

Disposition Crosses the boundary
Subsystem Why it crosses Citation
abilities-runtime crate Separate crate, clean boundary; producers, projection, and trust machinery proven in daily use. Never depended on the shell. ADR-0102, ADR-0111
Claims schema + services/ layer The memory+judgment moat: provenance, lifecycle, corrections. All mutations already flow through services/; v2.0 surfaces are new consumers, not new writers. §4 row 2: externally confirmed differentiator. ADR-0125, ADR-0113, ADR-0123
Composition substrate Model, registry, projection policies, per-item claim bindings — the pattern the industry standardized on (§4 row 1). v2.0's shell is built on it by definition. ADR-0130
Trust-as-opacity rendering model L4-approved 2026-06-10; keyed off per-claim provenance_kind; shell-independent. DOS-852
Design system Tokens, primitives, patterns, surfaces; .docs/design/reference/ as copy-paste canon. v2.0 blocks compose these patterns. ADR-0073, ADR-0077
DB hardening (writer queue + reader pool + DOS-866 fixes) Rank-then-cap, phased persist, W1-A — earned against real starvation incidents; lands at the substrate layer regardless of shell, and §5C builds on it. ADR-0133, ADR-0134, DOS-866
App as control plane Packaging, lifecycle, updates, and the only native push primitive — the 2026-05-29 adjudication's unanimous keep. Push-first (§1) requires it. .docs/plans/dailyos-rearchitecture-examination-2026-05-29.md
ADR corpus + docs/solutions/ + ladder process The K-channel and L0–L6 gates are version-independent; abandoning projects does not abandon what they taught. .docs/plans/engineering-ladder.md
Disposition Dies at the boundary
What dies Named successor Citation
The 26-route mission-control taxonomy Briefing-first taxonomy (§5A): briefing front door, entity drill-downs, deliberately small page inventory, chat escape hatch. §1, §4 row 3
All hand-wired page data paths (legacy hooks, per-page invoke assembly) CQRS read models the UI subscribes to (§5C). No page-owned fetching; no commits on page load; no unbounded claim reads. §3, db-lock-storm-class-2026-05-27.md
The legacy display grammar (intelligence-JSON as display source) + AccountDetailEditorial generation + dual hybrid hooks Producer-shaped block payloads as the only grammar. The mapper that translates claims back into the legacy JSON shape is deleted with its consumers. DOS-852, audit §2.4
Two of three feedback write paths Unified claim feedback writer — one path into claim state, carried on every block via claim_refs. ADR-0138, DOS-854
Tab views inside surfaces Pages-per-view + strip chrome per the DayStrip future-direction note. .docs/design/patterns/DayStrip.md
The parity layer (src/parity/, 874 LOC) One producer contract serving every surface (ADR-0128/0135): parity becomes a unit test on the producer, not a fixture-diff between two presentation codebases. audit §2.10, ADR-0128, ADR-0135
Dual same-purpose components (6 heroes, 2 shells, hook twins, 27 orphans) One component per purpose, reuse-first; deletion is an acceptance criterion (§6). CLAUDE.md, audit §2.7/§3.4

"Dies" means not ported and not shimmed: v1.x keeps running each surface until its v2.0 successor replaces it, and nothing on this list enters the v2.0 tree.

A · Briefing-first surface taxonomy

The D-spine briefing (±7-day window) is the front door; entity surfaces are drill-downs; the page inventory is deliberately small. Lists and triage are redesigned as consumption surfaces, not database operators. A chat escape hatch ships in v2.0 — available everywhere, primary nowhere — riding the existing ability-invocation surface.

B · Blocks are the only rendering system

One display grammar, one feedback path, salience-driven layout, trust bands carried on every block via claim_refs + provenance_ref. Deletion is an acceptance criterion: the measured precedent — two prior generations left in the tree — is the named failure mode, and a v2.0 that leaves v1.x rendering alive has produced a fourth parallel system, not a replacement.

C · Read/write separation — checkpoint-gated

The UI subscribes to materialized projections; pages never fetch imperatively, never read unbounded claim sets, never write on load. Enrichment persists in capped, phased batches (DOS-866 shape) on the write side. Mechanism (revised post-red-team): owned Rust projections behind existing service contracts; a framework must beat that at its L0. The whole read-model build is gated on ADR-0139's re-measurement checkpoint — if the targeted fixes alone hit <500 ms p95, the performance argument is dead and the commitment re-justifies on product grounds or not at all.

§6 · Costs and risks

Measured, with named mitigations.

The case is only honest if the bill is on the table. Estimates below are labeled estimates, calibrated against this repo's actuals (the 4-surface composition migration spanned multiple weeks).

Cost / risk Measured basis Mitigation
~10–15 engineer-weeks of migration surface Per-surface estimates in audit §6: MeetingDetail 2–3 wk, briefing 1–2 wk, triage 2–3 wk, lists 2–3 wk, reports 2–3 wk, hybrids 3–5 d; settings/onboarding carried, not rebuilt. Route-by-route swap behind the existing router is already proven (gen-3 account detail replaced gen-2 without a shell rewrite). ~4–5 users; migration cost near zero, downtime tolerance for customer-zero still not zero.
Three block-type families don't exist List, triage/action-dispatch, and report blocks have no analog in the 19-renderer registry; salience-ordered lists are a design problem, not a port. Named as v2.0 design work up front (James + Claude collaborative, per the v1.5.0 reconciliation decision) — not discovered mid-wave.
The graveyard pattern Two prior rebuilds left the old generation in-tree; 27 orphans and an unreachable shell are the measured precedent. Deletion as acceptance criterion on every conversion ticket; the wave is not done while the predecessor compiles.
The parity / perfection trap v1.4.9 W5 spent three days chasing perfect MCP parity before scope was manually cut. One producer contract per surface is the parity mechanism; multi-day polishing is a standing scope-cut signal at L0.
Read-model commitment built on stale evidence (§5C) The 8.8 s was measured on the legacy path, pre-DOS-866; LiveStore has no native Tauri adapter (red-team-verified); event-sourcing frameworks solve sync this product doesn't need. ADR-0139 checkpoint: targeted fixes land first, latency re-measured on the live path against <500 ms p95; owned Rust projections are the default mechanism; a framework must beat them at L0.
Overfitting the moment The 2026-05-29 adjudication's meta-warning: don't rewrite on the back of one incident. This case rests on the 19-week asymmetry (§2), the measured chain (§3), and an outside-in derivation (§4) — not on last week. And the moat-validation instrumentation from the examination's product-lens finding rides along: prove the judgment layer is felt.
