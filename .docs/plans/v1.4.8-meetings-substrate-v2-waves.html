Lane A · substrate + surface

Surface-relevant meetings projection.

Today the narrow read handle DailyReadinessContextReadHandle is shape-narrow but semantics-thin — it returns raw rows and each consumer re-implements the filter. Lane A makes the handle intent-carrying: the substrate owns the "what counts as a briefing-worthy meeting" policy, consumers declare intent, and one filter set lives in one place. The same PR re-enables the briefing self-assessment strip now that its data is correct.

  • Substrate change: new MeetingsViewIntent { Briefing, Schedule, AllRows } (final variants pinned at L0). New read_surface_meetings(db, workspace, date, tz, intent) -> Vec<SurfaceMeeting>. Promote focus_capacity::should_exclude_meeting into the substrate function.
  • Handle migration: DailyReadinessContextReadHandle::read_daily_readiness_context takes intent. Live impl threads it; test fixtures accept it.
  • Consumer migrations: get_daily_briefing declares Briefing. get_daily_readiness declares its intent (L0 question). focus_capacity callers route through the projection. Frontend defensive filter at DailyBriefing.tsx:283 stays or goes (L0 question).
  • Surface payoff: re-enable DailyBriefingAbilityStrip in DailyBriefing.tsx. The component logic isn't gone in git history — restore from PR #392's parent commit. The data it reads is now correct because Lane A's substrate change fixes the upstream source.
  • Closes DOS-771: the phantom NeedsPreparation(4) / UnlinkedMeetings(4) advisories are personal calendar blocks leaking through the readiness query. Lane A's substrate filter eliminates the class. Verified live as part of the DoD.
  • Definition of Done: see DOS-774.

Lane B · writer hardening

Apply the DOS-258 deterministic-engine pattern to meeting-row writers.

Currently 3+ production write paths into the meetings table — ensure_meeting_in_history, upsert_meeting, upsert_meeting_for_reconcile — set different field combinations with different invariants. There's no enforced contract that says "a meeting row is created via exactly one of these adapters with these required fields." DOS-258 solved this for entity linkage; Lane B does the same for the writer side.

  • Invariant matrix: required fields per row, transcript-row pairing rule, calendar_event_id NULL semantics, intelligence_state initialization. Pinned at L0.
  • Adapter pattern: services/meetings_writer/ with CalendarWriter, ReconcileWriter, ManualWriter. Each adapter normalizes its input source to the same DbMeeting shape with invariants enforced. Mirrors services/entity_linking/{calendar_adapter, email_adapter} from DOS-258.
  • Repository bypass: keep repository::raw_* for admin/migration paths; production code can't import it (pre-commit grep guard, same as DOS-258).
  • Backfill sweep: existing rows that violate the new invariants get repaired in a one-time migration. Likely targets: rows from old reconcile passes with local-format start_time strings; rows with calendar_event_id IS NOT NULL but no meeting_transcripts row.
  • Ad-hoc inserter migration: every INSERT INTO meetings outside the new adapters becomes a clippy/CI violation. Existing call sites migrate to the appropriate adapter.
  • Definition of Done: see DOS-775.

Open questions

  • Frontend defensive filter. Keep DailyBriefing.tsx:283 scheduleMeetings filter (defensive belt-and-braces) or remove (substrate owns it)? Trade DRY for defense.
  • Strip revival scope. Bring back exactly what PR #392 removed, or take the opportunity to refine the strip's content (e.g., drop "Trust: unscored" on no-meeting days, change advisory copy)? Flag for ce-design-lens-reviewer if material.

Lane B

  • Invariant matrix. Required fields per row? Transcript-row pairing required? calendar_event_id NULL semantics?
  • intelligence_state lifecycle initialization. What's the contract at write time?
  • Adapter granularity. CalendarWriter + ReconcileWriter + ManualWriter, or finer (e.g., separate GranolaWriter, EmailEnrichWriter)?
