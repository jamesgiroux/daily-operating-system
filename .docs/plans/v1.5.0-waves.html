DailyOS · v1.5.0 · Wave Plan · DRAFT

I shape the app to me — chapter by chapter.

Composable Surfaces. The Tauri app learns to render the block model the substrate already produces — and lets you compose it.

The substrate already describes a page as a list of typed blocks (ADR-0130's Composition) — and that model is already ~55% built. What's missing is the Mac app's ability to render it and let you compose it. v1.5.0 builds the React block renderer, an in-context edit/customize mode, and a thin slice of new block-producing abilities — built Gutenberg-informed but native, so the work is ~80% portable back to WordPress when we choose to. We consume the existing block substrate; we do not reinvent it, and we do not rebuild WordPress.

Target: 2026 (DRAFT) Waves: W0–W5 + WR (revision) + List-Surfaces lane Scope tier: Wave Decisions locked w/ James 2026-05-31

How to read this

Plain-language key.

Engineering-heavy plan; here's the jargon in plain terms. Every wave also has an "In plain terms" line. For the full picture of how the backend produces what the app shows, see the Abilities Explainer.

Block / chapter

A typed piece of a page the AI fills in — a risk callout, a health snapshot, a claim summary. The substrate calls them blocks; on screen they group into the editorial chapters you scroll. A page is a stack of them.

Composition

The substrate's already-built model for "a page = a list of blocks, each with its sources and trust band" (ADR-0130). The AI authors it; the app renders it. v1.5.0 builds the app's renderer for it.

Ability

A specialized backend function — a mini-analyst — that reads your data and produces claims / intelligence / a Composition, always with a record of where it came from. See the explainer.

Gutenberg-informed

We mirror WordPress's block patterns (block metadata, edit-vs-render split, inline text editing) in our own native code — so it ports back to WP later. We do not fork WordPress's code or rebuild it.

Layout overlay

Your saved per-type choice of which blocks show, in what order, in which variant. It sits over the AI-authored page; it never changes the data. This is the genuinely new thing v1.5.0 adds.

Wave · L0

Wave = a unit of work that ships together; later waves wait on earlier ones. L0 = the pre-build plan review this doc went through.

What's already built · grounded 2026-05-31

We consume the block substrate — it's ~55% done, not net-new.

A code review (not a guess) settled how much of ADR-0130 exists. This is the single most important framing: v1.5.0 builds the two missing parts, not a new composition model. Authoring a "chapter registry ADR" would reinvent shipped substrate — the L0 K-in check flagged exactly this.

Block model — DONE (~95%)

composition.rs (~1,480 lines): Composition, Section, Block, 18 canonical BlockTypes + Wave-1 primitives, Salience, ProvenanceRef, render hints — with tests and a CI lint enforcing substrate-only authorship.

Block registry + safe fallback — DONE (100%)

fallback_projection.rs (~1,716 lines): the unknown-block §3.1 projection — a privacy boundary (drop unknown fields, cap trust at needs_verification, non-dismissible banner), deterministic, tested.

React block renderer — ABSENT (0%)

The Mac app still hand-composes every page in React (renderHealthView etc.). There is no BlockRenderer, no block→component map. This is the net-new frontend, and the heart of v1.5.0.

Composition producers — SPARSE (1 of ~28)

Only dailyos/account-overview emits a Composition today. Project/Person/briefing/meeting still emit older intelligence JSON. "Full end-to-end" needs a thin slice of new producers.

In plain terms — the company already wrote the "a page is a list of smart blocks" engine and a safety net for blocks the screen doesn't recognize. What's missing is the Mac app code that draws those blocks, and teaching a few more analysts to output that block shape. v1.5.0 is those two things plus the layer that lets you rearrange them.

Build posture · decided with James

Gutenberg-informed native. Bank the WordPress work; don't rebuild it.

Bank WP, don't revert

The WP-primary work (the ~89 blocks + their per-block render.php, the get_entity_intelligence envelope) is preserved intact for the future where DailyOS is a headless runtime powering a local WordPress install. W0 parks it cleanly — nothing deleted, nothing extended. (Note: there is no built unified GutenbergBlockRenderer — it's per-block render.php today; the unified renderer is ADR-0130 §4's planned WP binding.)

Informed, not forked

Mirror Gutenberg's model + UX patterns — block.json-style metadata, edit-vs-render separation, RichText inline editing, block-toolbar / inserter UX — built native on our design system + dnd-kit. Do NOT fork @wordpress/* packages; that drags WP's whole paradigm in and fights the canonical design system.

~80% portable, by convention

Keep the Tauri block contract aligned to ADR-0130 §4's planned WP binding + the existing per-block WP render.php shape. When we return to WP, it's alignment, not a rebuild. The substrate is already block-shaped, so this is natural.

Inline edit is the anchor

The app already has live text edit (EditableText) on some surfaces; WP doesn't yet. Design our block inline-editing now, modeled on Gutenberg RichText — so it's the pattern we port to WP later. We're ahead, in a WP-shaped way.

Cross-wave decisions

Architecture that holds across the version.

Consume the substrate; don't re-ADR it

No new chapter-registry ADR. The block model, BlockType taxonomy, and §3.1 fallback exist. The only ADR work: flip ADR-0130 + ADR-0122 from Proposed → Accepted, and one small ADR for the layout overlay (the surface-side presentation layer).

React renderer = the ReactBlockRenderer

v1.5.0's "chapter system" is ADR-0130 §4's ReactBlockRenderer — a block-type → React component map + component library, consuming ProjectedComposition via the existing CompositionRenderOrchestrator.

Layout overlay is the net-new piece

Per-type "which blocks · order · variant" is a presentation layer over the AI-authored Composition (extends ADR-0130 §6.4). It never edits the Composition or the claims. The version's headline.

New designs, not old templates

Don't build the renderer into the project/actions/people/briefing/meeting templates we're replacing — that's throwaway work. Each surface is a vertical slice (its Composition producer + its new variant-D design), done one at a time: Account first (its producer exists), then forward. v1.5.0 owns only these producers, not the 28-ability sweep.

No tabs — Sections instead

Composition already has a Section primitive. Drop the hard Health/Context/Work tabs in favor of composed sections; the layout overlay is flat (per type). Design check (W1): confirm the Account content volume reads well as one composed scroll — Account is where we prove it.

3 types now; agnosticism is north-star

Account/Project/Person this version, keyed to the existing EntityType enum (ADR-0045). User-defined types + presets-dissolve are v1.6+. Presets (ADR-0079/0127) stay orthogonal — interpretation, not layout.

dnd-kit; own the format

Pin @dnd-kit/core@6.3.1 + @dnd-kit/sortable@10.0.0 (the React-18 line — stable, not stale) for reorder in edit mode only. Layout config is ours. DOS-829 reparent shares the dep.

The runtime is the engine — one substrate per loop stage

Decided with James 2026-06-10. The intelligence loop is five stages: signal in → claim created/corroborated/conflicted → producer enriches claims into content → surface displays → user feedback as new signal. The abilities runtime owns stage 3 (claims → content), exclusively — legacy "enrichment" fused stages 2+3 in one PTY call and must split: signal→claim extraction stays substrate machinery; claims→content synthesis happens only through producers, and legacy entity_intelligence snapshot writes retire. The WC wave executes this consolidation (DOS-855/856/860/861/862) and gates W4/W5. Two standing consequences for every wave: (1) trigger-side wiring is in scope — a wave that ships a Composition producer also rewires its scheduled trigger through WorkerAbilityBridge and deletes the capability's legacy PTY path (see W4 AC); (2) new work must name which loop stage it lives in at L0 — work that can't is probably duplicating a stage. Findings inventory: .docs/plans/v1.4.x-abilities-reconciliation-audit.md.

Edit & customize mode · how it looks and works

In-context, Gutenberg-informed, native.

Primary entry is on-page (your choice): a "Customize this page" affordance opens an edit mode over the surface you're looking at. Built from canonical primitives + a few Gutenberg-shaped micro-patterns — no WP fork.

The edit-mode surface

  • Enter/exit edit mode on the page itself (in-context primary); a per-type panel in Settings → Surfaces is the secondary home (shared with lifecycle stages, DOS-827).
  • Block toolbar / inserter — Gutenberg-informed: each block gets a lightweight toolbar (move, hide, variant) on hover/focus; an inserter re-adds hidden blocks. Native components, our design system.
  • Reorder via dnd-kit sortable, with the accessible keyboard contract: Space to grab, arrows to move, Space/Enter to drop, Escape to cancel.
  • Toggle = canonical Switch; variant = canonical Segmented with a one-line description per option. Locked/core blocks (masthead, lead) show a disabled control + lock glyph + aria-description.
  • Inline edit — Gutenberg RichText-shaped, extending the app's existing EditableText; edits route to claim feedback (ADR-0130 edit_routes), not free-text overwrites.

Behaviour (the states the design review flagged)

  • Live update — changes apply to the open surface immediately (reactive layout-overlay store), not next-navigation-only.
  • Auto-save per type — applies to every entity of that type, persists across restart. Reset to default (confirm step) restores the shipped variant-D layout.
  • Visibility precedence — four inputs resolved in order: eligibility (structural, e.g. parent-only) → data-present → item-suppression (suppression_tombstones, independent) → user toggle. "Off" is your choice and sticks, but a block still hides when it has no data or doesn't apply.
  • Empty surface — hide everything non-core and the page renders core blocks + a quiet "You've hidden most sections — Reset to default" link.
  • Recovery — Reset is the recovery path for W2; per-action undo (Cmd-Z) is out of scope, and the panel makes the auto-save legible.

In plain terms — on the Account page you hit "Customize," each section grows a little toolbar, you drag one up, hide Files, switch a section to its compact look, fix a label inline — and it saves itself for every Account. Keyboard works. "Reset" puts it back. It feels like editing a page in WordPress, but it's our own code.

WC — Runtime consolidation · one substrate per loop stage · NEW 2026-06-10 · gates W4/W5

The v1.4.x reconciliation audit (.docs/plans/v1.4.x-abilities-reconciliation-audit.md) found the intelligence loop — signal in → claim → producer → surface → feedback — is sound, but most stages carry 2–3 competing implementations: 16 context builders, 12 feedback-adjacent systems, dual producers per capability, and a worker bridge with zero callers. Every surface wave so far has tripped on this substrate (WR exists because W1/W3 did — provenance gaps, contract desyncs, raw-render fallbacks are all symptoms of the same dual-path drift). WC pays that down once, proactively, so W4 — the biggest surface wave and the release gate — doesn't become the next WR. Linear: DOS-855, DOS-856, DOS-860, DOS-861, DOS-862 in the v1.5.0 project.

  • C0 — Enrichment split (DOS-860). Legacy enrichment fuses loop stages 2+3 in one PTY call: it extracts claims AND writes user-facing entity_intelligence snapshots. Split it: signal→claim extraction stays intel-queue substrate; claims→content synthesis happens only through producers; snapshot writes retire as surfaces move to Compositions. This is the load-bearing simplification — producers read claims, nothing else.
  • C1 — DISSOLVED at WC L0 (2026-06-10). Verification showed detail-surface compositions are on-demand by design (orchestrator + cache; commit_composition persistence) — there is no scheduled refresh to rewire and building one would be machinery for its own sake. WorkerAbilityBridge first wiring ships in W4 with the briefing/prep producers (DOS-855 moved to W4). Risk-briefing recast is reports-track, way future — not WC, not W4.
  • C2 — Feedback unification (DOS-856). UI corrections write canonical typed claim_feedback (today: zero UI writers; thumbs write legacy entity_feedback_events that trust never reads); implement or amend the applied_at consumption contract. The W2 edit_routes path and WR R4 chip already point here — this closes the rest.
  • C3 — One context builder per concept (DOS-861). Collapse the duplicated account-context fetches into shared gather helpers; close the prep blind spots (email signals, stakeholders); document or align the 30/90-day windows. W4's briefing/meeting producers consume the consolidated builder — not a 17th one.
  • C4 — Signal-bus hygiene (DOS-862). Orphaned signals (ClaimTrustChanged, meeting_prep_status_changed) get consumers or die; google.rs stops bypassing the bus; envelope binding validated by one shared service function on both surfaces.

In plain terms — before building the two biggest pages, fix the plumbing so there's one way to do each thing: one place corrections go, one way pages get their data. We kept getting tripped by "which of the three paths is live?" — after WC there's one answer. Briefing and meetings keep using the old pipeline until W4 replaces them; that's deliberate and W4 deletes it.

Proof — a UI correction lands in claim_feedback and moves trust; enrichment writes claims only (reader-gated snapshot retirement); prep/intelligence read the same context helpers; no signal emits without a consumer or audit-only classification; ADR-0123 amended to verified event-sourced semantics. Deferred-but-tracked (post-WC, not W4 blockers): DOS-857 source reliability, DOS-858 recommendations feedback, DOS-859 dismissal consolidation.
