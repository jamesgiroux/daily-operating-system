DailyOS - Intelligence Loop - Remediation Plan

Make refreshes produce better intelligence.

Glean and local generation remain separate adapters, but prompt quality, parsing, claims, provenance, trust, and the visible refresh outcome converge before persistence.

The visible symptom was a user-initiated refresh showing partial Glean results: 2 of 6 dimensions completed and 4 failed. The root issue is broader than one connector warning. Remote and local generation can still diverge in prompt format, parser coverage, source attribution, claim production, and degraded-state reporting. This plan fixes the active failures first, then raises the quality bar for the generated output itself. A clean parser is not enough if the prompt produces vague, stale, generic, or hallucinated intelligence.

Created 2026-05-25 Status: L0 prep draft Scope: product-quality substrate slice Threat topology: remote-to-local plus local-to-local

Source and scope

Fix the degraded refresh without leaving the model split.

The plan targets prompt/provider contracts, output quality, parsing, normalization, claim materialization, trust recompute, invalidation, and the refresh surface. It does not redesign unrelated UI or create an evaluation platform.

  • Origination: User-initiated Glean refresh produced a partial-result warning. Audit logs show repeated failures in the same dimension families, which points to structural contract drift rather than random connector instability.
  • Primary goal: A user-triggered refresh produces visibly better, source-grounded intelligence from Glean or local generation, and explains partial state accurately when the source cannot support a complete answer.
  • Immediate stabilization: Stop known valid Glean output from being dropped, improve the prompts that caused malformed or low-value output, make failures observable, and make dimension applicability explicit by entity type and relationship.
  • Non-goal: Do not create a server-canonical architecture, a new HTML generation layer, or surface-specific schema readers that bypass the ability/claim runtime.
  • Non-goal: Do not hardcode customer names, domains, accounts, emails, or support examples in fixtures, diagnostics, docs, commits, or PR text.
  • Quality constraint: Do not add broad eval waves or convenience tests. Verification must be practical evidence that prompt quality and visible refresh quality did not regress.
  • K-in: ADR-0093, ADR-0100, ADR-0101, ADR-0102, ADR-0104, ADR-0106, ADR-0107, ADR-0112, ADR-0113, ADR-0115, ADR-0120, ADR-0125, the prompt-channel sensitivity sweep, and the claim-producer trust audit solution note.

User-facing outcome

The refresh must get smarter, not merely quieter.

The shipped outcome is a better refresh experience: stronger prompts, higher-quality generated intelligence, accurate partial-state messaging, and trust/source state on the fields users actually see.

Quality bar What must be true Practical proof
Prompt quality Dimension prompts use valid JSON examples, clear unknown/insufficient-evidence behavior, source requirements, injection-resistant data boundaries, and entity-specific instructions. Prompts must not ask for fields the source cannot reasonably support. Prompt review plus one sanitized replay of the degraded Glean failure class and one local/PTY equivalent. The output must be specific, source-grounded, and parseable.
Output quality Generated intelligence is concrete, current when the source can prove currency, calibrated when it cannot, and useful to the user. Generic summaries, unsupported commercial claims, fake precision, and hallucinated relationships fail the quality bar. A small before/after quality packet for the failing refresh shape: visible fields, source freshness, trust band, skipped/failed dimensions, and any user-facing warning text.
Refresh clarity The app distinguishes refreshed, reused, skipped, and failed dimensions. Skipped non-applicable dimensions do not count as failures, and applicable failures do not disappear behind successful partial output. One event-contract check and one rendered notification/surface check for applicable total, skipped dimensions, and required failures.
Correction memory When a user corrects surfaced intelligence, the next refresh must not casually regenerate the same wrong claim from the same weak source. One correction/regeneration check for a surfaced claim. This is a product-quality check, not a broad feedback-eval suite.

Diagnosis

The warning is correct; the error contract is not.

The current degraded event tells the user that Glean returned partial results, but it does not preserve enough structured detail for the system to know whether the failure was a connector timeout, invalid prompt schema, parser mismatch, or non-applicable dimension.

Finding Evidence Plan consequence
Prompt output can be valid but discarded dimension_prompts.rs asks for productClassification and gongCallSummaries, while prompts.rs currently maps those fields to empty or None. S0 adds parser coverage, prompt-quality review, and parse-through regressions before broader refactor work.
Source attribution is requested but not preserved Dimension prompts require itemSource; intermediate parser structs omit it for core risks, wins, stakeholder, and value items. S0 makes source attribution a parser contract and S2 promotes surfaced attribution into claim provenance and source_asof.
Prompt examples are type unsafe Examples include pseudo-values such as "score": "0-100", invalid numeric ranges such as 0.7-0.9, and boolean fields described as strings. S0 moves ranges to prose and adds a schema-example parse test for every dimension.
Entity applicability is too broad All six dimensions are fanned out for each entity while some schemas are account-shaped and only partially gated by entity type. S0 freezes a dimension applicability matrix for account, project, person, partner, and internal relationships.
Provider and service boundaries are leaky Glean provider and Glean context gathering perform writes or side effects before the shared finalization path; queue reconciliation also uses producer-blind source refresh rules. S1 moves drift-producing writes behind service-owned materializers without broad provider cleanup.
Claims are produced, but not as a complete runtime contract Legacy projection commits some claim-shaped intelligence, but many fields lack provenance, source refs, trust recompute triggers, and consistent feedback loops. S2 audits surfaced generated output against the claim/trust lifecycle instead of adding isolated claim writes.
Provenance primitives exist but are underused The runtime has source taxonomy, field attribution, ownership checks, and unattributed-field rejection, while several producers still store {} or ad-hoc JSON in claim provenance. S2 requires validated provenance envelopes and source-entity evidence before surfaced generated facts become trusted runtime inputs.

Adapters stay accountable

Glean chat, PTY, OpenAI/Ollama, and replay providers return completions plus metadata for the refresh path. Writes that affect visible intelligence, future prompt context, or trust move through services.

Contracts live once

Dimension schema, entity applicability, prompt template metadata, parser expectations, and field attribution must be declared in one auditable registry.

Services materialize

Claims, projections, side effects, signals, health recompute, and trust invalidation happen through services/ with ServiceContext gates.

Target architecture

One provider-independent production path.

The target is not a new source hierarchy or provider-purity campaign. It is a narrower refresh contract: every source produces observations or completions, every completion normalizes into a typed intelligence result, and durable effects that change visible intelligence, future prompt context, or trust flow through services.

Stage Owner Contract Must not do
Gather context_provider/* plus service intake For the refresh path, return local context plus typed remote observations with source lineage and sensitivity class where those observations affect visible intelligence or future prompt context. Move unrelated gather-side writes solely to satisfy an architectural ideal.
Generate IntelligenceProvider adapters Return Completion, prompt fingerprint metadata, elapsed time, response size, provider kind, and sanitized failure classes. Persist surfaced products, snapshots, claims, or side effects outside service-owned refresh materialization.
Normalize intelligence parser/contract modules Parse to a typed NormalizedIntelligenceOutput with per-dimension status, field attribution, and entity applicability. Drop unknown but declared fields, erase source attribution, or swallow serde failures.
Compose services::intelligence_generation or equivalent Reconcile with existing state using the actual producer/source family, preserve user edits and tombstones, and produce claim/side-effect proposals. Use producer-blind pty_synthesis reconciliation for Glean output.
Materialize services::intelligence, services::claims, services::glean_finalization, services::enrichment_side_effects Commit surfaced claims, visible projections, source refs, validated provenance envelopes, signals, and invalidation jobs transactionally where needed. Let queue, provider, or context-provider code write visible intelligence directly.
Consume Abilities runtime and surfaces Read claim-backed, provenance-bearing, trust-band-aware outputs through abilities and service DTOs. Legacy schema/source-ref facts are compatibility inputs only until claim-backed reads replace them. Teach Tauri, MCP, WordPress, or HTML surfaces to bypass the runtime with bespoke schema reads for refreshed intelligence.

Slice shape

Three slices: quality first, substrate only where needed.

The plan should not spend multiple waves on eval infrastructure or abstract purity. Each slice has a user-facing quality outcome, and each substrate change must directly protect that outcome.

Slice Purpose Primary files Gate
S0 - Refresh and prompt quality Fix dropped fields, repair prompt instructions/examples, make dimension applicability explicit, and update partial-state diagnostics. dimension_prompts.rs, prompts.rs, io.rs, glean_provider.rs, intel_queue.rs, useNotifications.ts A replay of the degraded refresh class produces specific, source-grounded, parseable output and an accurate visible partial-state message.
S1 - Shared materialization for visible intelligence Centralize only the generation-derived writes that affect visible intelligence, future prompt context, or trust. Do not refactor provider purity beyond current drift-producing paths. services/intelligence.rs, glean_finalization.rs, enrichment_side_effects.rs, intel_queue.rs Glean and local output for the same normalized fields commit through the same service path or document an intentional source-specific exception.
S2 - Trust, feedback, and source lifecycle for surfaced fields Attach provenance/trust/correction behavior to fields that appear in user-visible intelligence or future prompt context. Leave non-surfaced caches out of scope unless they influence refresh quality. services/claims.rs, services/trust_recompute.rs, account_fact_claims.rs, abilities-runtime/src/abilities/provenance/*, bridge/surface redaction files where touched Visible claims show the right trust band, corrections affect the next refresh, and revoked/unavailable sources stop influencing surfaced intelligence.

Implementation units

Concrete units, with quality proof named up front.

S0 can land independently only if it proves the actual degraded-refresh class is fixed and the generated output is better. Later slices are scoped to visible intelligence, not broad substrate cleanup.

Intelligence Loop check

The five mandatory questions, answered before code starts.

This work touches new claim producers, source attribution, trust, invalidation, runtime consumption, and feedback. It is incomplete unless all five dimensions ship together.

Question Decision for this plan
Claim model Generated facts, assessments, risks, commitments, recommendations, stakeholder reads, product/commercial facts, and durable current-state statements become claims or claim reinforcement when they affect future context or user trust. Pure transient diagnostics remain run metadata.
Provenance and trust All normalized items carry source family, downstream Glean lineage where known, source_asof or observed timestamp, field attribution, prompt fingerprint, actor, sensitivity, and trust recompute trigger.
Signals and invalidation Claim commits, trust-band changes, source revocation, feedback, degraded materialization, and ability-output changes emit service-owned signals. Dropped or failed invalidation is a visible stale/degraded marker, never silent.
Runtime and surfaces build_intelligence_context(), gather_account_context(), get_entity_intelligence, meeting prep, Tauri, MCP, and HTML/composition surfaces consume the same claim-backed/service DTOs. Legacy schema/source-ref facts are compatibility inputs until claim-backed reads replace them. Surfaces do not parse provider output.
Feedback loop User corrections, dismissals, wrong-source feedback, contradiction resolution, and claim receipt actions update claim lifecycle/trust inputs and source reliability. A corrected claim changes future prompt context through the central claim readers.

Claim producer contract

Generated facts need claim-grade receipts.

The implementation must use the existing claim and provenance substrate instead of inventing a Glean-specific receipt path. This is the minimum contract for any surfaced generated item that can influence future context or user trust.

Requirement Implementation rule Acceptance evidence
Validated provenance envelope Build provenance with runtime primitives and reject attributed output that cannot identify its source family, field path, and timing when knowable. No new surfaced generated claim stores {}, raw SourceAttribution, or bespoke source JSON in provenance_json.
Claim proposal helper Create a service-owned helper that maps normalized output into ClaimProposal values with actor, data source, sensitivity, lifecycle, temporal scope, source ref, and source-as-of. Surfaced account facts, entity projections, and Glean-derived facts enter commit_claim through the same helper.
Reinforcement recompute Every commit, reinforcement, contradiction, withdrawal, correction, and source-reliability update must enqueue or coalesce trust recompute. Tests fail if a same-claim reinforcement changes evidence without a recompute job.
Glean source ownership Bridge GleanAssessment and opaque downstream source IDs to explicit source/entity links. Prefer indexed SourceAttribution entries over SourceRef::Direct. Ownership validation can prove that a generated claim is supported by a linked source or marks the claim as needing verification.
Receipt privacy Tauri receives local provenance summaries; MCP receives redacted claim/source identifiers and stripped timing where policy requires it. Receipt checks cover Tauri and MCP redaction only where this slice changes those outputs.

Verification

Practical proof beats broad evals.

The quality bar is real refresh behavior through the Intelligence Loop. Passing type checks is necessary, but the acceptance gate is prompt quality, output quality, and honest degraded rendering for the known failure class.

Review protocol

This is Amendment 3 territory.

The plan touches trust boundaries, privacy, source lifecycle, filesystem/cache writes, claims, provenance, ability runtime, and external provider behavior. L0 should treat this as a product-quality slice with substrate risk, not a small connector patch or a broad platform rewrite.
