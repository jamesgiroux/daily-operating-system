# v1.5.0 W0 Substrate Genericity Audit

**Scope:** DOS-836. Audit `get_entity_intelligence`, `dailyos/account-overview`, and the composition render orchestrator before the Tauri renderer consumes the ADR-0130 substrate.

## Verdict

The composition substrate is surface-generic enough for W1 to consume. The active contract is an ability-produced `Composition` projected into `ProjectedComposition`; it does not require WordPress blocks, Gutenberg metadata, PHP render functions, or WordPress storage.

Known non-generic work remains in producer routing, not in the block model:

- `resolve_producer_ability_name()` and `extract_account_id_from_composition_id()` are account-overview hardcoded and must become entity-type keyed in W1/forward surfaces.
- `dailyos/account-overview` is intentionally account-only today; W1 uses it as the reference vertical before Project/Person producers generalize the pattern.
- `CompositionRenderOrchestrator` comments still name the historical WordPress surface, but the runtime path already supports the first-party `/v1/local/project-composition` route via `Actor::User`.

## Evidence

### `get_entity_intelligence` envelope

- Input is entity-typed (`Account`, `Project`, `Person`, `Meeting`) rather than WordPress-block typed.
- Sections are substrate concepts: facts, health, metadata proposals, open loops, relationships, touchpoints, threads, and record.
- Provenance is carried by source references and envelope-level provenance, not copied into surface-specific fields.
- Allowed actors include `User`, `Agent`, `System`, `SurfaceClient`, and `McpClient`; rendering policy derives from the invocation context.
- No `block.json`, render PHP, Gutenberg attribute, or WordPress option shape is part of the DTO.

### `dailyos/account-overview` producer

- Produces `AbilityOutput<Composition>` and commits through the composition service context.
- Uses ADR-0130 primitives: `Composition`, `Section`, `Block`, `BlockType`, `ClaimRef`, `FieldBinding`, `ProvenanceRef`, `Salience`, and `RenderHints`.
- Its account-only subject and default composition id are intentional current scope: `dailyos/account-overview:account:{account_id}`.
- The producer does not call WordPress code or require active WP blocks.

### Composition render orchestrator

- Projects ability output through `project_composition_for_surface()` and caches `ProjectedComposition` by composition id, version, and actor scope identity.
- The local loopback route uses `Actor::User` and the orchestrator has an explicit `Actor::User` cache key branch (`local_first_party`).
- The SurfaceClient route remains available for future WP/headless surface work, but W1 Tauri work should consume the local first-party path or a Tauri command chosen at W1 L0.

## W1 Follow-Up

W1 must replace the account-prefix resolver/parser with an entity-type keyed producer registry before Project/Person/forward surfaces rely on it. That follow-up belongs with the W1 transport/producer decision, not W0 banking.
