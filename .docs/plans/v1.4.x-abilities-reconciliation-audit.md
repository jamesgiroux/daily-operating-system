# v1.4.x Abilities-Era Reconciliation Audit

**Date:** 2026-06-10
**Method:** 8-lane parallel audit (2 codex + 6 Claude agents), each lane producing a producer→consumer inventory with file:line evidence, findings classified DUPLICATE / ORPHAN / DIVERGENT / DEAD, and kill/keep/merge verdicts. Cross-lane contradictions adversarially verified against source.
**Lanes:** feedback systems · abilities-vs-legacy production paths · context assembly · signals/invalidation · surface parity (Tauri/MCP) · schedulers/queues · frontend↔backend wiring · DB table orphans.
**Status:** Findings inventory. Tickets not yet filed; priority/scope decisions pending review.

---

## 1. Structural diagnosis — three root causes

Almost every finding below is a symptom of one of these three. Fixing symptoms without these stays whack-a-mole.

### RC-1: The abilities runtime is half-plugged-in (`WorkerAbilityBridge` is an orphan)

`bridges/worker.rs:22-68` defines the worker bridge that was supposed to let scheduled jobs invoke abilities. **It has no non-test caller.** Consequence: abilities are LIVE only via manual/UI `invoke_ability` (`lib.rs:925` → `commands/abilities.rs:45-66`) and MCP v2 — while everything *scheduled* (Today workflow, intel queue, meeting prep queue, risk briefing) still runs legacy PTY/Glean paths. Every capability therefore has two live producers **by necessity**: the old one can't be deleted because the new one isn't reachable from the production loop.

ADR-0102 end-state (`.docs/decisions/0102-abilities-as-runtime-contract.md:448-452`) explicitly says direct capability commands get removed once `prepare_meeting`, `get_daily_readiness`, `get_entity_context`, `list_open_loops`, `detect_risk_shift` migrate behind abilities. That migration stalled at the bridge.

### RC-2: The canonical feedback substrate has no UI writer

ADR-0123 `claim_feedback` is written by MCP v2 (`tool_claim_feedback.rs`), surface-nonce path (`surface_runtime/mod.rs:2919`), and the recommendations ability (`services/recommendations/feedback.rs:27`) — **but no React surface calls `submit_claim_feedback_command`** (registered `lib.rs:936`, zero frontend invocations). The app's own thumbs/correction UI (`useIntelligenceFeedback.ts`, `useIntelligenceCorrection.ts`) writes the legacy `entity_feedback_events` path (`services/feedback.rs:309`), which `claim_feedback` readers (trust recompute, salience, surfacing) never see. The user's daily corrections — the me-shaped moat — bypass the trust substrate.

Compounding: `claim_feedback.applied_at` is never set anywhere in production (`services/claims.rs:7847` inserts NULL; `trust_recompute.rs:1108` reads without marking consumed). The ADR-0123 consumption contract is silently unimplemented.

### RC-3: Surfaces consume different truths

Same concept, different data per surface: meeting prep context sees no email signals and no synthesized stakeholders that intelligence enrichment sees; 30d/3-meeting vs 90d/20-meeting history windows; MCP v1 `get_briefing` reads stale workspace JSON files while Tauri reads live services; MeetingDetailPage uses legacy `get_meeting_intelligence` while every other surface uses `invoke_ability("get_entity_intelligence")`. Trust-as-product requires no drift between surfaces; today drift is structural.

## 3. Priority structure

**P0 — product-truth bugs (user corrections don't reach trust; surfaces disagree):**
1. Wire UI feedback to `claim_feedback` (O2 + D4 + D9). Single highest-leverage fix; everything in the trust loop downstream of it is currently starved of UI signal.
2. Decide RC-1: is the abilities runtime the production engine? If yes → version-scale cutover plan (wire `WorkerAbilityBridge`, D1/D2/D3 merges, persistence parity, delete legacy PTY paths per ADR-0102 end-state). If not yet → freeze + document legacy as engine, stop building parallel ability producers.
3. `applied_at` contract (V7) — implement or amend ADR-0123.

**P1 — consolidation (drift closure):** D5, D6, D7, V1, V2, V3, V5, V6, X1.

**P2 — cleanup (Codebase Maintenance project):** O3–O8, X2–X4, D8, D10, V4, V8, O9, O10 routing decision.

## 4. Why this happened and how to stop reaccumulation

Per-issue L0/L2 reviews are diff-scoped: each new path looked correct in isolation, and nothing in the ladder ever asks "what does this supersede, and where's the kill ticket?" Proposed gates:

1. **Supersession rule (L0):** any plan introducing a replacement for an existing capability must name the superseded path and include the legacy-deletion ticket in its AC. "Ships alongside" without a cutover plan is a BLOCKED finding.
2. **Reachability proof (L1):** a new ability/producer/signal/table ships with at least one production caller/consumer traced in the proof bundle — same spirit as "the wiring IS the work" (CLAUDE.md DoD), enforced at proof-bundle level. An emit with no listener and a bridge with no caller are L1 failures, not future work.
3. **Recurring reconciliation sweep (L3/L5):** re-run this 8-lane audit per minor version close (it's cheap — ~2h wall clock, mostly parallel) and diff against this document. New orphans/duplicates = retro findings.
