DailyOS - v1.4.5 - Parallel Wave Plan

Workspace files become first-class source memory.

Local files, AI work product, inbox residue, and MCP-placed documents all feed the claim/provenance graph through one service-owned pipeline instead of living as manual side channels.

Workspace memory today is split across inbox processing, watchers, Drive import, attachments, content indexing, embeddings, and MCP/search paths. v1.4.5 collapses those into a single staged ingestion pipeline with durable source identity, lifecycle states, entity links, ingestion run history, and provenance-aware claim proposals. The proof surfaces are a Gutenberg source-management block, a sanitized markdown preview side rail, and a frozen headless contract that v1.4.7 MCP tools can build against without amendment.

Source and scope

Workspace memory becomes a single ingestion service with provenance.

v1.4.5 is the substrate that makes files trustworthy as source material. It is not the UI redesign and it is not the MCP tool expansion - both have downstream waves.

  • Problem: workspace files flow through inbox, content index, embeddings, Drive, watcher, and MCP paths without a single durable source identity, lifecycle, hash, provenance, source type, sensitivity, or trust posture.
  • First proof surface: the Gutenberg source-management block (DOS-472) plus the sanitized markdown preview (DOS-473) - both consume the new substrate via the v1.4.2 SurfaceClient bridge.
  • Headless proof: the frozen workspace_placement::place_document ability contract (DOS-474) becomes the v1.4.7 MCP write surface for AI-placed documents.
  • Upstream dependency: v1.4.2 W4 surface-bridge block scaffolding pattern + v1.4.2 W6 audit attribution helper must be confirmed merged before W4 lanes start.
  • Non-goal: no Tauri React surfaces for source management. No new trust UI primitives. No new claim_kind variants without an L0 amendment.
  • Threat topology: mixed - markdown rendering, MCP write payloads, and attachment file paths are untrusted input boundaries; local file ingestion is trusted-source but lifecycle-controlled.
  • K-in: ADR-0107 (DataSource taxonomy), ADR-0108 (sensitivity rendering), ADR-0125 (envelope-actor binding), v1.4.1 freshness decay table, existing CLAIM_TYPE_REGISTRY, SourceAttribution primitive.

Operating principles

One service, typed proposals, validated input.

All mutations through services::workspace_ingestion

No direct DB writes from watcher handlers, processor pipeline, Drive poller, attachment paths, or MCP. The lifecycle, registry, links, and ingestion run tables have exactly one writer. CI lint script (check_workspace_mutation_allowlist.sh) enforces.

File-derived facts are claim proposals, not direct claims

Extraction never inserts into intelligence_claims directly. Every extracted fact goes through services::claims::commit_claim with mandatory provenance: source_asof, data_source, source_attribution, separate ingestion_run_id. content_index and embeddings remain derived caches.

Untrusted input passes through validation before service entry

Markdown content, MCP write payloads, attachment file paths - none reach commit_claim without sanitization. The markdown sanitizer is allowlist-based, not blocklist-patched. The MCP placement ability uses server-derived source_asof, not caller-provided.

Wave shape

5 implementation waves; W2 and W3 internally serialized; W4 parallel; W5 sequenced.

W0 freezes the boundary. W1 builds the contract and registry. W2 builds the staged pipeline. W3 fills it with real extraction, signals, and a graph projection. W4 ships the source surfaces and the headless contract. W5 backfills and validates the release.

W4 - Source UX & Headless Contract

DOS-472 / W4-A - dailyos/source-management Gutenberg block: entity-scoped source list (Drive files, inbox items, entity documents), lifecycle states, ingestion run history, trust-band distribution of derived claims. User actions: re-ingest, quarantine (calls pipeline::quarantine_source), re-link (calls link::override_link with SignalEmitter).

DOS-473 / W4-B - dailyos/markdown-preview block + sanitizer: allowlist-based, not blocklist. Allowed tags only (paragraph, heading, list, code, blockquote, link, image, table); all style attributes dropped; URI schemes restricted (http/https/mailto for href; dailyos-asset:// only for img src); HTML comments dropped; no CSS at all. Negative fixture suite covers script injection, event handlers, dangerous schemes, SVG/MathML/foreignObject escape, conditional comments, remote assets, CSS injection. New Rust ability markdown_preview with mcp_exposure: None.

DOS-474 / W4-C - workspace_placement::place_document ability: frozen contract. Synchronous + dry-run shapes. Server-derived source_asof (caller's hint stored separately as audit-only). Transactional validation+write+enqueue. Per-actor rate limits (10/min, 200/hour). Idempotency triple (entity_id, content_sha256, client_dedup_key.unwrap_or_default()). Base64 wire encoding for binary content. Canonical category slug from WorkspaceCategoryRegistry or server auto-detect. Typed errors including RateLimited, IdempotencyConflict, CategoryNotAllowed. MCP write allowlist entry; /cso + /plan-devex-review at L0 + L2.

Surface Bridge dependency: v1.4.2 W4 block scaffolding + trust-band-render helper + v1.4.2 W6 audit attribution helper must be confirmed merged.

W5 - Backfill & Validation (release gate)

DOS-475 / W5-A - backfill: idempotent, resumable, dry-runnable. Cursor-based resume (backfill_state row updated atomically per file). Trust-band discipline - historical files with source_asof older than freshness decay threshold receive use_with_caution or needs_verification, never likely_current without confirmed re-ingestion. New binary workspace_backfill with --dry-run flag. Migration slot v268.

DOS-476 / W5-B - E2E validation: five axes. (1) Every claim has traceable source_attribution - zero attribution_gap entries. (2) Trust-band correctness on old vs recent files. (3) Signal propagation from WorkspaceFileIngested through EntityIntelligenceUpdated to meeting prep invalidation. (4) Context inclusion via build_intelligence_context() and gather_account_context(). (5) User correction round-trip via source-management block.

Pass: pnpm release-gate -- --mode hermetic exits zero; manual dogfood against ≥5 real entities' workspace files; validation report at .docs/plans/wave-W5-v146/validation-report.md.

Open questions

Resolve at W3 L0, not during implementation.

  • Claim kind coverage: W3-A maps file-derived facts to CLAIM_TYPE_REGISTRY. Unmapped facts become RawObservation. L0 must enumerate which structured entity-JSON fields cleanly map to existing kinds vs which need a registry amendment.
  • Signal payload shape: W3-B's typed payload structs exclude raw content, file path, claim text, prompt/output bodies, full content hash, and raw actor user IDs. Payloads use opaque file IDs, run IDs, entity targets, controlled reason codes, and actor classes.
  • Graph projection sensitivity: W3-C redacts file paths always and entity names without scope. L0 must freeze the exact field-level scope matrix (file_id never redacted, entity_name behind read.entity_names, claim text never returned via projection).
  • Backfill trust band table: W5-A must follow the v1.4.1 freshness decay table per DataSource variant. L0 should grep the active table and pin the exact thresholds for each WorkspaceFileKind.
  • Auth overhaul interaction: the local-to-local auth strip (DOS-758-class) may affect the MCP write path for DOS-474. L0 should confirm whether write.workspace_place_document scope still composes against the post-overhaul actor materialization.
