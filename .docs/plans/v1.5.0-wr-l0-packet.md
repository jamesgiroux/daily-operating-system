## §1 — Why WR exists

The substrate is real and works; the version's *promise* is not met on any surface and the producer contract is unguarded.

**The design-quality gap.** The wave plan defines W1's proof as the new design *rendered* — "matches the variant-D design (not the old page); one-composed-scroll validated." What shipped renders the correct claim payload through a generic, unstyled component library (`BlockComponents.tsx` → `pageStyles.composition*`). The editorial design system (`EntityHeroBase.module.css`: 76px serif, the vitals strip, the chapter rhythm) exists and is copy-paste-ready (`.docs/design/reference/`), but the blocks don't use it. W3 forward surfaces are worse — they render composition "while preserving existing controls," i.e. hybrid, not variant-D.

**The substrate gaps (found 2026-06-08).** Doing the Account pass surfaced three load-bearing defects, none surface-specific:

1. **Producer contract is unguarded.** `fallback_projection` rejects a producer output whose `FieldBinding.field_path` does not resolve in the payload (`InvalidProducerOutput { reason: BindingTargetsUnknownField }`), which the orchestrator surfaces to the UI as `producer_unavailable`. A trivial payload↔binding desync introduced during the Account pass passed `cargo test` (fixtures didn't exercise the shape) and only failed at runtime — blanking the whole page. There is no CI parity check between a producer's emitted payload and its declared bindings over realistic output.
2. **Field provenance is dropped by the file-sync.** `upsert_account` (`db/accounts.rs:12`) persists `arr/lifecycle/contract_end/nps` from each account's `dashboard.json` but never writes the `*_source` provenance columns; those are only set by separate edit/lifecycle paths. `push_account_vital_field` (`context.rs:2592`) correctly drops any vital without a provenance source, so **every headline vital renders empty** despite the values existing. The sync already knows the origin (it is reading `dashboard.json`) — it discards it.
3. **Producers emit raw, unformatted values.** Vitals carry `value: snapshot_value_text(...)` (e.g. `"185400"`, `"2026-11-24"`) with no display formatting and no type hint, forcing each surface to re-format (drift) or render raw. Decided with James: formatting belongs in the producer (separation of logic from display; identical rendering across Tauri/WP/MCP), emitting both a typed `value` and a formatted `display_value` so MCP/agents keep computability.

Ad-hoc patching of (1)–(3) during the session broke the producer (`producer_unavailable`); that draft is stashed (`stash@{0}`, "WR ad-hoc … draft"). WR redoes the work properly, under L0/L1 discipline, with a gate so it can't silently regress.

## §2 — K-in citations and constraints

- **ADR-0130 Surface-Independent Composition Contract:** abilities return `AbilityOutput<Composition>`; renderers project blocks and never author composition; field bindings (`Source`/`FeedbackTarget`/`ComputedFrom`/`DisplayOnly`) carry `claim_refs`; inline edits route through `edit_routes` to claim feedback, not free-text overwrites; `feedback_allowed` is true only for `BindingRole::FeedbackTarget` (`fallback_projection.rs:775`). Provenance-bearing vitals are required by the contract — rendering a value without a source is a contract miss, which is why R1 is substrate, not cosmetic.
- **ADR-0129 Composable Surfaces (WP banked):** surface parity — Tauri, WordPress, and MCP render the same producer output. Producer-side formatting (R2) is the parity-preserving choice; per-surface formatting would drift. (Memory: visual parity is never path-α for surface work.)
- **ADR-0083 Product vocabulary:** all user-facing strings (vital source labels, `kind` display, chip text) use product vocabulary.
- **ADR-0107 Source taxonomy (2026-05-19 amendment):** file-sourced fields use the **typed** `DataSource::WorkspaceFile { kind: EntityDoc }` (the account `dashboard.json` is an `EntityDoc`); `DataSource::Other(...)` is explicitly *not* the authoring path. Decides R1's source classification — see Decision B.
- **ADR-0105 Provenance as first-class output (2026-04-24 amendment):** provenance metadata is lifted at the write path that already reads the source (not stamped `now`), and existing rows are backfilled idempotently. This is the canonical precedent for R1's shape; `source_asof` comes from the dashboard file timestamp.
- **ADR-0108 Provenance rendering:** surface source labels render through `DataSource::display_name()` via the single render entry point — R1/R2 reuse it rather than inventing a label string.
- **ADR-0123 Typed claim feedback semantics:** edits route as typed corrections through the closed `FeedbackAction`/`ClaimFeedback` substrate; lifecycle/identity fields are structured-only (no free-text). Governs R4 — the chip routes an `AccountFieldCorrection`-class typed correction.
- **ADR-0136 Layout overlay as surface-side preference:** the W2 overlay applies after projection, never mutates composition/trust; renderer tests must prove the unknown-block fallback privacy boundary still holds in edit mode. Governs R3.
- **ADR-0073 / ADR-0077 Editorial design language / magazine layout:** the variant-D visual system (Newsreader 76px hero, metrics/logistics strip) is documented design substrate — R3 is translation of an existing system, James-collaborative on the delta.
- **W1 L0 packet + proof bundle:** the accepted renderer path is `invoke("get_projected_composition")` → `CompositionRenderOrchestrator` → ability output → fallback projection → `ReactBlockRenderer`; block components are pure renderers over projected payload; the W1 proof bar is variant-D fidelity, not raw payload.
- **W2 L0 packet:** the layout overlay / `useChapterLayout` edit mode is established and must not be reworked by WR (R3 renders inside it; it does not touch the overlay).
- **Design system (`.docs/design/reference/`):** canonical, copy-paste-ready tokens/primitives/patterns/surfaces. `EntityHeroBase.module.css`, `AccountHero.module.css`, `VitalsStrip.module.css` are the visual source for R3 (translation, not new design). `account-*-meridian.html` exports are *direction only*.
- **`docs/solutions/` + `.docs/decisions/`:** `ce-learnings-researcher` runs the authoritative K-in grep at L0; cite hits on composition, provenance, vitals, producer-output validation, and surface formatting. Reinvented substrate = BLOCKED.

No prior solution replaces these requirements; the relevant substrate is ADR-0130 + W1/W2/W3.

## §3 — Binding decisions

### Decision A — Producer↔projection parity becomes a CI-enforced invariant (R0)

The projection already validates binding/payload parity at runtime; WR adds the **build/test gate** that was missing. The gate covers **all four shipped Composition producers** — `dailyos/account-overview`, `dailyos/project-overview`, `dailyos/person-overview`, `dailyos/action-detail` — because the `producer_unavailable` class is substrate-wide, not Account-specific (this is the one part of WR that is *not* Account-only; it is test coverage, not a producer feature sweep, so it does not contradict the Account-first design scope). For each producer, a test takes its real-shaped output (representative fixtures incl. multi-item vitals, empty, degraded, fallback) and asserts: (a) every `FieldBinding.field_path` resolves to a present payload pointer; (b) the output projects without any `InvalidProducerOutput`. Runs in `cargo test`; it is the gate that would have caught the `display_value` desync. WR also root-causes and documents the `BindingTargetsUnknownField` class so the assertion names the failing pointer.

### Decision B — Field provenance is captured at the file-sync write path (R1)

The file-sync records the originating workspace file as the field-provenance source when it upserts file-sourced values. Five constraints, all from cycle-1 review:

1. **Typed source, not free-string (ADR-0107).** The source is `DataSource::WorkspaceFile { kind: EntityDoc }` (the account `dashboard.json`), rendered via `DataSource::display_name()` (ADR-0108). The earlier `Other("account dashboard")` option is **struck** — ADR-0107 forbids `Other` as an authoring path. `source_asof` is populated from the dashboard file timestamp (ADR-0105 population chain), not left null.
2. **No churn.** The write does **not** bump `accounts.updated_at` and does **not** call `write_account_json` — the sync direction is decided by file mtime vs `accounts.updated_at` (`accounts.rs:753`), so touching neither avoids a file↔DB loop. A dedicated function (not the existing `set_account_field_provenance`, which bumps `updated_at` at `db/accounts.rs:1433`) carries this.
3. **Clobber protection via priority + value-changed (BLOCKER from cycle 1).** `set_account_field_provenance` is an unconditional overwrite and the vitals columns have no priority gate, so a naive writer would downgrade `user_edit`/`lifecycle` provenance to file-origin on every sync. The write is gated: introduce a `workspace_file` source priority **below** `user_edit` and `lifecycle`, and stamp a field only when **the file-sync actually changed that field's value this pass** AND the existing source is empty or itself file-origin. The "file-sourced upsert site" is *not* the boundary — the per-field value-changed + priority check is. The write is gated to the value-changed merge branch, **not** the directory-rename branch (`accounts.rs:733`, which bumps `updated_at` by design and changes no vitals).
4. **Honest backfill.** Existing rows are backfilled `WHERE <field> IS NOT NULL AND <field>_source IS NULL` (idempotent + clobber-safe + no re-stamp). Because backfilled values are of *unknown* true origin (pre-provenance migration 075 left them NULL), the backfill uses a **distinct, lower-priority** honest label (e.g. `workspace_file:backfilled` / `unknown_pre_provenance`) so the first real sync/edit overwrites it — it does **not** reuse the forward-sync `WorkspaceFile{EntityDoc}` label, which would fabricate origin. No `updated_at` bump; runs once in the single-writer startup context.
5. **Multi-entity scope (resolved).** Accounts use the column-based path above. **People** route through `set_person_field_source` (`db/people.rs`), but its *priority machinery* exists only as an unknown-source reject — **the no-bump variant and the priority-downgrade clobber guard are new work** (it currently bumps `updated_at` and does not compare incoming vs existing priority), and the `workspace_file`/`workspace_file:backfilled` labels must be **registered in `source_priority()` below `user_edit`/`lifecycle`** or the call is rejected. People get the same clobber gate the account path gets — not a free reuse. **Projects have no field-provenance substrate at all** and building one needs a migration this no-migration wave excludes — **projects are out of scope for R1; file a follow ticket.** "Fix where shared" is replaced by this explicit per-entity scoping.

### Decision C — Producers emit `value` + `display_value` + `kind` (R2)

Each rendered scalar vital carries the typed `value` (preserved for MCP/agent computation), a producer-formatted `display_value` (currency `$185,400`, date `Nov 24, 2026`), and a `kind` hint (`currency`/`date`/`number`/`text`). Surfaces render `display_value` (fallback `value`). **Time-relative rendering** (countdowns, "N days") stays surface-side — the composition is cached and would freeze a relative value — and is driven by the **existing `kind` hint** (a surface computes a countdown from a `kind: "date"` vital's typed `value`); WR does **not** add a fourth `relative_display_value` field. New payload fields carry display-only bindings (the Decision A parity gate enforces this). Written across the shared producer formatting path; rendered/validated on Account.

### Decision D — Variant-D rendering reuses the design system; Account only (R3)

The block component library renders to variant-D quality by composing the curated CSS modules (`EntityHeroBase`/`AccountHero`/`VitalsStrip`), chrome-free where the chapter is full-bleed (no `BlockShell` card on the masthead). Inline edits route through `CompositionInlineEdit` → `edit_routes` (ADR-0130), never `saveAccountField`. R3 renders inside the existing W2 layout overlay; it does not modify `useChapterLayout`/dnd. **The visual design is James-collaborative** (reference-translation of the existing system as the floor; new design decisions made with James), so R3 lands chapter-by-chapter, hero-first, with review at each chapter — not a single big-bang render.

### Decision E — Editable type/lifecycle chip via typed account-field correction (R4) — resolved

The chip's backing field (account `lifecycle`/`type`, customer/partner/internal) is a **snapshot field, not a claim** (`account_overview.rs:1356` binds `/account/type` `display_only`; no claim backs it). A `FeedbackTarget` edit-route therefore **cannot** be emitted — it requires a field-aware claim ref, and emitting one without it violates the ADR-0130 contract (cycle-1 finding, codex + scope-guardian).

**Resolution (decided with James 2026-06-08):** keep the chip editable, routing its edit as a **typed `AccountFieldCorrection`-class correction** through the existing claim-feedback substrate (ADR-0123) — the same path `IntelligenceCorrection`/`BlockFeedback` already use for snapshot fields — **not** a `FeedbackTarget` binding. Per ADR-0123 the lifecycle/identity field is **structured-only** (no free-text `NeedsNuance`); the chip emits a structured typed correction. **L1 verification gate:** confirm the correction propagates to the rendered value; if it cannot within WR, the chip falls back to read-only and the editable version moves to a follow ticket (no fabricated provenance, no half-built path).

### Decision F — WR is one wave PR with internal milestones

Per protocol, one PR per wave, grouped internally: R0 (gate) → R1 (provenance) → R2 (formatting) → R3 (Account variant-D, chapter-by-chapter) → R4 (claim chip). R0 lands first so the rest is built behind the gate. **No SQL migration** — WR uses existing columns and binding mechanics; if any sub-stream discovers a migration need, it reserves the next free slot per the wave plan before implementation.

## §5 — Intelligence Loop integration check

1. **Claim model:** R3 renders existing claim-backed blocks; R4 makes an identity field claim-backed-editable (or descopes if unbacked); no ad-hoc frontend-only intelligence fields. R1/R2 operate on snapshot-wrapped fields with sensitivity + provenance classification.
2. **Provenance + trust:** R1 closes the provenance gap so vitals carry source/`source_asof`/trust; R3 renders trust bands + provenance; R2 preserves the typed value for downstream trust/computation. Missing provenance still degrades visibly.
3. **Signals + invalidation:** R1's provenance write does not alter claim recompute; R2/R3/R4 do not change invalidation. R0 is test-only.
4. **Runtime + surfaces:** R2's `value`+`display_value`+`kind` is consumed identically by Tauri and MCP via the same projection (parity). No MCP/SurfaceClient fork.
5. **Feedback loop:** R4 routes chip edits to claim feedback via `edit_routes`; R3 inline edits route to claim feedback; no free-text overwrites.
