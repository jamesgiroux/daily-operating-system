## §1 — Why W1 exists

W0 confirmed that the durable substrate is not WordPress; it is the ADR-0130 Composition contract. W1 must prove that contract on the first real Tauri surface before later waves fan out.

The current routed Account Detail page is a React template with three mounted views (`Health`, `Context`, `Work`) and tab-state-derived chapter navigation. That is the old surface model. W1 replaces it with one substrate-authored composition: the Account producer decides sections and blocks; React renders known block types; unknown/custom blocks degrade through the existing safe projection path; the magazine shell derives navigation from the projected composition, not from hardcoded tab arrays.

The wave plan says W1 is Account only. The session handoff also says "Project/Person in W1" in one line, but the authoritative wave plan puts Project/Person/Actions in W3. W1 therefore does **not** ship Project or Person producers. It does remove account-only transport assumptions where that is needed for W3, but it keeps the only shipped producer path as `dailyos/account-overview`.

## §2 — Binding decisions

### Decision A — Composition→React transport uses Tauri `invoke()`, not browser fetch to loopback

React already uses `invoke()` for first-party data access. W1 will add a first-party Tauri command, tentatively `get_projected_composition`, that calls a shared service-owned composition projection function. The existing `/v1/local/project-composition` route remains as a smoke-tested loopback surface and reuses the same service function.

Reasons:

- It avoids teaching the React app local runtime port discovery, local HTTP fetch retries, and CORS-like failure modes.
- It keeps frontend access in the same command/invoke error model as the current Account page.
- It preserves W0's local-loopback route as shared substrate without making the Tauri renderer depend on an HTTP detour.
- It lets the route and command share cache/version/audit/projection semantics instead of creating two implementations.
- It avoids a parallel ability bypass. The command is only a bridge into the existing ability/orchestrator/provenance path; it must not read Account data directly and assemble a page-shaped response.

### Decision B — Projection must carry section outline

`ProjectedComposition` is currently a flat block list. That is not enough for W1 because the Account page navigation and one-scroll layout must be derived from the resolved composition's `Section`s. W1 will extend projection output with a safe section outline:

- section id
- optional label
- layout hint
- salience
- projected block indexes or ids in render order

This outline contains no raw unknown-block payload and does not bypass fallback projection. Existing flat `blocks` stay available for compatibility.

The projection surface must represent Tauri explicitly. `SurfaceKind::TauriApp` already exists in `fallback_projection.rs`; W1 must use `BridgeSurface::TauriApp` plus `SurfaceKind::TauriApp` for the command path. The existing helper currently hardcodes `SurfaceKind::SurfaceClient`, which maps to a different render policy and must not be reused silently for Tauri.

Projection cache entries are render-policy-specific. The cache key must include the `SurfaceKind`/render-policy identity and fallback-policy version so a `SurfaceClient` projection cannot be served to Tauri, or vice versa.

### Decision C — Account producer owns the Account page composition

The React page must not assemble the Account dossier from independent frontend queries and call that a composition. `dailyos/account-overview` will be extended to emit the Account variant-D section set from service-owned inputs:

- claim-backed intelligence already read through `read_entity_context_claims`
- a narrow account snapshot reader added to the abilities service context for identity/vitals/source refs needed by the masthead
- existing service-owned readers where already available and necessary for visible blocks

If a design section cannot be backed by service-owned data in W1, it renders as a visible empty/degraded block from the producer, not as a hidden frontend omission.

### Decision D — Account is the renderer proving ground, not a compatibility wrapper

`AccountDetailPage.tsx` will switch to a composition-first route:

- load projected composition by account id
- register magazine shell chapters from projected sections
- render `<BlockRenderer composition={projected} />`
- keep loading/error/empty shell states
- remove the three-view tab switcher from the routed Account surface

Existing Account components may be reused inside block renderers when their API matches the block payload. They are implementation components, not the page template authority.

### Decision E — Design reference is a W1 deliverable

The current canonical Account reference (`.docs/design/reference/surfaces/account.html`) mirrors the old template and imports legacy/editorial classes. W1 cannot claim design fidelity against that artifact. W1 therefore starts with an Account variant-D design gate: update the Account surface spec/reference and surface inventory to the composed-scroll variant **before** implementing the React renderer or producer mapping. If implementation discovers the content volume needs collapsible sections, the reference and source change together.

### §3.1b — Producer input architecture

W1 chooses one new ability-service read seam: `AccountCompositionSnapshotReadHandle`. It is not a second page model and not a frontend query fanout. It is a service-owned, typed input bundle for non-claim Account page facts the producer cannot get from `read_entity_context_claims`.

The handle returns `AccountCompositionSnapshot` with field wrappers for every non-claim value:

- `value`
- `sensitivity`
- `source_label` / `source_ref` when known
- `source_asof` when known
- `trust_band` or `trust_status` when known
- `provenance_kind`: `source_ref`, `manual_user`, `derived`, `system_config`, or `unavailable`

The only exception is explicitly non-sensitive identity/display data (`account_id`, display name, account type) which may be marked `non_sensitive_identity`. Any ARR, renewal, health, lifecycle, stakeholder, work, timeline, file, or report field must carry the wrapper or be omitted/degraded.

- No `AccountViewSwitcher`, hidden mounted tab containers, or `?view=health|context|work` dependency remains on the routed Account page.

- On desktop and mobile, the first viewport shows the masthead plus a visible hint of the next section.

- Critical and Important salience sections render expanded by default. Background salience sections may collapse by default only if their header is reachable by keyboard and screen reader, their summary states what is inside, and their expanded content remains in document order.
- Dense fixture threshold: if total rendered height exceeds 12 desktop viewports or 18 mobile viewports, W1 must either collapse Background sections by default or document why all expanded content remains scanable in the proof bundle.
- Collapse/expand controls, if added, are semantic `<button>` controls with visible focus state, `aria-expanded`, and no pointer-only interaction.
- Unknown fallback block shows the non-dismissible banner and no dropped payload/source/provenance values in visible text, DOM attributes, logs, or diagnostics.
- Provenance proof includes at least one block with resolved provenance, one missing-envelope/masked-field degraded state, and one claim-backed correction/feedback target visible in the rendered block.

## §4 — Intelligence Loop integration check

1. **Claim model:** W1 does not add new claim tables or claim types by default. It consumes existing active claims via `read_entity_context_claims`; any net-new Account fact needed in composition must first prove whether it belongs as a claim rather than display-only payload. Account snapshot fields are limited to explicitly non-sensitive identity/display data unless promoted into field-provenance-bearing composition inputs.
2. **Provenance + trust:** Blocks carry `ClaimRef`, `FieldBinding`, `ProvenanceRef`, trust band, and source freshness. React renders those fields; it does not compute trust or display raw provenance envelopes. Snapshot-derived fields either carry per-field provenance/trust/freshness or remain narrowly classified non-sensitive identity fields.
3. **Signals + invalidation:** Composition versions and cache keys remain substrate-owned. Producer output-change signal policy on `dailyos/account-overview` remains the refresh trigger; W1 tests cache miss/hit and version changes.
4. **Runtime + surfaces:** Tauri consumes through a first-party command; the existing local-loopback route remains functional; MCP/headless surfaces are not changed in W1.
5. **Feedback loop:** Blocks with feedback routes expose claim/field targets so corrections, dismissals, and corroborations continue to flow through existing claim feedback services. W1 does not add display-only intelligence that cannot be corrected.
