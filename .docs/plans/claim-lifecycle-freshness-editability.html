How claims live, go stale, and accept your edits.

The current position on three things the substrate does implicitly — assembled in one place, adapted as the product develops.

A "claim" is one recorded fact (a risk, a win, a commitment) with its sources and a trust band. Three questions follow it through its life, and the answers are scattered across the code and a few ADRs. This page assembles them: how a claim changes state as you act on it, how it ages, and when you can edit it inline. The mechanics here are real and shipped (ADR-0123 / 0125 / 0114 / 0130); the positions — the policy dials — are marked proposed and are James's to set. This is a living doc: it states today's position and is revised as the product develops.

Status: living · v0 draft Grounded in code: 2026-05-31 Implemented by: v1.5.0 W2 (edit) + W4 (freshness/trust)

1 · Lifecycle

A claim has four states, and your feedback moves it between them.

Every claim is in one of four states. It starts active. What you do to it — confirm, mark outdated, mark false — moves it, and adjusts how much the system trusts that source next time. (ADR-0123 defines the actions; the schema defines the states.)

created → ACTIVE ──confirm──────────────→ ACTIVE (more trusted)
                ──mark outdated────────→ DORMANT (can be replaced by a fresher claim)
                ──needs nuance / edit──→ SUPERSEDED  (your corrected version becomes the active one)
                ──mark false───────────→ WITHDRAWN (gone for good; a tombstone shadow blocks the exact claim resurfacing)
                ──wrong subject────────→ tombstoned for that entity (the fact may be right elsewhere)
You say…What happens to the claimEffect on trust
Confirm ("still true")Stays activeSource judged more reliable
Mark outdated ("was true, not now")Goes dormant; eligible to be replaced by a fresher claimFreshness downweighted
Edit inline ("partly right — here's the fix")Original superseded; your corrected version becomes activeSmall reinforce or contradiction depending on how much you changed
Mark false ("this is wrong")Withdrawn — permanent (a separate tombstone shadow blocks the exact claim from resurfacing; the state itself is withdrawn, not tombstoned)Source penalized
Wrong subject ("right fact, wrong account")Tombstoned for this entity onlySmall source penalty
Wrong source ("source doesn't say that")Stays active unless no qualified source remainsThat source downweighted for this claim type
Can't verifyStays active; queues a re-checkNo penalty
Not here / surface-inappropriateHidden on this surface only; state unchangedNo trust change

In plain terms — confirm makes it stickier; "outdated" lets a newer fact take its place; an inline edit swaps in your version; "false" buries it for good. The one rule worth remembering: marking false is permanent — new evidence won't resurrect that exact claim (a fresh, contradicting claim can still be made).

2 · Freshness

Each claim type has an age profile.

Claims don't expire on a hard clock; they decay in confidence as they age, and how fast depends on the claim type. A meeting-readiness note goes stale in days; who the champion is stays relevant for months. Decay is a real, computed factor in the trust band (ADR-0114); the per-type profiles are below (from the claim type registry, ADR-0125).

Age profileRough half-lifeClaim types
StaticNever decaysDismissals / tombstones (a "no" stays no)
SlowMonthsWins · value delivered · stakeholder role · entity identity · company context · account facts
MediumWeeksRisks · commitments · open loops · engagement · recommendations
FastDaysMeeting readiness · prep facts
Event-boundTied to an event/expiryMeeting topics · suggested outcomes · triage snoozes

In plain terms — the system shows fresher claims more prominently and lets confidence fade as things age — but it does not, today, hide a stale claim on its own. When a faded claim should gray out or drop off the page is a product position (see §4), and it's exactly what v1.5.0's trust/freshness rendering (W4) will make visible. Note: point-in-time facts ("Bob said X on 4/23") never decay — they're history, not state.

3 · Editability

A field is editable inline only when it's tied to a claim and the claim allows it.

In the new block model (ADR-0130), each field a block shows carries a binding that says whether it's display-only or editable. An inline edit isn't a free-text overwrite — it routes back as a correction to the underlying claim. Here's the rule.

Editable when…

The field is bound to a claim as a FeedbackTarget, the claim resolves to a real field, the claim type permits refinement, the sensitivity tier allows it on this surface, and the block isn't in the unknown-block fallback state.

Not editable when…

The field is display-only or computed, has no claim behind it, is too sensitive for the current surface, or sits on a block the surface couldn't fully recognize (capped to "needs verification"). Each refusal carries a reason, so the UI can explain why.

Free-form vs structured

Free-text fields accept a full rewrite (your text supersedes the claim). Structured fields — a role, a commitment, a renewal date, a health band — accept a correction (pick the right value / mark wrong) but not a free rewrite, because their shape is typed.

An edit is a correction

When you edit, the system records it as feedback: the original claim is superseded and your corrected version becomes the active one, with provenance noting you made the change. Nothing is silently overwritten.

In plain terms — if you can edit a thing on the page, it's because there's a real claim behind it and the system knows how to take your correction. Some things you can rewrite freely; some you can only set to the right option. Either way, your edit is a tracked correction, not an overwrite — which is what keeps the page trustworthy.

4 · Positions to set

The policy dials — proposed defaults, James to confirm.

These are the genuine product calls. Each has a recommended default so we can move; change any of them and the doc + the v1.5.0 AC follow.

Staleness → on screen

Proposed: at ~1 half-life, a claim de-emphasizes (smaller / trust band drops to "use with caution"); at ~2 half-lives it collapses under a "stale" fold rather than disappearing — nothing is silently hidden. Confirm the fade/hide behavior (W4 renders it).

Editing a low-confidence claim

Proposed: yes — editing IS the way to fix low-confidence claims, so allow edits at "use with caution"; block inline edit only on the unknown-block fallback state (needs-verification cap). Confirm.

Is "false" forever?

Proposed: keep tombstones permanent (a "no" stays no), but add a visible "undo" window right after the action so a misclick is recoverable. Confirm permanence + the undo window.

Who can edit

Proposed: you (the user) can edit any eligible field; agents propose, never silently edit. Single-user app today, so no per-user gates. Confirm.

One code tidy this implies: make "does this claim type allow free-form refinement?" an explicit flag on the claim type registry (it's currently implied across ADR prose + UI). Small, and it makes the editability rule enforceable in one place — a candidate W2 sub-task.

5 · Where this lands

A living position now; surfaced by v1.5.0.

This doc is the high-level position you asked for — held in one place, revised as the product develops. It's not a build wave on its own; it's the spec two v1.5.0 waves implement against:

  • W4 (freshness/trust rendering) implements §2 + the §4 staleness position — claims fade / fold by age, trust band shown per block.
  • W2 (inline-edit eligibility) implements §3 + the §4 editing positions — which fields show an edit affordance, and what a correction does.
  • Deeper lifecycle UX (a contradiction review queue, dismissals you can revisit) is v1.4.9 W4 / a later follow-on — out of scope for v1.5.0, noted so it isn't lost.

As the renderer makes these visible, expect this doc to gain a real claim-lifecycle diagram and per-type staleness numbers tuned against what actually feels right on screen. That's the "adapted as the product develops" part — this is v0.
