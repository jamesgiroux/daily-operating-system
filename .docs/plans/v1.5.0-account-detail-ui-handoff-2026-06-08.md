## The architecture (confirmed against the plan — do not relearn this the hard way)

v1.5.0 = **Composable Surfaces** (ADR-0130). A page is a list of **claim-backed blocks** the abilities-runtime producer authors (each block carries its sources + `trust_band`). The Mac app's net-new job is the **`ReactBlockRenderer` = a block-type → React component-library** that renders those blocks in the variant-D design, **and** inline edits route to **claim feedback** (`edit_routes`), never to DB field writes. Per-type "which blocks / order / variant" is a **layout overlay** (customize/reorder/hide, Gutenberg-informed) over the AI-authored Composition — it never edits the Composition or claims.

**The correct dataset is claims via the producer. The UI is the only thing that's wrong.**

### What NOT to do (this session's two wrong turns — don't repeat)
1. **Do NOT reuse the curated components as-is.** `AccountHero`, `AccountHealthSection`, etc. (`src/components/account/`) read the **old `get_account_detail` read model** (`useAccountDetail`) and edit via **`saveAccountField`** (DB writes). Both are the *wrong runtime* for v1.5.0. Reusing them feeds the page the non-claim-backed read model — the exact thing v1.5.0 replaces. (A prior attempt did this; it's reverted — commit `e76c9fe1` reverts `891a2659`.)
2. **Do NOT revert to the old page** (`AccountDetailEditorial.tsx`). It works but it's the old data path. Reverting = throwing away the claim-backed runtime = wasted work.

### What TO do (the pattern)
- Render the **claim block payload** (from `get_projected_composition`) through components styled to the **variant-D design**, **reusing the curated components' VISUAL design — the CSS modules and editorial structure** (e.g. `AccountHero.module.css`), not their data/edit logic.
- Inline edits → the block's **`edit_routes`** (claim feedback, ADR-0130), via the existing `CompositionInlineEdit`.
- When the variant-D design needs a field the producer doesn't emit, **extend the producer** (`account_overview.rs`) to emit it as a claim/attribute so it stays claim-backed + customizable. **James confirmed this** (e.g. the editable customer/partner/internal lifecycle chip should be producer-emitted, not pulled from the old read model).
- Keep the layout overlay / customize (`useChapterLayout`) — don't touch the DnD/customize code.
