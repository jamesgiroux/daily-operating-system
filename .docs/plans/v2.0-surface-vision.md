## The one-sentence answer

**The app is a library of living documents over the claim graph — one standing document per day, every other document composed on prompt or click — where a document is a saved query, not a saved artifact.**

Six primitives. Everything in the current 25-surface shell either becomes one of them or dies.

## The six primitives

### 1. The Claim (exists — the substrate)
Unchanged. The atom of memory + judgment: provenance, trust band, lifecycle, corrections. Research confirmation: the field's own state-of reports name staleness/salience/trust the unsolved problems, and **no shipping product does claim-level provenance + trust bands + freshness dating on personal data**. This is the moat; everything below renders it.

### 2. The Document (the new center)
A composed, sectioned, claim-backed view: typed blocks (ADR-0130 Composition — already built), inline citations per section, trust-as-opacity per block, **per-section freshness dating** ("from data as of…").

The load-bearing idea from the OSS research, **corrected by the L0 feasibility review**: a document is a parameterized query over the claim graph **plus a dated run record**. The substrate is *already* saved-query — `commit_composition` persists only a version counter + audit event, no content; the Composition JSON lives in a 60s cache and regenerates from claims (feasibility finding 1, verified at `migrations/v172`, `services/compositions.rs:244-373`). What the flagship features (diff-vs-last, briefing history, Library full-text) need and the substrate lacks is the **persisted run**: snapshot of the Composition or a claim-version pin set (`ClaimRef` already carries `claim_version`, so pin sets are schema-compatible). That is a named, separately priced **document-persistence substrate L0** in W0 — snapshot-vs-pin decided there. Regenerate = re-run the query (new dated run); edit = correct the claim (fixes every document that cites it). Corrections use the tracked-changes pattern (suggestion-node accept/reject → ADR-0138 writer); the correction-on-refresh state machine (what the user sees when a corrected document re-runs) is a required WD output before W1.

Lineage (K-in): this resolves ADR-0062's artifacts-vs-live-queries tension (saved-query side wins, with dated runs) and supersedes ADR-0030's daily-refresh model for the Day; document = a named, persisted, refreshable **Composition** (ADR-0130) — no new document IR. Document-view personalization stays in the layout overlay (ADR-0136); publishes leave via the pencil-and-pen boundary (ADR-0117).

Markdown's role (James's question): **structured Composition is the source of truth; markdown is the projection** — written to the workspace for the open-ecosystem promise (PHILOSOPHY: any AI can read your archive) and for Cowork to consume. We do not recalibrate markdown into HTML; we render Compositions natively and *export* markdown. This is also what the document-AI products converged on (typed schema validated and rendered; markdown as interchange).

### 3. The Library (new — files become visible)
The persistent, named, searchable home for every document: generated briefings, meeting documents, transcripts, reports, captures. Research: Glean's Library, ChatGPT Projects, Perplexity Spaces all converged here — **a Library is a named product primitive in every tier-1 tool**, and the failure mode is the junk drawer. Our anti-junk-drawer mechanics: documents carry subject + freshness + trust summary; retrieval is query-across-library ("what did Q1 customer calls ask for?"), not folder spelunking.

**Search substrate — open decision, K-in corrected:** the domain is already claimed twice in-tree — SQLite FTS5 (`migrations/065_search_fts5.sql`, `db/search.rs`: `search_index`, `search_global`, `rebuild_search_index`; entity-scoped today) and the ADR-0074/0078 fastembed vector stack (`content_embeddings`, hybrid retrieval; ADR-0131 canonicalization). The Library's L0 compares **extend FTS5 to document bodies vs. add tantivy vs. hybrid with ADR-0074 retrieval** — and if tantivy wins, states what `search_index` becomes (consumed/superseded — never dual-running; that's the 11-dual-systems anti-pattern this program exists to kill). ADR-0130's amendment explicitly forbids abilities reinventing retrieval; this decision honors it.

**Transcripts are first-class Library citizens** with the two-layer pattern (Granola's proven trust affordance): structured summary on top, raw transcript one click beneath, every summary bullet tracing toward its transcript origin. **Feasibility correction:** the substrate stores file-level `source_ref` + evidence *quote text* (`claim_semantic_evidence.original_text`) — no span offsets. So bullet→span is render-time quote matching with a designed no-match fallback (LLM paraphrase is a real path; highlight the file, not a phantom span), OR span-level provenance capture at extraction time, which is its own substrate L0. WD names the mechanism; W3's AC tests the paraphrase-miss case. Intake extends ADR-0044 (meeting-scoped transcript intake) and the ADR-0081 enrichment pipeline — extension, not reinvention. The Library IS the file surface: workspace markdown files are projections of Library documents (an explicit one-directional supersession of ADR-0047's bidirectional two-file sync, in the ADR-0048 lineage), and the folder is Cowork-grantable, so delegated long-form work lands in the same place. File intake routes through ADR-0050's extraction path.

### 4. The Day (calendar is the spine)
Research is unambiguous: every surviving product in this category (Granola, Fellow, Read.ai, alfred_) organizes by the day or the meeting; calendar-as-source-not-spine is the minority losing position. The Day is the one *standing* document: the D-spine briefing (±7-day window), regenerated by the system, pushed before you wake, every section claim-backed. Meetings hang off it; their prep documents and post-meeting documents link back to it. **Email's role (re-derived):** the market killed full-inbox-inside-knowledge-apps (Clockwise dead, others narrowed). Email is a *source* and a *digest section in the Day* with in-context triage actions — `EmailsPage` dies without a successor page, replaced by the Day's communications section + claims. Same logic for the standalone Inbox page.

### 5. The Prompt (and the Click — same pipeline)
"Give me a briefing on Acme" — typed anywhere, or clicked (every entity chip is a canned prompt). Intent → producer (ability) → document streams into existence block-by-block (Streamdown for prose blocks, typed block markers for claim components — Stack B from the OSS research: **keep our 19 renderers, add streaming insertion; adopting Plate/Tiptap wholesale loses our typed Composition advantage**) → lands as a named Library document.

What the answer looks like, concretely, at beyond-state-of-the-art (the unclaimed gap the research identified):

> **Acme — Briefing — 2026-06-12.** Sections: *What changed · Open threads · Key people · Risks · Next actions.* Every section: inline claim citations, trust-as-opacity, "from data as of Tue." Header affordances: **Refresh** (re-run the query), **What changed since last time** (diff vs the previous Acme briefing — no product does this), **Correct** (block-level, feeds the loop), **Go deeper** (delegates long-form work to Cowork/Agent SDK and the result lands in the Library).

Asked again next week, you get a new dated document + the diff. The Library accumulates a *briefing history per entity* — which is itself memory.

**Entities, re-derived:** standing entity *pages* die. An entity is a thin standing spine (hero + vitals, claim-backed) plus its documents: briefing-on-demand, meeting history, transcript trail. The CRM-style 1,076-LOC AccountsPage becomes a Library query ("accounts, by attention"). **Tasks/actions, re-derived:** actions are blocks inside documents (they were born in transcripts and emails anyway) plus one standing queue document ("needs your decision," budgeted, per the old DOS-443 thinking) — not a page with 12 invokes.

### 6. The Correction (exists — the loop)
Block-level correction everywhere a block renders, one writer (ADR-0138), tracked-changes accept/reject UX. The moat instrumentation (DOS-869) measures whether this loop is *felt* — and the document grammar makes every correction visibly improve the next document, which is the product thesis made tangible.

## Captured thinking — the trust contract as a protocol (2026-06-12, NOT designed)

Context: the company is moving from Glean to Claude Enterprise as the org default. Beyond Glean-as-source aging out gracefully (provenance + temporal decay handle source death by design), James's idea, captured at idea-fidelity:

Colleagues will build Claude skills and agents. If **we author DailyOS-style trust expectations into skills we build** — an output convention where assessments/briefings emit a claims appendix (claim + subject + evidence references across the MCP sources consulted + as-of date, i.e., ADR-0125 anatomy + ADR-0105 envelope as an authoring convention) — then Claude-produced derivative work becomes **pre-claimed source material**. Ingestion inverts from expensive extraction to cheap validation: incoming claims corroborate, contradict (→ review queue), or commit as novel against the existing ADR-0123/0126 machinery, and **each colleague's skill becomes its own learnable source** with a personal reliability curve from corrections — the me-shaped moat extended over other people's agents.

Two guards noted for whenever this is designed: evidence references unreachable from local MCP can only be *attributed*, never auto-verified (`use_with_caution`, reference preserved); and ingest needs the mirror of the ADR-0117 publish boundary — sensitivity classification on the way in.

**Status: thinking captured only.** No schema, no tickets, no wave slot. Revisit naturally when W3 (Library — where such documents would land) or the Claude-runtime spike makes it concrete.

## What this kills beyond the old plan

The earlier wave plan converted the existing taxonomy to blocks. This vision **deletes most of the taxonomy instead**: no standing list pages (Library queries), no EmailsPage/InboxPage (Day sections + sources), no per-report bespoke pages (documents), entity detail shrinks to spine + documents. The page inventory collapses to roughly: **the Day, the Library, a document view, the queue, settings/onboarding.** Five-ish, not twenty-five. The 21 hand-wired surfaces don't get converted; they get *answered* by three primitives.

## What stays honest

- Gates unchanged: latency checkpoint + instrumentation readout still precede conversion waves (ADR-0139).
- The substrate is untouched; producers/Compositions/claims are consumed, not re-architected. New block families (list/triage/report from DOS-870) become *document section types* rather than page frameworks.
- Risks named: streaming-block coordination is real build (the OSS research's "Stack B underestimates editing infrastructure" warning); the Library can junk-drawer without the freshness/subject mechanics; diff-between-briefings needs claim-level change tracking the substrate already has (lifecycle events) but no one has rendered; Day-document regeneration cadence vs token burn (James's felt pain) is exactly what DOS-869's token axis measures.
