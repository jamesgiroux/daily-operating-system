v2.0 Shell Rebuild — Boundary Document

The shell is rebuilt from a clean slate. The substrate crosses intact. This doc names what crosses, what dies, and what is born at the boundary.

Decision (James, 2026-06-11): DailyOS v2.0 rebuilds the shell — pages, layouts, chrome, display components — from a clean slate on the existing v1.x substrate. All current projects are abandoned in favor of v2.0. With ~4–5 users, migration cost is near zero; the expensive thing is not the move, it's continuing to retrofit blocks onto a shell that predates them. This is a boundary document, not a wave plan: every subsystem gets a disposition and a citation, then the design session takes it from there.

SUPERSEDED 2026-06-11 — see v2.0-case.html (this draft's matrices fold into its §5) Decided 2026-06-11 ~4–5 users · migration cost near zero All current projects → v2.0 Substrate: existing v1.x, not rewritten

The decision

Rebuild the shell. Keep the substrate.

v1.x grew its shell page-by-page before the blocks model, the claim substrate, and the trust-rendering work existed. The substrate is now ahead of the shell that displays it. Rather than a fourth retrofit, v2.0 starts the shell over with the blocks model as the architecture from day one.

Clean-slate shell

Pages, layouts, and display chrome are authored fresh against the blocks model. Nothing in the v1.x page tree is owed continuity.

Existing substrate

Claims, abilities runtime, composition model, DB hardening, design system — all proven v1.x machinery crosses unchanged. The boundary is shell/substrate, not new/old.

Migration cost near zero

~4–5 users, one of whom is customer-zero. No external migration program, no compatibility shims, no deprecation period beyond what the rebuild itself needs.

New in v2.0

Born at the boundary.

Net-new shell architecture that exists on the v2.0 side only. Three pieces, all consuming the substrate that crosses above.

Blocks model as the shell architecture

Producers shape content. Display-only blocks render it — design-system patterns like EntityHero, DayStrip, VitalsStrip. The customizer composes layouts. No page-specific data plumbing.

Daily briefing D-spine surface

A briefing surface on the D-spine with a ±7-day window — yesterday's residue and the week ahead on one navigable strip.

One EntityHero

A single EntityHero across account, person, and project pages. Entity-type differences are data, not component forks.

Evidence

Why this week, not later.

The decision is grounded in three observations from the past two weeks, not in appetite for novelty.

Three retrofit failures on DOS-852

Three attempts to retrofit blocks onto the existing detail-page shell failed before content-fidelity landed. The retrofit cost exceeded the rebuild cost; the fourth attempt should not be a retrofit.

DOS-866 starvation incidents

Writer-queue starvation was diagnosed and fixed entirely at the substrate layer — rank-then-cap, phased persist — without touching the shell. The boundary this doc draws already exists in practice.

Clean-sheet examination, 2026-05-28

The DB-loss forcing-function examination concluded: decouple cheap-certain from contested. A shell rebuild on proven substrate is the cheap-certain move; a substrate rewrite is the contested one this doc declines.

Examination doc: .docs/plans/dailyos-rearchitecture-examination-2026-05-29.md. DOS-852 retrofit history and the starvation incident trail live on the Linear tickets (DOS-852, DOS-866).

Non-goal

This is not a substrate rewrite.

The second-system tuition is already paid. The claims schema, abilities runtime, composition model, and DB hardening were each earned through production incidents and review cycles; rewriting them would re-buy lessons we already own.

v2.0 changes what renders, not what knows. If a v2.0 work item proposes touching claim semantics, the writer queue, the abilities contract, or the composition model beyond consuming them, it is out of scope for the shell rebuild and goes through its own L0 as substrate work. The 2026-05-28 examination treated storage-model and surface-model rewrites as contested hypotheses to validate cheaply before betting the moat — that posture stands.

Open questions

For the design session.

The boundary is decided; these are not. Each resolves at the James + Claude design session before wave planning starts.

1 · Page inventory

Which pages exist in the v2.0 shell on day one? The kill list removes tab views and the deprecated entity pages; the pages-per-view model needs an explicit inventory before layouts are composed.

2 · Migration order

Which surface converts first, and in what sequence? Daily briefing, entity detail, and list surfaces have different substrate readiness; order determines what the customizer must support earliest.

3 · What v1.x keeps running

Which v1.x surfaces stay live during the rebuild for the ~4–5 current users, and what is the cutover trigger per surface? Near-zero migration cost still isn't zero downtime tolerance for customer-zero.
