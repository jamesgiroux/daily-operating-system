## 2. Dual / parallel systems

Every place two (or more) mechanisms do one job, found by grep across `src/` and `src-tauri/src/`.

### 2.1 Two shells, one reachable
`src/router.tsx` maintains a magazine shell (`MagazinePageLayout`, `router.tsx:358-389`) and a sidebar shell (`SidebarProvider`/`Header`, `router.tsx:391-418`). `MAGAZINE_ROUTE_IDS` contains all 26 route IDs, so the sidebar branch never executes. It keeps alive `src/components/dashboard/Header.tsx` (imported only by the router) and `src/components/ui/sidebar.tsx` (724 LOC, imported only by `Header` and the router). The dual shell is dead weight that every router change has to navigate, and the route-ID allowlist (`router.tsx:99`) is a hand-maintained string set that must be edited for every new route.

### 2.2 Three generations of entity detail, two still in the tree
- Gen 1 (deleted): `AccountDetailShell.tsx` + `src/pages/account-views/{AccountContextView,AccountHealthView,AccountWorkView}.tsx`, `PersonDetailPage.tsx`, `ProjectDetailPage.tsx` (all in `git log --diff-filter=D -- src/pages`).
- Gen 2 (dead-but-importable): `AccountDetailEditorial.tsx` + `src/components/account/*` (2,154 LOC) + `useAccountDetail` orchestrator chain. 72 commits of history.
- Gen 3 (live): `AccountDetailPage.tsx` (composition-backed). 90 commits under `--follow`.
- Person/project detail are mid-migration hybrids: `PersonDetailEditorial.tsx` and `ProjectDetailEditorial.tsx` each call BOTH `useProjectedComposition` and their legacy detail hook (`usePersonDetail` / `useProjectDetail`) in the same render.

45 page files have been created at `src/pages/*.tsx` over the repo's life; 24 remain (plus the monthly-wrapped subtree). The shell has already been partially rebuilt at least twice without retiring the prior generation's code.

### 2.3 Three feedback mechanisms
1. `src/hooks/useIntelligenceFeedback.ts` — self-described "Compatibility hook for the legacy thumbs-up / thumbs-down UI"; reads `get_entity_feedback`, writes `submit_intelligence_correction`. Used by **8 live surfaces**: `BookOfBusinessPage`, `SwotPage`, `RiskBriefingPage`, `WeeklyImpactPage`, `MeetingDetailPage`, `AccountHealthPage`, `EbrQbrPage`, plus dead `AccountDetailEditorial`.
2. `src/hooks/useIntelligenceCorrection.ts` — the unified correction action (confirmed/rejected/annotated/corrected/dismissed). Used by `src/components/ui/IntelligenceCorrection.tsx` and `src/components/composition/CompositionInlineEdit.tsx`.
3. `submit_claim_feedback_command` (`src-tauri/src/commands/claim_feedback.rs:67`) — claim-level feedback, reached from the frontend only via `src/services/claim-receipt/useClaimReceiptSubscription.ts`.

Three write paths into the feedback loop; which one a correction takes depends on which page generation the user happens to be on.

### 2.4 Two display sources for entity intelligence
- Legacy path: `useEntityDetailIntelligence` → `invoke_ability("get_entity_intelligence")` (`src/services/entity-intelligence/invoke.ts:31`) → `mergeEntityDetailIntelligence` (`src/services/entity-intelligence/entity-detail-mapper.ts`) which maps the claim envelope **back into the legacy `EntityIntelligence` JSON shape** so old renderers don't have to change. The shape descends from `intelligence.json` files, whose fields were moved into `entity_assessment.*_json` columns by `src-tauri/src/migrations/057_intelligence_db_columns.sql`.
- Composition path: claims → producer ability → typed blocks with `claim_refs`/`provenance_ref` per ADR-0130.

Same claims, two projection grammars, two trust-rendering vocabularies. The mapper file exists precisely because the old shape can't be deleted while 8+ surfaces render it.

### 2.5 Two briefing data paths
`DailyBriefing.tsx` is fed by `useDashboardData` (`get_dashboard_data` command, `src/hooks/useDashboardData.ts:60`) at the router level, and itself consumes `useDailyBriefingAbility` (`src/services/daily-briefing/invoke.ts`) — a command path and an ability path feeding the single most important surface.

### 2.6 Bespoke report pages plus a generic one
Six bespoke report pages (`RiskBriefingPage`, `AccountHealthPage`, `EbrQbrPage`, `SwotPage`, `WeeklyImpactPage`, `BookOfBusinessPage` — 2,998 LOC combined) and a generic `ReportPage` (128 LOC) all render `get_report` rows. The router carves bespoke routes out ahead of the `$reportType` catch-all (`router.tsx:477-529`). Report JSON artifacts are a display source with no per-claim provenance — exactly the "data that only renders in the frontend" shape CLAUDE.md's Intelligence Loop check names as incomplete.

### 2.7 Six hero implementations
`src/components/account/AccountHero.tsx`, `src/components/person/PersonHero.tsx` (orphan), `src/components/project/ProjectHero.tsx` (orphan), `src/components/entity/SentimentHero.tsx` (513 LOC, used by `BlockComponents.tsx`), `src/components/health/SentimentHero.tsx` (11-line re-export shim whose comment says "so the page compiles during the Wave 0 overlap"), and the composition `AccountHeroBlock` (`src/components/composition/blocks/AccountHeroBlock.module.css` + `BlockComponents.tsx`). One job — entity hero — six implementations across the generations.

### 2.8 Tab systems encoded as route search params
Settings keeps 6 live tab IDs plus 6 "Legacy tab IDs for backwards compatibility" (`router.tsx:86-92`). People has relationship tabs + hygiene filters as validated search params (`router.tsx:94-95, 605-621`). Tabs-as-state and pages-as-routes coexist with no rule for which a new view gets.

### 2.9 Two triage inboxes
`EmailsPage` (1,336 LOC, 17 invokes, Gmail triage) and `InboxPage` (1,081 LOC, capture/dropbox triage). Separate components, separate command sets, same interaction grammar (list → classify → act).

### 2.10 The parity layer is the dual-systems tax made explicit
`src/parity/` (874 LOC + mock fixtures: `account_detail.json`, `meeting_detail.json`, `person_detail.json`, `project_detail.json`, `dashboard_briefing.json`, `reports.json`, …) exists to verify that Tauri pages and MCP outputs agree. A registry of contracts per surface (`phase3ContractRegistry.ts`, `phase3OwnershipMap.ts` — both still importing dead `AccountDetailEditorial`) is maintenance that only exists because the same intelligence is projected through two independent presentation codebases. The v1.4.9 W5 scope spiral (memory: "MCP/surface parity perfection is a scope trap") was a symptom of this structure, not a planning accident.

### 2.11 Duplicate/dead hooks
`useAccountDetailPage.tsx` is referenced by no file except itself (orphan twin of `useAccountDetail.ts`). Entity-intelligence consumption is spread across `useEntityDetailIntelligence`, `useMeetingEntityIntelligence`, and `useExecutiveIntelligence` — three per-context wrappers over the same ability family.

## 4. Product-thesis alignment

Sources: `.docs/design/product/MISSION.md`, `VISION.md`, `PRODUCT-THESIS.md`, `PHILOSOPHY.md`.

**Where the shell structurally fights the thesis:**

1. **"Open the app. Your day is ready."** (VISION.md:3) vs. a 26-route navigation surface. The thesis is briefing-first consumption; the shell is mission-control. List pages — `AccountsPage` (1,076 LOC, 12 invokes), `EmailsPage` (1,336 LOC, 17 invokes), `PeoplePage`, `ProjectsPage`, `ActionsPage` — are operate-the-database surfaces. PHILOSOPHY.md:81: "The AI gathers, compiles, organizes. You show up and consume the output" — but 21 of 25 surfaces are hand-assembled by page code issuing 1–28 imperative invokes, i.e., the *frontend* is the operator assembling meaning, which is the exact failure MISSION.md:15 attributes to the status quo ("the person doing the work still has to assemble the meaning").
2. **"The mission is not the surface"** (MISSION.md:55) — yet surface cost dominates: 83K TS/TSX + 30K CSS LOC of per-page wiring against a substrate whose whole point (ADR-0128 §1) is "the substrate is the product; the heads are surfaces over it." Each new entity type or report today requires a new page, new hooks, new commands, a `MAGAZINE_ROUTE_IDS` entry, and a parity fixture.
3. **"Trust as a testable contract … no drift between surfaces"** (PRODUCT-THESIS.md:87-96; memory `project_memory_plus_judgment_equals_trust`). The shell currently renders the same claims through two grammars (§2.4) and accepts corrections through three paths (§2.3). Drift between surfaces is not a risk — it's the standing state. The 8 report/legacy surfaces using thumbs feedback can't express the correction vocabulary (`corrected`, `annotated`, `dismissed`) the thesis says drives belief revision.
4. **"Corrections that change future behavior"** (PRODUCT-THESIS.md:133) — report rows (§2.6) are terminal JSON artifacts; feedback against them attaches to entity fields, not to the claims that produced the content, so the loop back to source-reliability learning is lossy on 7 surfaces.
5. **Decision filter #2** (MISSION.md:93, "context when it matters, or more information to manage?") — Emails/Inbox/Accounts/People as standing destinations are "information to manage" surfaces. The thesis tolerates them only as today's incidental shape (MISSION.md:53 "The surfaces will change").

**Where the shell already agrees with the thesis:** the briefing-first startup gate (`routerStartupGate.ts`, `StartupBriefingScreen`), proactive push (`useNotifications`, `PostMeetingPrompt`), and the 4 composition-backed detail surfaces with per-claim provenance (trust-as-opacity, commits `337d5c40`/`1537b745`) are aligned. The misalignment is concentrated in the 21 non-composition surfaces and the navigation taxonomy.

## 5. What a blocks-native shell enables that the current one cannot

Grounded in ADR-0130 (composition contract, Accepted), ADR-0128 (MCP as co-equal head), ADR-0135 (app + MCP are the surface strategy):

1. **New entity types without new pages.** Today a new entity kind needs: a page component, hooks, direct commands, a route, a `MAGAZINE_ROUTE_IDS` entry, parity fixtures. Blocks-native: a producer ability returning `AbilityOutput<Composition>` plus (at most) new block types in one registry (`BLOCK_RENDERERS`, currently 19 entries). The orchestrator already resolves producers by `(ability, subject_kind)` tuple (`composition_render_orchestrator.rs:588-609`) — adding a 5th entity kind is one match arm, not a 500-LOC page.
2. **One payload, every surface (ADR-0128/0135).** The same `Composition` the Tauri renderer consumes is the MCP answer shape. The parity layer (§2.10) shrinks from fixture-diffing two presentation codebases to verifying one producer contract — the thing that cost v1.4.9 W5 three days becomes a unit test on the producer.
3. **Customizer composition.** Preset- and layout-personalization already exists *only* on composition surfaces: `useActivePreset`, `useChapterLayout`, drag-reorder via `useSortable` in `AccountDetailPage.tsx`, `CompositionInlineEdit.tsx`. None of the 21 legacy surfaces can be reordered, re-weighted, or persona-shaped without bespoke code per page. Blocks make "me-shaped" (the moat) a rendering property instead of a per-page feature.
4. **Uniform trust rendering and feedback.** Blocks carry `claim_refs` + `provenance_ref` (ADR-0130 §2 amended), so trust bands, trust-as-opacity, and claim-level corrections come for free on every surface — collapsing the three feedback paths (§2.3) and two display grammars (§2.4) into one. This is the only structural route to "no drift between surfaces."
5. **Salience-driven layout instead of hand-ordered JSX.** `Section.salience`/`Block.salience` let the substrate decide prominence (PRODUCT-THESIS.md:136 "more accurate surfacing thresholds"); today prominence is whatever order a page author wrote in 2026-03.
6. **Deterministic degradation.** ADR-0130 §3's schema-bounded projection gives unknown payloads a defined `needs_verification` fallback; legacy pages throw or silently drop.

What blocks-native does **not** automatically give: list/triage interaction grammars (multi-select, bulk ops), write-heavy flows (email triage actions, team management mutation), or Settings. Those need block types or shell affordances that don't exist yet — see §6.

## 6. Honest counter-case — what works today and what a rebuild risks

The system is in daily production use by customer-zero. Estimates below are labeled estimates (single engineer + agents, calibrated against this repo's actuals: the 4-surface composition migration spanned v1.5.0 R0–R5 across multiple weeks).

| Working today | Risk if rebuilt | Migration estimate |
|---|---|---|
| **MeetingDetailPage** (2,940 LOC, 28 invokes): prep, agenda drafts (`useAgendaDraft`), outcomes, post-meeting capture. No meeting producer exists in `composition_render_orchestrator.rs`. | Highest-value daily surface; richest write flows; a regression here breaks the ritual the product exists for. | **2–3 weeks** (producer + write-intent blocks + L4) |
| **DailyBriefing** (1,144 + meeting cards 757): the proven ritual. Dual data path but it works. | Breaking the "open the app, day is ready" moment during a shell swap is the worst possible regression. | **1–2 weeks** (briefing producer exists as ability; layout + freshness/empty/error states are the work) |
| **Email + Inbox triage** (2,417 LOC, 25 invokes combined): operational mutation flows. | Block model is read-oriented; triage needs action-dispatch blocks that don't exist (nearest analog: `action_list`). | **2–3 weeks combined** |
| **List pages** (Accounts/People/Projects/Actions, ~2,900 LOC): selection (`useEntityListSelection`), hygiene filters, bulk archive. | No list-composition block type exists; salience-ordered lists are a design problem, not just a port. | **2–3 weeks combined** |
| **Reports ×7** (~3,100 LOC): generation flows (`generate_risk_briefing` etc.), save/regenerate lifecycle works. | Report-as-composition requires claim-backed report producers — substrate work, not just rendering. | **2–3 weeks** |
| **Settings + onboarding + recovery** (7,562 LOC settings-ui; `OnboardingFlow`, `DatabaseRecovery`, `LockOverlay`, startup gate): not intelligence surfaces. | Porting these to blocks is wrong-tool work; they should be carried over, not rebuilt. | **~0 if explicitly carried; 1 week of shell-integration glue** |
| **Field-edit mutation paths** (`useAccountFieldSave`, `useTeamManagement`, `useIntelligenceFieldUpdate`): battle-tested writes through services. | `CompositionInlineEdit` covers some of this on 4 surfaces; parity for team management / stakeholder flows is unproven. | folded into per-surface items above |
| **Person/Project hybrids**: already half-migrated. | Low — finish the migration, delete the legacy hooks. | **3–5 days** |

**Sum of estimates: roughly 10–15 engineer-weeks** for a complete blocks-native shell at current quality, *excluding* new design work (the v1.5.0 detail-page designs are explicitly James+Claude collaborative per the reconciliation memory) and excluding the block types that don't exist yet (list, triage/action-dispatch, report).

**Structural risks, from this repo's own record:**
- **The parity trap generalizes.** v1.4.9 W5 spent 3 days chasing perfect MCP parity before scope was manually cut. A big-bang shell rebuild is that trap at 10× scale. Mitigation evidence: the incremental path (route-by-route swap behind the existing router) is already proven — `AccountDetailPage` replaced `AccountDetailEditorial` without a shell rewrite.
- **The graveyard pattern.** Both prior detail-page rebuilds left the previous generation in the tree (§2.2, §3.4). A v2.0 that doesn't include deletion as an explicit acceptance criterion will produce a *fourth* parallel system, not a replacement. The 27 orphans and the unreachable sidebar shell are the measured precedent.
- **Blocks-path early mono-file growth.** `BlockComponents.tsx` is already the largest frontend file (1,232 LOC) with 19 renderers in one module. The new system shows the same accretion habit; a rebuild without componentization rules reproduces the disease in new clothes.
- **WordPress lesson (ADR-0135).** The last "redesign tokens spent once" wager was reverted; the ADR's own closing rule applies: the cheapest moment to commit a surface is after the differentiator is proven. The counter-pressure: unlike WP, blocks-native Tauri requires no new deployment story, no new runtime, and 4 surfaces of it are already shipped — it is an extension of the accepted ADR-0130 path, not a new bet.

## 7. Summary of measured findings

1. 26 routes, 25 surfaces, 21 of them hand-wired; 4 composition-backed (2 hybrid). The dual shell's sidebar branch is unreachable dead code.
2. At least 11 dual/parallel systems doing one job each (shells ×2, detail generations ×3, feedback ×3, intelligence display ×2, briefing data ×2, report renderers ×2, heroes ×6, inboxes ×2, tab regimes ×2, hook twins, plus the parity layer that exists to police the duplication).
3. Accretion is the house style, not an account-detail incident: 45 pages created → 24 remain; 27 orphan components; components 175→236 in 3.5 months; the backend needed ADR-0133 to halt the identical pattern (seven write-discipline layers) on its side.
4. The shell's center of gravity (lists, triage, per-page invoke assembly) is structurally at odds with the written thesis (briefing-first, consume-not-operate, no-drift trust); the parts that agree with the thesis are exactly the composition-backed parts.
5. Blocks-native is not speculative here: contract accepted (ADR-0130), orchestrator + renderer + inline-edit + presets shipped, 4 surfaces live.
