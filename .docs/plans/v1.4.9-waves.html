v1.4.9 — Substrate Reset & Judgment Maturation

Wave execution plan · the version that makes corrections stick
DRAFT 2026-05-30 · Linear project 874a7361 · waves mirror W1–W6 milestones · protocol: .docs/plans/v1.4.0-waves.md

"I correct it once, and it stays corrected — everywhere."

North Star

A claim carries provenance and a trust band. The user dismisses, contradicts, or re-scopes it — in the app or by editing the claim's readable file — and the system responds: the source's reliability updates, derived claims invalidate, and what surfaces next visibly changes, consistently across the macOS app and MCP.

Proof obligation (PRODUCT-THESIS)

Every wave either demonstrates its slice of the correction loop —

claim (provenance + trust band) → user correction (dismiss / contradict / re-scope / edit file) → source reliability + derived claims update → next surfacing reflects the correction

— or is explicitly labelled substrate (infrastructure with no direct user outcome, justified by what it unblocks). "If a release doesn't move the correction loop, it's substrate maintenance, not product." v1.4.9 carries both: W1–W2 are the reset's substrate; W3–W6 carry the headline.

Strategic frame — DailyOS is the personal-judgment substrate (claims · trust · abilities · salience · belief revision). Memory is commoditizing; judgment you can trust is the moat, deepened by the daily-correction loop (the me-shape). Per ADR-0135 the primary programmatic surface is MCP read/write; the macOS app stays the visual + control-plane surface (not deprecated); net-new surface design defers to v1.5.0. SQLite stays canonical (ACID); readable files are a projection out, never files-as-truth.

Cross-Wave Decisions

  • SQLite stays canonical; encryption is dropped, not the database. Cipher-drop (W1) is an ADR-0092 §D5 amendment: plain SQLite on a FileVault-encrypted volume; at-rest protection moves to the OS disk boundary, matching the local-same-user threat model.
  • Fresh-install rebuild, not migration, is the recovery path. Canonical workspace JSON + re-enrichment rebuilds the DB from scratch (W1) — the path James exercised in the 2026-05-29 incident recovery, made first-class.
  • Single-process DB ownership + writer-priority lane (647). Continues db-throughput W0; 758 lands the handler-side request-scoped DB/services contract + nested-writer guard. (The v1.2.2 enrichment write-lock James is hitting right now is exactly the contention this resolves.)
  • Files-as-projection, bidirectional via correction only. W3 projects claims → per-entity markdown out; editing a file is a correction input through the claim service — it does not make the file authoritative.
  • Security right-sized to the OS boundary (W2). HMAC/pairing/presence-nonce/scope-grant ceremony for local same-OS-user surfaces is stripped; hostile-input proof (510) re-scoped. (759/760 already cancelled.)
  • Trust rendering is centralized. Same provenance + trust-band + sensitivity rendering serves app and MCP (W5 = agent-native parity, not a second renderer).
  • Migration-slot reservations. W1 and W6 both add migrations — reserve non-overlapping blocks at kickoff (the v1.4.1 lesson). Confirm next free slot against dev head.

Wave Detail

W1 — Storage reset & single-writer substrate

Make the DB cheap to rebuild, safe to operate, single-writer-owned — the durable fix for the dev-workflow-corrupts-prod hazard (DOS-820).

  • DOS-826 NEW — drop SQLCipher → plain SQLite + FileVault (ADR-0092 §D5 amendment)
  • DOS-827 NEW — first-class rebuild-from-canonical-JSON (recovery path)
  • DOS-647 single-process DB ownership + writer-priority lane · DOS-758 McpToolHandler request-scoped DB/services + nested-writer guard
  • DOS-823 820-C: replica-refresh clone + destructive-command guards — completes DOS-820
  • DOS-767 DOS-768 DOS-770 DOS-812 ingestion-hygiene + consolidation carryovers (re-validate against rebuilt pipeline)

substrate; demoable — replica-refresh clones prod→replica, prod-destroyers refuse outside the guard, a from-scratch rebuild reproduces the working DB.

W2 — Security right-size substrate

Collapse app-layer auth ceremony to the OS user boundary for local same-user surfaces.

  • Auth overhaul — strip HMAC + pairing + presence-nonce + scope-grant for local-to-local same-OS-user (verify post-overhaul model before re-adding any gate)
  • DOS-510 hostile-input / prompt-injection proof gates, re-scoped to the post-overhaul threat model (hostile content is evidence text only, never instructions)

substrate; demoable — local invoke + WP/MCP loopback reach parity with no signing ceremony; hostile-input fixtures pass.

W3 — Claims → editable readable files first loop slice

The reverse leg of bidirectional markdown↔substrate: project claims out to per-entity readable files, and accept edits to those files as corrections.

  • DOS-628 per-entity claim→markdown projection (out) + file→claim correction write-back through the claim service. SQLite stays canonical.

edit a claim in its readable file → the claim updates, provenance records the correction, the projection re-renders, trust/derived state reacts.

W4 — Judgment moat / correction loop HEADLINE

The full correction loop, visible end-to-end and measured.

  • DOS-8 semantic claim feedback (typed claim_feedback) · DOS-318 contradiction UX as review-queue reconciliation (1-byte stub today)
  • DOS-443 review-queue daily budget + prioritization · DOS-447 per-claim_type render suppression (stub)
  • DOS-316 + DOS-811 deviation / "what's unusual" + expected_presence registry
  • DOS-338 the eval harness that proves the moat (stub) — usefulness / noise / missed-important + correction-stickiness
  • DOS-446 adversarial hundred-claims fixture · DOS-278 briefing count divergence · DOS-277 agenda survives re-enrichment · DOS-317 engagement → ranking (full)

a correction in any entry point propagates to source reliability + derived claims and changes what surfaces next, with the eval harness (338) measuring stickiness + noise. This is where "correct once, stays corrected" is demonstrated.

W5 — MCP-first parity loop over MCP

The same loop + trust rendering reachable over MCP — no second renderer, no service bypass.

  • DOS-169 create_action · DOS-170 update_action_status · DOS-171/DOS-479 provenance + source-aware read · DOS-172 pagination/ranked discovery · DOS-173 resources
  • DOS-777 daily + meeting briefing read handlers (Phase-B; un-cancelled) — the surface where corrected claims appear over MCP · DOS-481/DOS-482 evals + E2E validation

an MCP client sees the same claims, trust bands, and post-correction surfacing the app shows; corrections made over MCP propagate identically.

W6 — Transcript substrate transcript claims → loop

Rebuild transcript extraction as claim-producing abilities so transcript intelligence flows through the same trust + correction loop.

  • DOS-343 transcript extraction → claims; stabilize meeting-record rendering (no-findings / skipped / failure / malformed / not-processed / valid-empty)
  • DOS-327 local-first Quote Wall source typing + provenance/UI readiness · DOS-511 formal L0 package split

a transcript claim carries provenance + trust band, surfaces in briefings, and responds to correction like any other claim.

Definition of Done

  • Headline proven: a correction made in the app, in a readable file, and over MCP each propagates to source reliability + derived claims and changes the next surfacing — with real workspace data, measured by the DOS-338 eval harness.
  • Substrate reset complete: plain SQLite + FileVault; repeatable rebuild-from-JSON; single-writer ownership; replica-refresh + destructive-command guards (DOS-820 closed); auth right-sized with hostile-input proof.
  • Cross-surface parity: identical claims + trust rendering + post-correction behaviour across Tauri and MCP.
  • No stubs/TODOs/deferrals: contradiction.rs, render_rules.rs, deviation.rs, eval.rs are real; transcript extraction is claim-producing.
  • Gates green: cargo clippy -- -D warnings && cargo test && pnpm tsc --noEmit (DOS-824 test-flake tracked separately).
