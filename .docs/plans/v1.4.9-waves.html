DailyOS · v1.4.9 · Wave Plan

I correct it once, and it stays corrected — everywhere.

Substrate Reset & Judgment Maturation. Substrate-first sequencing; the headline outcome lands at W4.

A claim carries provenance and a trust band. The user dismisses, contradicts, or re-scopes it — in the app or by editing the claim's readable file — and the system responds: the source's reliability updates, derived claims invalidate, and what surfaces next visibly changes, consistently across the macOS app and MCP. W1–W2 are the reset's substrate; W3–W6 carry the headline.

Target: 2026 (DRAFT) Waves: 6 Issues: 34 Source: Linear project 874a7361

Proof obligation

Every wave moves the correction loop, or is labelled substrate.

Per PRODUCT-THESIS: "if a release doesn't move the correction loop, it's substrate maintenance, not product." The loop each wave must show its slice of:

claim (provenance + trust band)
   → user correction  (dismiss / contradict / re-scope / edit file)
   → source reliability + derived claims update
   → next surfacing reflects the correction

Strategic frame — DailyOS is the personal-judgment substrate (claims · trust · abilities · salience · belief revision). Per ADR-0135 the primary programmatic surface is MCP read/write; the macOS app stays the visual + control-plane surface (not deprecated); net-new surface design defers to v1.5.0. SQLite stays canonical; readable files are a projection out, never files-as-truth.

Wave shape

Cross-wave decisions

Architecture that holds across the version.

SQLite stays, cipher goes

Cipher-drop (W1) is an ADR-0092 §D5 amendment — plain SQLite on a FileVault volume. At-rest protection moves to the OS disk boundary, matching the local-same-user threat model.

Rebuild, not migrate

Canonical workspace JSON + re-enrichment rebuilds the DB from scratch (W1) — the path exercised in the 2026-05-29 incident recovery, made first-class.

Single-writer ownership

647 + 758 give single-process DB ownership + writer-priority lane + nested-writer guard. The v1.2.2 enrichment write-lock is exactly the contention this resolves.

Files-as-projection

W3 projects claims → markdown out; editing a file is a correction input through the claim service — it does not make the file authoritative.

Security to the OS boundary

W2 strips HMAC/pairing/nonce/scope-grant for local same-OS-user surfaces; hostile-input proof (510) re-scoped. 759/760 already cancelled.

Migration slots

W1 and W6 both add migrations — claim non-overlapping slot blocks at kickoff (the v1.4.1 rebase-renumber lesson).

Wave detail

What each wave carries and proves.

W1 — Storage reset & single-writer · substrate

The durable fix for the dev-workflow-corrupts-prod hazard (DOS-820).

  • DOS-831 NEW — drop SQLCipher → plain SQLite + FileVault (ADR-0092 §D5 amendment)
  • DOS-832 NEW — first-class rebuild-from-canonical-JSON (recovery path)
  • DOS-647 single-process DB ownership + writer-priority lane · DOS-758 McpToolHandler request-scoped DB/services + nested-writer guard
  • DOS-823 820-C: replica-refresh clone + destructive-command guards — completes DOS-820
  • DOS-767 / 768 / 770 / 812 ingestion-hygiene + consolidation carryovers

Proof — substrate; demoable: replica-refresh clones prod→replica, prod-destroyers refuse outside the guard, a from-scratch rebuild reproduces the working DB.

W2 — Security right-size · substrate

Collapse app-layer auth ceremony to the OS user boundary for local same-user surfaces.

  • Auth overhaul — strip HMAC + pairing + presence-nonce + scope-grant for local-to-local same-OS-user
  • DOS-510 hostile-input / prompt-injection proof gates, re-scoped to the post-overhaul threat model (hostile content is evidence text only)

Proof — substrate; local invoke + WP/MCP loopback reach parity with no signing ceremony; hostile-input fixtures pass.

W3 — Claims → editable readable files · first loop slice

The reverse leg of bidirectional markdown↔substrate.

  • DOS-628 per-entity claim→markdown projection (out) + file→claim correction write-back through the claim service. SQLite stays canonical.

Proof — edit a claim in its readable file → the claim updates, provenance records the correction, the projection re-renders, trust/derived state reacts.

W4 — Judgment moat / correction loop · HEADLINE

The full correction loop, visible end-to-end and measured.

  • DOS-8 semantic claim feedback (typed claim_feedback) · DOS-318 contradiction UX as review-queue reconciliation
  • DOS-443 review-queue daily budget + prioritization · DOS-447 per-claim_type render suppression
  • DOS-316 + DOS-811 deviation / "what's unusual" + expected_presence registry
  • DOS-338 the eval harness that proves the moat — usefulness / noise / missed-important + correction-stickiness
  • DOS-446 adversarial hundred-claims fixture · DOS-278 briefing count divergence · DOS-277 agenda survives re-enrichment · DOS-317 engagement → ranking (full)

Proof — a correction in any entry point propagates to source reliability + derived claims and changes what surfaces next, measured by the DOS-338 eval harness. Where "correct once, stays corrected" is demonstrated.

W5 — MCP-first parity · loop over MCP

The same loop + trust rendering reachable over MCP — no second renderer, no service bypass.

  • DOS-169 create_action · DOS-170 update_action_status · DOS-171 / 479 provenance + source-aware read · DOS-172 pagination · DOS-173 resources
  • DOS-777 daily + meeting briefing read handlers (Phase-B; un-cancelled) · DOS-481 / 482 evals + E2E validation

Proof — an MCP client sees the same claims, trust bands, and post-correction surfacing the app shows; corrections made over MCP propagate identically.

W6 — Transcript substrate · transcript claims → loop

Rebuild transcript extraction as claim-producing abilities.

  • DOS-343 transcript extraction → claims; stabilize meeting-record rendering (no-findings / skipped / failure / malformed / not-processed / valid-empty)
  • DOS-327 local-first Quote Wall source typing + provenance/UI readiness · DOS-511 formal L0 package split

Proof — a transcript claim carries provenance + trust band, surfaces in briefings, and responds to correction like any other claim.

Definition of done

All five true at version close.

  • Headline proven: a correction made in the app, in a readable file, and over MCP each propagates to source reliability + derived claims and changes the next surfacing — with real workspace data, measured by the DOS-338 eval harness.
  • Substrate reset complete: plain SQLite + FileVault; repeatable rebuild-from-JSON; single-writer ownership; replica-refresh + destructive-command guards (DOS-820 closed); auth right-sized with hostile-input proof.
  • Cross-surface parity: identical claims + trust rendering + post-correction behaviour across Tauri and MCP.
  • No stubs/TODOs/deferrals: contradiction.rs, render_rules.rs, deviation.rs, eval.rs are real; transcript extraction is claim-producing.
  • Gates green: cargo clippy -- -D warnings && cargo test && pnpm tsc --noEmit (DOS-824 test-flake tracked separately).
