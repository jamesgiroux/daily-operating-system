DailyOS · Engineering Ladder

From plan to merge, in seven gates.

L0–L6 with Plan, Implement, Review, and Capture roles per rung. Reviewer composition trimmed 2026-05-23 — defaults small, specialists routed in by concern.

The Engineering Ladder is how work moves from intake to merge. Each rung names the skills that apply at that phase — not just review. A continuous Knowledge Channel feeds findings into L0 and captures findings out of L3 / L5 so the same drift doesn't surface twice. The reviewer composition rule is one default reviewer per gate plus router-selected specialists — not every reviewer on every change.

Adopted 2026-05-18 Reviewer composition revised 2026-05-23 L0–L6 numbering preserved K-channel: docs/solutions/ + .docs/decisions/

Composition principle

Compose installed agents. Don't run every reviewer on every change.

Default reviewer counts are deliberately small. The cost of a 4-reviewer L0 × 5–6 convergence cycles drove this revision (W1 v1.4.5 burned ~27 review cycles across 3 lanes). The library of installed agents — ce-* and pr-review-toolkit:* — is large; the ladder composes specific agents per concern.

One default + routed specialists

L0 default is 2 reviewers (codex challenge + 1 planning reviewer). L2 default is 1 (codex review via the bounded-reviewer orchestrator) plus 0–2 router-selected specialists keyed to what the diff actually touches.

Advisory ≠ blocking

Code-quality concerns (maintainability, simplicity, duplication) run in parallel as advisory. Findings file to the maintenance project, not back to the cycle-N+1 reviewer loop. Tracked, not skipped — but not bottlenecking.

Scope tier picks panel size

Trivial fixes skip L0 entirely. Small fixes get 1 reviewer at L0. Standard gets 2. Wave gets 3 + K-in. Most work isn't wave-tier.

Skill matrix

Each rung, four roles.

Plan, Implement, Review, and Capture skills per rung. K-in (via ce-learnings-researcher at L0) and K-out (autonomous /ce-compound at L3 retro) are mandatory.

Scope-based sizing

Not every packet warrants the full reviewer panel.

Tier by scope. Declared in §0 alongside origination class. Reviewers can escalate or de-escalate at intake.

Scope What it looks like L0 panel L2 panel
Trivial Single-file fix <50 LOC, no contract change, no user-facing impact Skip L0 /codex review only
Small Single substrate or UI change, single domain /codex challenge (1) /codex review + 0–1 router
Standard Multi-file scope, single domain, no cross-cutting contract changes /codex challenge + 1 planning (2) /codex review + 1–2 router
Wave Architecture, substrate reshape, multiple domains, ADR-touching /codex challenge + 2 planning (3) + K-in parallel /codex review + 1–2 router + Suites at L3

Memory feedback_review_loop_diminishing_returns_means_scope_is_wrong: if a tier-N L0 produces 5+ findings per cycle, the tier is likely wrong — reset to tier-N+1 rather than absorbing findings cycle by cycle. Tier mis-declaration is a packet-author error, not a reviewer-thoroughness error.

Origination check

Debug-driven, greenfield, or extension.

Every L0 packet declares an origination class in §0 before §1 header. Debug-driven packets must include a symptom-to-failure trace.

Greenfield

Net-new substrate, no prior surface. Reviewer focus: substrate-grep K-in (don't reinvent), ADR fit, contract design.

Extension

Extends or refines existing substrate. Reviewer focus: backward compat, migration safety, ADR alignment.

Debug-driven

Originates from a user-visible failure. §0 MUST include symptom verbatim + call-path trace + suspected failure point (file:line) + hypotheses already rejected. §3 implementation must intersect the trace, or verdict = wrong cure.

Wrong-cure verdict — new disposition alongside APPROVE / REQUEST_CHANGES / BLOCK. Harsher than REQUEST_CHANGES because it means the packet's premise is broken; patching the implementation won't fix it. The packet must restart from a corrected trace. Memory feedback_parallel_codex_for_diagnosis_when_vortexing: 2h+ on the same symptom = dispatch codex with "trace, don't patch" brief BEFORE drafting any packet.

Threat-topology framing

L0 reviewer threat models scope to declared topology.

Every L0 packet declares its trust topology in §1 header. ce-security-lens-reviewer, ce-security-reviewer, and /codex challenge scope their threat model to that topology — they do NOT enforce multi-actor gates on single-actor surfaces.

TopologyExampleGates that DO apply
local-to-local single-user WP block → loopback Tauri runtime, single OS user Compile, crate boundaries, slug/path validation, indirect prompt injection (ADR-0093), sensitivity redaction in logs (ADR-0108)
local-to-local multi-user Shared workstation, multiple OS users Above + cross-user data isolation + permission gates
remote-to-local External MCP client → Tauri runtime Above + transport auth + scope-gated access + actor allowlists
remote-to-remote External service → external service Above + principal differentiation + cross-actor poisoning + full multi-actor threat model

Reviewers who flag multi-actor gates on a single-actor surface waste a cycle. Memory feedback_local_to_local_security_overreach_primary_concern: surface topology FIRST in every cross-surface architectural decision.

Knowledge Channel

Drift can't be prevented at the gate — it has to be prevented at authoring.

The Knowledge Channel K is a continuous feedback loop parallel to L0–L6 — not a rung. Findings flow out of L3 / L5 into the knowledge store, and back into L0 / L1 / L2 as substrate-grep obligations.

L3 composition + Suite firing rules

Suites S / P / E fire by need, not by default.

Most waves only need Suite E plus one other. Suite S and P fire only when wave AC names the concern.

S

Security

SQL injection on new write sites, cross-tenant exposure, PII / secrets in logs, immutability-allowlist bypass.

Owner ce-security-reviewer + ce-security-sentinel

Fires when wave AC names auth/permission/data-exposure OR Amendment 3 paths touched

P

Performance

Migration overhead, projection latency, backfill scale, hot-path budgets. Budgets locked at end of W1 baseline.

Owner ce-performance-oracle + benchmarks

Fires when wave AC names perf budget OR touches migrations / hot paths / projections

E

Edge cases

Property tests on invariants; fuzz on validators; adversarial bundle coverage.

Owner ce-testing-reviewer + harness

Fires when always (cheap; catches the long tail)

L6 escalation policy

When to pull James in, and when not to.

L6 is expensive — every escalation is a context-switch. The orchestration handles as much as possible downstream so L6 is reserved for genuine human-judgment calls.

MUST escalate

Objective triggers — agents do not get to skip these.

  1. Cycle cap exceeded (Amendment 1)
  2. Reviewer flags "needs human judgment" with a specific structural question
  3. L5 drift detected without remediation path (major versions only)
  4. Suite gate failure requiring regression acceptance or budget relaxation
  5. Reviewer infrastructure failure (codex outage after 3 retries)
  6. Net new scope expansion (NOT scope discovery within the agreed outcome)
  7. Contract amendment — plan needs fundamental change
MUST NOT escalate

Handle downstream. These are the orchestrator's remit.

  1. Routine review iteration within cycle cap — read findings, fix, resubmit
  2. Single flaky codex output — retry per Amendment 2
  3. Lint, type-check, test failures — fix them
  4. Reviewer dissent (1/3 or 2/3 against) — investigate the dissenter, don't break the tie
  5. Same finding class repeats twice — class-level sweep, file new tickets on the wave
  6. Scope discovery within DoD — create tickets, attach to wave, continue
  7. Choice between equivalent implementations — pick the more complete option
  8. "I don't know what to do" without a specific structural question
  9. Deferral requests — "park for v1.4.x" is not a valid escape valve
  10. Half-finished implementations — finish or escalate as net-new-scope
  11. Asking for context already in codebase, memory, or plan
  12. Tool choice when codebase has a convention

Pacing

No wave starts until the prior wave clears L3 and L5 (where applicable). No agent codes before L0 clears unanimously. Two revision cycles on the same plan or PR without convergence → L6 escalation.

Bounding

L2 reviews are bounded by acceptance criteria, enforced by the l2-bounded-reviewer orchestrator agent. Path-α findings (theoretical hardening beyond AC) file to the maintenance project, not cycle-N+1.

Wave

Wave is the project-management primitive for big version programs. Parallel agents fan out within a wave; hard ordering across waves. Smaller versions collapse to L0 → code → L2 → ship.
