## §0 — Origination & scope

- **Origination class:** Consolidation. The audit found the intelligence loop (signal → claim → producer → surface → feedback) is sound and stage 2 is verified-unified (all 28 claim-writer call sites converge on `commit_claim()`, `services/claims.rs:6323`), but stages 3–5 carry 2–3 competing implementations each. Every surface wave so far has tripped on this substrate (WR exists because W1/W3 did). WC collapses the duplicates **before** W4 builds the two biggest surfaces on them.
- **Scope tier:** Wave. Four streams: C0 enrichment split · C2 feedback unification · C3 context assembly · C4 signal-bus hygiene.
- **C1 dissolved at this L0 (decided with James 2026-06-10):** verification showed detail-surface compositions are **on-demand by design** (`get_projected_composition` → orchestrator → in-memory cache, `services/composition_render_orchestrator.rs:195-227`; persisted via `commit_composition`, `services/compositions.rs:67`) — there is no scheduled refresh to rewire and building one would be machinery for its own sake. `WorkerAbilityBridge` first wiring ships in W4 with the briefing/prep producers (W4 AC). Risk-briefing recast is **reports-track, way future** — not WC, not W4. DOS-855 moves to wave W4.
- **Trust topology:** local-to-local single-user. Amendment 3 paths touched: claim feedback substrate (C2), trust recompute semantics (C2 ADR amendment), signal propagation (C4). Second planning reviewer required (§7).
- **Review posture:** AC-scoped. Blockers are AC misses, ADR-named contract violations, or WC-introduced regressions. Theoretical hardening routes to Codebase Maintenance.
- **Proof obligation:** after WC, each touched loop stage has one substrate: a UI correction lands in `claim_feedback` and moves trust; enrichment writes claims only (reader-gated snapshot retirement); prep and intelligence read the same context helpers; every emitted signal has a consumer or an explicit audit-only classification; ADR-0123 matches verified trust semantics.

## §1 — Why WC exists

Three verified root causes from the audit (file:line evidence in the audit doc §1–2; architecture map carries the per-stage verdict):

1. **Stage 5 is split.** The canonical ADR-0123 `claim_feedback` path has **zero UI writers** (`commands/claim_feedback.rs:67` registered at `lib.rs:936`, no frontend caller); the app's thumbs/corrections (`useIntelligenceFeedback.ts:87`, `useIntelligenceCorrection.ts:113`) write legacy `entity_feedback_events` (`services/feedback.rs:309`) which trust recompute, salience, and surfacing never read. The user's daily corrections — the moat — bypass the trust substrate. Additionally `claim_feedback.applied_at` is inserted NULL and never marked (`services/claims.rs:7847`, `trust_recompute.rs:1108`): the ADR contract is silently unimplemented while the system actually converges by full per-subject recompute.
2. **Stages 2+3 are fused in enrichment.** `intel_queue` enrichment (`intel_queue.rs:723-780` → `services/intelligence.rs:1551-1802`) extracts claims (healthy — via `commit_claim()`) AND writes stage-3 output (`entity_intelligence` snapshots at `services/intelligence.rs:2070-2086`, LLM health narrative merge at `intel_queue.rs:2554-2571`) in the same pass. Producers must read claims, nothing else; surfaces must read producer output, not snapshots.
3. **Stage-3 inputs diverge.** 16 context builders; the two main account builders duplicate five fetches verbatim (`intelligence/prompts.rs:308-497` vs `prepare/meeting_context.rs:322-423`) and prep context omits email signals and synthesized stakeholders entirely — briefing surfaces can be blind to risk the intelligence layer already knows.
4. **(C4) Loop arrows leak.** Two signals emit with full propagation policies and zero consumers (`ClaimTrustChanged`, `trust_recompute.rs:1253-1268`; `meeting_prep_status_changed`, `meeting_prep_status/write.rs:241`); `google.rs:851` writes `prep_invalidation_queue` directly past the bus; envelope binding for claim feedback is validated differently per surface (`commands/claim_feedback.rs:108` vs `mcp_v2/handlers/tool_claim_feedback.rs:56-107`).

What is **not** broken (verified — guard, don't touch): the `commit_claim()` gate and its one-transaction corroborate/contradict/supersede tree (`claims.rs:6788-7080`), per-key commit locks (`claims.rs:6481`), PRE-GATE tombstones (`claims.rs:6602-6628`); the 31-mechanism background-execution inventory; delta+consolidated reliability pairs; `prep_context_json`/`prep_frozen_json` (ADR-0101); the `claim_receipt:invalidated` event bridge.

- **ADR-0120 Observability contract:** C4's consumer-or-reclassify rule for signals; removals are logged decisions, not silent deletions.
- **Verified substrate (audit + dedicated stage-2 pass):** `commit_claim()` unified gate; recommendations feedback ability (`services/recommendations/feedback.rs:27-78`) is the working model for mapping domain actions → ADR-0123 actions; claim-feedback propagation worker + outcome tables (`claim_feedback_propagation.rs`) already provide the consumption audit trail Decision B leans on.
- **Prior learnings (gstack):** `temporary_tauri_dev_commands_are_production_surface` (9/10) — any C2 compat wrapper left registered is production surface; remove or feature-gate, update the registry guard. `dashboard-prep-none-hardcoded` (9/10) — when C3 touches prep context assembly, verify fetched JSON is actually parsed into the payload, not reduced to a boolean.
- **Memory constraints:** "check substrate before authoring primitives" (all four streams consume existing primitives); "enumerate channels before patching trust boundaries" (C2 must inventory ALL feedback entry channels before rewiring — the audit's 12-system map is that inventory); "CI gate inputs are L1 deliverables" (C4's no-bypass lint and C2's registry-guard update ship in the same PR as the change).

No reinvented substrate: every stream collapses onto an existing, verified primitive.

## §3 — Binding decisions

### Decision A — Enrichment split is reader-gated, not big-bang (C0 · DOS-860)

Enrichment keeps extracting claims through `commit_claim()` (untouched, verified healthy). Its **stage-3 emissions retire field-by-field, gated on reader migration**: L1's first deliverable is a verified reader inventory of `entity_intelligence` snapshot fields. Known readers at L0: legacy recommendations UI (`RecommendedActions.tsx:72` → DOS-858, post-WC) and any briefing/meeting reads (retire at W4). Fields with zero live readers stop being written in WC; fields with live readers get a named kill date (DOS-858 or W4) recorded in the ticket — **no reader, no write; live reader, named kill date.** Manual `enrich_account`/`enrich_person`/`enrich_project` become stage-2 semantics ("refresh claims"), not content producers. The LLM-health-prose-as-ability migration (audit V4) is **reports-track, deferred** (Decision with James 2026-06-10: reports are way future); WC only stops snapshot writes per the reader gate. Deterministic health scorer untouched.

### Decision B — UI feedback rewires at the hook layer; ADR-0123 amended to event-sourced (C2 · DOS-856)

1. **Hook-level rewiring.** `useIntelligenceFeedback` / `useIntelligenceCorrection` write typed `claim_feedback` first (resolving a claim/subject target; legacy `confirmed/rejected/corrected/dismissed` map to ADR-0123 actions per the recommendations-feedback model), with `entity_feedback_events` retained as a compatibility projection. One change covers every consuming surface — including report pages that outlive W4 — regardless of retirement schedule.
2. **ADR-0123 amendment (decided with James 2026-06-10):** consumption semantics become **event-sourced**: trust full-recomputes per subject from all feedback rows (`trust_recompute.rs:1108` behavior is correct); `applied_at` marking is dropped from the contract (column retained, documented as unused-by-design or removed in a later migration wave); the propagation jobs/outcomes tables are the named audit trail. If trust ever goes incremental, the marker is rebuilt then.
3. **Write-kill on `intelligence_feedback`** (`db/intelligence_feedback.rs:112`); UNION-ALL read shim stays temporarily (drop tracked in DOS-864).
4. Any compat wrapper or superseded command touched here is removed or feature-gated per the production-surface learning; registry guard updated in the same PR.

### Decision C — One fetch per concept; blind spots closed; windows documented (C3 · DOS-861)

Shared `gather_account_*` helpers (actions, products/team, source refs, technical footprint) extracted; both builders consume, format per surface. Prep context gains **email signals and synthesized stakeholders** (lightweight top-K variant). The 30/90-day window split is **documented as an intentional recency-vs-depth contract** (decided with James 2026-06-10) — code-comment contract at both builders + one line in the architecture map; W4's prep producer re-decides with real requirements. Local-vs-Glean context-provider mode semantics documented, not changed.

### Decision D — Signals: consumer, audit-only, or gone (C4 · DOS-862)

Per orphaned signal, exactly one of: (a) register a real consumer (propagation rule / subscriber), (b) reclassify to audit-only (`ReadModelMaterialized`-style policy, documented), (c) delete the emission. `ClaimTrustChanged` and `meeting_prep_status_changed` get their disposition at L1 with evidence (what would consume them in the W4 world). `google.rs:851` stops writing `prep_invalidation_queue` directly — it emits through the signal path (`signals/invalidation.rs` already dedups). Envelope binding for claim feedback moves to **one shared service function** called by both the Tauri command and the MCP v2 handler. Derived-state subscriber registry: populate with a real emitter or remove (`signals/derived_state_subscribers.rs:21-65`). A lint/test asserts no direct `prep_invalidation_queue` writes outside the signal path — shipped in the same PR (CI-gate-inputs rule).

### Decision E — Three lanes, one PR per lane, A before W4-dependent merges

| Lane | Streams | Modules | Ordering |
|---|---|---|---|
| A | C0 → C3 | `intel_queue.rs`, `services/intelligence.rs`, `intelligence/prompts.rs`, `prepare/meeting_context.rs` | sequential (shared intelligence module) |
| B | C2 (+ C4 envelope unification) | frontend hooks, `services/claims.rs`/`claim_receipt`, `commands/claim_feedback.rs`, `mcp_v2/handlers/tool_claim_feedback.rs`, ADR-0123 doc | sequential within lane (shared feedback surface) |
| C | C4 signals (orphans, google bypass, subscriber registry, lint) | `signals/`, `google.rs`, `services/trust_recompute.rs` emission site | independent |

Lanes launch in parallel (worktree isolation); B's envelope work and C's signal work both touch nothing in A. Conflict flag: C0 and C2 both read `services/claims.rs` — C0 does not modify it (claim writes untouched), so no real conflict. L2 per lane PR; wave-level L3 on the integrated diff.
