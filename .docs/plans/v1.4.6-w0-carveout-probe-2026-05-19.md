## Authority question for James

The reorientation doc says (§"v1.4.4 — WordPress Surface Migration" > "Wave structure"):

> **W0 — Surface audit (gate)** — DOS-677. Active / carry-forward / inactive / open-questions lists from `src/router.tsx` + `.docs/design/INVENTORY.md` + nav reachability + James's call. **Gates W1+ start.**

Strict reading: W1-RECEIPT can't start until W0 closes. But C2 (§"Execution constraints") says:

> Substrate-only work below the surface tier (in v1.4.5+ projects) is independent and can run in parallel as planned.

Does C2's "substrate-only" carve-out extend to v1.4.4 W1 sub-lanes whose substrate is already L0-converged in the archived Claim Experience plan and whose scope is independent of W0 surface audit findings?

**Recommended answer: yes**, on the following reasoning:
1. ClaimReceipt + claim_review_queue substrate scope was frozen 2026-05-09 in the L0 Contract Addendum, before W0 surface audit was conceived. The audit cannot reshape this substrate; it can only inform which surfaces consume it.
2. The W0 audit's purpose is to scope **surfaces** (active/carry-forward/inactive lists). ClaimReceipt is consumer-agnostic by design (route-neutral DTO).
3. v1.4.6 Salience consumes ClaimReceipt with `target.kind = Recommendation` extension — this is the same pattern as DOS-336 (`target.kind = Candidate`), itself an extension hook designed into the original W3-E scope.
4. Blocking v1.4.6 substrate on the W0 surface audit creates a 2-3 week serial gate for substrate work that has no surface dependency.

**Risk of the carve-out:** if the W0 audit surfaces a new substrate gap that conflicts with ClaimReceipt shape (very unlikely given the route-neutral design), the v1.4.4 W1-RECEIPT lane would need re-work. Mitigation: keep `ClaimReceipt` shape exactly as L0 Addendum pinned; defer all extension hooks to typed `target.kind` variants.
