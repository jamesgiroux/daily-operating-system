The loop as it actually is.

Five stages — signal → claim → producer → surface → feedback — mapped against what the code does today, not what the docs aspire to. Every cell carries file:line evidence.

Cross-check · 2026-06-10

Does the WC wave match this architecture? Mostly — three corrections from reality.

✅ Confirmed: WC targets the right stages

WC's five items map onto exactly the red cells: C0/C1 → stage 3's dual engines, C2 → stage 5's split, C3 → stage-3 inputs, C4 → stage-1 hygiene. Nothing in WC touches stage 2 — correct, because stage 2 is verified healthy. The audit's worry that claim creation might also be fragmented was disproven by the dedicated verification pass.

✏️ Correction 1 — DOS-860 framing narrowed

Earlier framing implied enrichment's claim-writing was part of the problem. Verified: enrichment's claim writes go through commit_claim() correctly. The fusion problem is only that the same pass also emits stage-3 output (entity_intelligence snapshots, LLM health prose). C0's split is therefore smaller than it sounded: keep the extraction + claim-write path as-is; remove the snapshot/prose emission from it. Ticket updated.

✏️ Correction 2 — 4 Composition producers, not 1

The Abilities Explainer ("only account_overview emits a Composition") is stale: project_overview, person_overview, action_detail shipped with W3 and are registered. C1's first tranche (scheduled refresh via WorkerAbilityBridge) covers four shipped producers. The roster is ~29 registered abilities via #[ability], not "about two dozen."

✏️ Correction 3 — the Explainer described the goal as the present

Three Explainer claims are aspiration, not description: "abilities are the single source of truth" (scheduled production bypasses them); "feedback routes back through an ability" (zero UI writers on the canonical path); the §5 worked example credits get_entity_intelligence with claim creation (it's a read ability; legacy enrichment writes the claims). The Explainer now carries a reality-check note pointing here. After WC + W4, those sentences become true — that's a usable definition of done for the consolidation.

Verified healthy · do not "fix"

What the audit confirmed is right — guard it.

  • Stage 2 claim gate — commit_claim() with per-dedup-key commit locks (claims.rs:6481), one-transaction corroboration/contradiction, PRE-GATE tombstone blocking (claims.rs:6602-6628), reconciliation kinds (claims.rs:10255-10290), and a lint preventing bypass writes. Any future ingestion source must feed this gate, never write claims directly.
  • Background execution inventory — 31 mechanisms, all intentionally spawned from lib.rs; startup-drain + continuous-worker pairs are deliberate.
  • Delta + consolidated reliability table pairs; prep_context_json vs prep_frozen_json (ADR-0101 read-model/export split).
  • claim_receipt:invalidated event bridge (event_bridge.rs:71 → useClaimReceiptSubscription.ts:194) — the reference pattern for backend→frontend event wiring.
  • Frontend invoke hygiene — all 143 frontend invoke() calls map to registered commands.
