DailyOS · Maintenance · Performance Cleanup

Make the app faster by removing duplicate work, not by adding new product surface.

A separate branch and maintenance-plan track for SRP, DRY, render-time, and response-time cleanup on top of dev.

This plan is deliberately not v1.4.9 and not v1.5.0. It starts from dev on codex/performance-srp-dry-audit, files maintenance issues, and sequences cleanup that reduces duplicate paths and avoidable work without shipping net-new features. Anything owned by v1.4.9 - DB ownership, MCP auth/parity, claims-to-files, correction loop, trust parity, or transcript substrate - is dependency, measurement, or exclusion.

Boundary

The performance branch must not step on v1.4.9 or v1.5.0.

v1.4.9 is the active substrate reset and judgment maturation plan. This cleanup track can measure and document adjacent problems, but it does not implement the same ownership, correction, MCP, projection, or Composition-renderer changes in parallel.

Audit baseline

The codebase is large enough that cleanup needs routing, not taste.

The read-only pass counted roughly 571k runtime Rust/TypeScript lines under src and src-tauri, and roughly 1.1M tracked lines across runtime, scripts, docs, and archives. The largest runtime files include services/claims.rs, services/intelligence.rs, surface_runtime/mod.rs, workflow/deliver.rs, and MeetingDetailPage.tsx.

Signal Finding Route
Clone scan jscpd --min-tokens 80 reported 216 clones and 4,301 duplicated lines in runtime-heavy clusters. Use as W0 evidence; do not chase generated/archive duplicates.
Frontend render work Heavy pages build hidden tabs and repeated selectors; report lifecycle duplication exists but is already deferred to v1.4.15. W1/W2 safe implementation for non-report surfaces; reports use the default-off guard and entrypoint-removal model.
Backend read/query work Dashboard, email, list, proactive-suggestion, and entity-edit paths need telemetry before code changes. DOS-845, blocked by v1.4.9 W1.
Substrate size Claims and intelligence services are legitimate split candidates, but active v1.4.9 W3/W4 work owns those contracts. Post-v1.4.9 planning only.

Proof baseline

No wave can claim speed without a before/after artifact.

W0 creates one proof bundle per implementation issue under .docs/proof/performance-srp-dry/<issue>/ before code changes start. A wave is blocked until the bundle names fixture data, exact commands, scenario steps, raw before metrics, and the pass/fail thresholds below.

Metric Required baseline Pass rule
Frontend render work React Profiler export for account detail tab switch, daily briefing load, accounts hierarchy expand, email list/detail render, and MeetingDetail transcript/action render. Claimed render cleanup must remove at least 20% of avoidable renders for the named interaction, or the PR must be framed as code reduction only. No affected interaction may regress p95 commit time by more than 5%.
Response time Three cold and five warm runs recording p50/p95/p99 for the affected route or Tauri command, with the database/profile fixture named in the bundle. Claimed response-time improvement requires at least 10% p95 reduction and no p99 regression greater than 5%. Otherwise the issue remains measurement/routing.
Query and command count Before count of Tauri invokes, report commands, and DB read/write queries for the scenario, captured from logs or instrumentation named in the bundle. No new writes, hidden UI paths make no report command calls, direct report invokes return disabled before reads/writes/generation, query count is less than or equal to baseline, and each claimed duplicate path identifies the specific removed call/query.
Repeatability The bundle includes the command sequence used, including pnpm dev, browser/profile steps or test command, and pnpm tsc --noEmit. A reviewer can rerun the command sequence against the same fixture and reproduce the direction of change.

Wave shape

Five waves: audit first, then safe cleanup, then post-W1 response-time work.

The waves are ordered by collision risk. Frontend render-time cleanup and behavior-preserving helper extraction can proceed first only where it survives v1.5.0. DB-adjacent response-time work remains measurement-only until v1.4.9 W1a and telemetry are complete and an owning-wave handoff exists.

Report boundary

Reports are deferred; do not polish the current report stack.

Linear already routes reports to v1.4.15 - Reports as Shareable Intelligence. The maintenance finding is not "extract the current report lifecycle hook now"; DOS-96 already tracks that as deferred work if the current UI survives. The near-term cleanup is to make reports default-off at the route boundary.

DOS-839 uses one model: introduce or reuse a real default-false reports_enabled feature flag enforced before report pages, hooks, Tauri report commands, scheduled report generation, or report service write work run. The guard removes report entry points from normal chrome and redirects direct report URLs with replace; direct command invokes return a disabled-feature result before DB write work. It does not add a new disabled-report page or new explanatory copy.

Intelligence loop

Cleanup is not allowed to make display-only intelligence.

This plan adds no tables, claim fields, or user-visible intelligence features. If an implementation touches trust, provenance, claim lifecycle, signal invalidation, ability runtime, or feedback behavior, it stops and moves to the v1.4.9 owner. Frontend presentation-helper extraction may preserve existing rendered trust data; it may not recompute trust, salience, or provenance in the display layer.

Question Answer for this plan
Claim model No new claims, claim fields, tables, or claim producers.
Provenance + trust Do not change trust scoring or trust-band rendering contracts; trust UI consolidation is deferred to v1.4.9 W4/W5.
Signals + invalidation No signal semantics change. Health/invalidation overlap remains measurement-only for v1.4.9 W4.
Runtime + surfaces Tauri React cleanup preserves existing commands and ability outputs. MCP parity work is excluded.
Feedback loop No correction, dismissal, contradiction, source-reliability, or feedback writer changes.

Surface preservation

Lazy work must preserve the interaction contract users already have.

W1 and W2 are cleanup waves, not redesign waves. Each implementation issue must prove the states below still behave the same on desktop, tablet, and mobile widths before L2 can pass.

Surface States that must be preserved Accessibility / route checks
Account detail tabs Initial load, active tab selection, inactive tab lazy render, empty tab, error/not-found account, partial data, and browser back/forward tab state. Keyboard tab switching still works, focus lands on the selected tab panel, and no hidden inactive-tab controls enter the tab order.
Accounts hierarchy list Collapsed root list, expanded children, loading children, empty child set, fetch error, retry, and previously expanded account state. Expansion remains keyboard reachable, announces loading/error state, and does not shift layout across mobile/tablet/desktop checks.
Daily briefing and email surfaces Loading, empty, partial data, existing ranking order produced by the current canonical source, email meta display, trust badge display, action links, and error fallback. Shared helpers must not change reading order, labels, or screen-reader text for ranked items and metadata.
MeetingDetail Transcript loading/empty/error, existing action state from the current owner, notes/agenda sections, partial transcript data, and unchanged command wiring. Reusable helpers preserve focus after section changes and do not introduce new surface chrome or Composition renderer behavior.
Reports default-off Hidden nav, direct account report URL redirect, direct personal report URL redirect, browser history replacement, and no report page mount. Redirect target receives focus, no disabled report control is focusable, and tests prove disabled routes, commands, and scheduler paths exit before reads/writes/generation.

Test suites

Performance cleanup needs proof beyond compiling.

S

Scope

Static check in review: no DB ownership, MCP auth/parity, claim correction, projection, trust parity, transcript substrate, or v1.5.0 Composition edits unless the owning wave records the handoff artifact defined above.

Owner ce-scope-guardian-reviewer

Pass zero v1.4.9/v1.5.0 collisions or a named handoff artifact

P

Performance

Profiler/render-count or query-count evidence for every claimed response-time improvement; baseline p50/p95/p99, render count, and query count are captured before implementation.

Owner ce-performance-reviewer

Pass 10% p95 improvement for speed claims, no p99 regression over 5%, and named duplicate work removed

E

Equivalence

Behavior-preserving cleanup requires snapshot, golden, hook, or selector tests proving existing output and interactions still hold.

Owner ce-testing-reviewer

Pass unchanged visible behavior

A

Access

L4 is mandatory for W1 and W2. Keyboard, focus, screen-reader, redirect, and mobile/tablet checks are required for every visible or route-level change.

Owner /qa-only plus accessibility reviewer when user-facing behavior changes

Pass no focus traps, no focusable hidden report controls, and no responsive overlap

No net-new features

Each issue is cleanup, measurement, or behavior-preserving extraction. New UI, new abilities, or new schema means the task is misrouted.

Stop on same-shape drift

If two review cycles find the same duplicate-path shape inside the approved issue boundary, sweep that approved class and add a guard rather than patching a third local offender. New modules, substrate owners, report paths, MCP paths, DB paths, or v1.5.0 surfaces require a new L0 or owner handoff first.

K-in stays live

Every wave cites docs/solutions/ and .docs/decisions/. Reinventing DB throughput, claim, or ability substrate is a blocking finding.
