## Framing

The Library ("The Library" §, v2.0-surface-vision.md) requires full-text + semantic retrieval over generated documents AND meeting transcripts — a scope that is not served by the existing entity-name index. Two retrieval systems already exist in-tree:

1. **FTS5 entity index** (`migrations/065_search_fts5.sql`, `db/search.rs:1`): `search_index` virtual table, columns `name` + `secondary_text` only. Entity-scoped: accounts, projects, people, meetings, actions, emails. No document body, no transcript body, no snippet/highlight. Rebuilt wholesale via `rebuild_search_index` (`db/search.rs:59`), called from `commands/app_support.rs:1450`. No sensitivity partitioning.

2. **ADR-0074/0078 fastembed vector stack** (`src/embeddings.rs`, `src/queries/search.rs`, `migrations/006_content_embeddings.sql`): nomic-embed-text-v1.5 768-dim via fastembed, `content_embeddings` table keyed to `content_index`, 500-token chunks, BM25 in-process (`queries/search.rs:117`), cosine hybrid 70/30. Used for `search_entity_content` (enrichment context) and claim canonicalization (ADR-0131). No sensitivity-tier gate at the query boundary. `EmbeddingModel::embed_batch` (`embeddings.rs:167`).

ADR-0130 amendment (2026-05-10, `decisions/0130-surface-independent-composition-contract.md:108`): "Composition-producing abilities MUST NOT reinvent retrieval. They consume the substrate's embed-model-backed search; the substrate owns the relevance question."

Neither system today touches document bodies or raw transcript text. Both have zero snippet/highlight support. **Dual-running two search engines is the 11-dual-systems anti-pattern this v2.0 program exists to kill** (v2.0-surface-vision.md §"The Library").

## Three Options

### Option A — Extend FTS5 to Document and Transcript Bodies

**What changes:**
- Alter or supersede `search_index` with a second FTS5 virtual table (call it `library_fts`) covering document body text and transcript body text, alongside the existing entity-name columns.
- `rebuild_search_index` (`db/search.rs:59`) either becomes a dual-table rebuild or is replaced by a per-document incremental upsert trigger.
- FTS5 `highlight()` and `snippet()` functions are available natively; snippet rendering is straightforward SQL.

**Sensitivity partitioning:**
- Transcript bodies are raw sensitive text; ADR-0125 classifies meeting-sourced content as `Internal` at minimum, with `Confidential` paths for personal notes (`decisions/0125-claim-anatomy-temporal-sensitivity-typeregistry.md:60-78`). FTS5 does not enforce sensitivity tiers; the gate must be applied in the calling Rust layer before results are returned. Snippet leakage is the specific risk: `snippet()` returns verbatim raw text fragments. Any snippet surface over transcripts requires the sensitivity gate to fire on the query side, not the FTS row side. A row-level filter on sensitivity before snippet extraction is required, not advisory.
- No sensitivity column currently exists on `search_index`; adding one requires schema migration and discipline at every insert path.

**`search_index` fate:** Consumed — single FTS5 table replaces both the entity index and the document body index. Entity rows move into the unified table under an `entity_type` discriminator column.

**Effort:** Low schema lift (1 migration, extend existing pattern). Snippet support is free from FTS5. Sensitivity gate is a discipline problem, not a capability gap. Reindex is synchronous at document write time; no background processor.

**Gaps:**
- FTS5 BM25 is SQLite-internal, not tunable; phrase proximity and field boosting are limited.
- Semantic (intent/paraphrase) queries are not covered. "What did Q1 customer calls ask for?" is a semantic question that exact-token BM25 cannot answer reliably.
- Scalability: FTS5 full-table rebuild on large transcript corpora is a write-lock event.
- Does not consume the ADR-0074/0078 vector stack for Library retrieval, so semantic intent queries remain unserved (a gap the vision doc names explicitly).

---

### Option B — Adopt tantivy as the Document Index; Supersede `search_index`

**What changes:**
- Add `tantivy` crate (Rust, no service, embedded); define a Library index schema with fields: `doc_id`, `doc_type` (document | transcript | entity), `body`, `title`, `sensitivity_tier`, `subject_id`.
- `search_index` is superseded; `rebuild_search_index` is deleted; `search_global` command is re-implemented against tantivy.
- tantivy writes to a separate on-disk index directory (e.g., `~/.dailyos/search-index/`); index survives app restart without rebuild.

**Sensitivity partitioning:**
- `sensitivity_tier` is a stored, non-tokenized field on every tantivy document. Queries filter on `sensitivity_tier NOT IN [Confidential, UserOnly]` before snippet extraction. This is a structural gate, not a discipline convention — wrong-tier results cannot appear because the filter is in the query plan, not the presentation layer. Transcript rows are indexed with body text but `sensitivity_tier = Confidential`; they are excluded from any surface that does not have an explicit sensitivity grant. Snippet extraction runs after filter; no verbatim fragment of a confidential document leaks via the result payload.
- Purge path: tantivy supports per-document deletion by doc address; transcript deletion triggers an indexed document deletion, not a full rebuild.

**`search_index` fate:** Superseded. Migration adds a schema version marker; `search_index` table is dropped. No dual-running period — tantivy handles both entity-name and document-body queries from day one.

**Snippet/highlight:** tantivy's `Snippet` API provides highlighted term fragments natively; field-level highlight is available.

**Effort:** Medium. tantivy is not currently a dependency (`Cargo.toml` — not present). Build integration, index schema design, migration path, background index writer, and persistence across updates all require new Rust infrastructure (~300-500 LOC net). v2.0-surface-vision.md platform table already names tantivy as the chosen answer ("Search over the Library: **tantivy** (Rust crate, no service)").

**Gaps:**
- Semantic/intent queries still require the ADR-0074 vector stack if Option B is pure lexical. The platform table names tantivy without naming hybrid — this is ambiguous and must be resolved at L0.
- tantivy index is a parallel persistence store alongside SQLite; purge/lifecycle must be kept in sync with the DB (e.g., meeting deletion must drive tantivy document deletion or the index drifts).
- Model: not the same as Option C below — tantivy would be the lexical engine; semantic would require explicit integration on top.

---

### Option C — Hybrid: ADR-0074 Vector Retrieval + ONE Lexical Engine

**What changes:**
- The ADR-0074/0078 vector stack (`content_embeddings`, `search_entity_content`) is extended to cover Library documents and transcript chunks — same chunking strategy (500 tokens, 80-token overlap per ADR-0074), same nomic model, same `EmbeddingProcessor`.
- ONE lexical engine handles exact-token queries: either FTS5 (Option A path) or tantivy (Option B path). Not both.
- `search_global` becomes a hybrid result merger: semantic results from `search_entity_content` + lexical results from the single engine, scored and merged (same 70/30 pattern already implemented in `queries/search.rs:65-113`).
- `search_index` fate depends on which lexical engine is chosen: if FTS5, it is consumed into a unified `library_fts`; if tantivy, it is superseded.

**Sensitivity partitioning:**
- Vector stack: `content_embeddings` FK to `content_index`; sensitivity gate must be added to `content_index` (column) and enforced at `search_entity_content` query boundary. Today it is absent (`queries/search.rs` — no sensitivity filter). Chunk retrieval could return raw transcript chunk text in `ContentMatch.chunk_text` (`queries/search.rs:16`) without a sensitivity gate.
- Lexical side: same gate as whichever engine is chosen (A or B above).
- The critical invariant: `ContentMatch.chunk_text` must never be returned to a surface for chunks whose source document is `Confidential` or `UserOnly` unless the surface holds an explicit sensitivity grant. This is an addition to the current query API, not a re-architecture.
- Purge: embedding deletion cascades via FK (`content_embeddings.content_file_id REFERENCES content_index(id) ON DELETE CASCADE` per migration 006). Transcript deletion drives `content_index` deletion which cascades. This path already works for file-based content; extension to Library documents needs the same FK chain.

**Effort:** Medium-high. The vector stack already runs and already implements BM25 in-process (`queries/search.rs:117`). Extending it to Library documents and transcripts is incremental on the embedding side. The lexical engine choice (FTS5 or tantivy) determines the remaining cost. If FTS5: low additional lift. If tantivy: medium lift. The integration layer (hybrid merger for Library search) is ~100-150 LOC on top of the existing pattern.

**ADR-0130 alignment:** This option most directly honors the amendment language. The substrate already owns retrieval; Option C extends it to Library scope without reinvention. It pays the embedding cost once (already paid) and uses it for canonicalization, enrichment, and Library search.

## Recommendation

**Option C — Hybrid, with FTS5 as the lexical engine.** The ADR-0074/0078 vector stack is already operational, already chunking content files, and already used in canonicalization and enrichment. Extending it to Library documents and transcripts is incremental. FTS5 handles exact/prefix/phrase queries; the 70/30 hybrid merger is already implemented in `queries/search.rs`. This avoids a new Cargo dependency while fully covering semantic intent queries ("what did Q1 customer calls ask for?") that pure lexical cannot reach.

The v2.0-surface-vision.md platform table names tantivy specifically. That name should be the first question the panel settles — if James's intent is tantivy-as-lexical-layer alongside the vector stack (i.e., Option C with tantivy replacing FTS5), Option C still applies; the ADR-0130 alignment does not change. If the intent is tantivy-only-lexical (Option B, no semantic), the platform table is underspecified and the panel must adjudicate.

Either way, Option A alone is a dead end: it cannot serve semantic Library queries and leaves the ADR-0074 vector stack as a parallel retrieval system with no Library integration — the dual-system outcome the program exists to kill.

## Three Questions the L0 Panel Must Settle

1. **tantivy or FTS5 as the lexical layer?** The platform table names tantivy, but tantivy adds a new Cargo dependency and a second persistence store. If the answer is FTS5-as-lexical + ADR-0074 vector (Option C, FTS5 variant), confirm that is intentional and close the platform table ambiguity in the ADR. If the answer is tantivy, confirm whether the intent is pure-tantivy (Option B) or tantivy-as-lexical in a hybrid (Option C, tantivy variant).

2. **How is transcript sensitivity enforced at the search boundary?** `content_embeddings` currently returns `chunk_text` verbatim with no sensitivity gate (`queries/search.rs:95-100`; `content_index` has no sensitivity column). The panel must name the gate mechanism — a required `sensitivity_tier` column on `content_index` enforced at `search_entity_content` query entry is the structural answer. This is a schema addition; its migration slot must be reserved in the W0 slot block.

3. **Document persistence substrate first or search substrate first?** The Library requires persisted document run records before Library-level search makes sense (you can't index documents that aren't stored). The v2.0-surface-vision.md §Document names document-persistence as a named separately-priced W0 L0. If persistence is not resolved before the search substrate L0, the query scope for Options A/C (what are we indexing?) is undefined. Confirm ordering: persistence L0 gates this search L0, or both are co-settled in W0.
