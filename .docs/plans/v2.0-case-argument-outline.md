# v2.0 case — argument outline (James gate, pre-HTML)

**Date:** 2026-06-11 · **Status:** outline for sign-off; the Tier 1 HTML case doc follows this structure once approved.
**Inputs:** product corpus, full ADR arc, docs/solutions corpus, `.docs/plans/v2.0-shell-audit.md` (key numbers re-verified first-hand), the 2026-05-29 examination + adjudication, greenfield landscape research (mid-2026 frameworks/paradigms), DOS-866 packet. The rejected boundary draft folds in as one section of §5.

**Thesis.** DailyOS v2.0 rearchitects everything between the store and the user's eyes — the surface taxonomy AND the read path — because the category (personal intelligence: memory + judgment) means context only ever grows, and the current shell's cost is proportional to accumulated context. The substrate crosses intact; an unconstrained greenfield exercise independently re-derives it.

## §1 — The category demands a different shell
Memory that compounds is the product premise; therefore context growth is not an edge case, it is the success condition. A shell serving this category must: render trust uniformly, be consumption-first, push proactively, and have **performance independent of accumulated context**. The current shell is a 26-route mission control where 21 of 25 surfaces hand-assemble meaning via 1–28 imperative invokes each — the frontend is the operator, the exact failure MISSION.md attributes to the status quo. (Audit §1/§4.)

## §2 — The journey earned this conviction
19 weeks (first commit 2026-01-29), 2,570 commits, 140 ADRs. The asymmetry is the evidence: **zero substrate ADRs superseded; the shell superseded itself repeatedly** (dashboard layout 0053→0055→0077 in six days; 0034 deprecated; readiness enums invalidated in ten days). The solutions corpus: **0 of 31 entries are substrate-internal failures**; the recurring classes are shell/data-path (eight write-path interventions in fourteen weeks per ADR-0133, dual-system drift, the 874-LOC parity layer that exists to police duplication). Three generations of entity detail, gen-2 still in tree; 45 pages created → 24 remain; 27 orphan components; 11 dual systems. The substrate crystallized while the shell kept searching for its form. Learned → failed → learned: each shell patch was rational locally; the accumulation is the lesson.

## §3 — The scaling thesis (core)
Measured chain, all re-verified at `0262d6bb` / replica DB:
- Worst subject carries **2,143 claims** (1,874 active) — the prompt's "693" was understated 3×. ~311k signal_events ≈ 60% of the 397MB DB (43 events/claim).
- Enrichment cost is **O(accumulated claims), not O(new information)**: trust recompute loads all active claims per subject per touch; persist re-merges the full legacy snapshot; parent cascades multiply it.
- All writes funnel through one gate fed by ~16 background producers; an enrichment persist holds it for the whole transaction (DOS-866's starvation class).
- The read path is OLAP-shaped queries against the OLTP store under that write load: account detail = ~10 IPC round trips + a 30-query backend assembly; the composition path **commits to the DB on page load** (`account_overview.rs:148-152`) after an **unbounded depth-3 claim read**.
- Result: 8.8s on a routine click at 20 entities (precise mechanism per the lock-storm doc: WAL bloat starving the reader pool + combined-domain transaction shape).

Framing: this is a **read/write architecture failure (a CQRS violation), not a SQLite bug**. Eight interventions in fourteen weeks each governed *who may write when*; none separated the read workload from the write workload. DOS-866, 693/2,143-claim subjects, commit-on-load, enrichment grind — symptoms of one missing layer: materialized read models the UI subscribes to.

## §4 — The greenfield test (unconstrained, per James 2026-06-11)
Method: "if we built this today, from the mid-2026 toolscape, no constraints" — researched shells, data layers, AI-native UX paradigms, agent runtimes. Four convergences, one divergence:
1. **Declarative typed-component dispatch won.** A2UI (Google, production in Gemini/Opal), AG-UI protocol, MCP Apps — the industry standardized on "agent names a component from a typed registry; client renders." That is ADR-0130 composition. We built the winning pattern before the specs existed. → validates KEEP.
2. **Memory commoditized; judgment didn't.** The 2026 memory-stack consensus (vector+BM25+entity fusion) is table stakes; staleness, salience, provenance, trust bands are the *named unsolved problems* in the field's own state-of reports. Exactly our claims/trust substrate. → moat externally confirmed; KEEP.
3. **Post-chat, push-first experience.** Google's Daily Brief, Siri AI's briefing surface, ambient copilots shipping 4× chat-first with 3× engagement; ChatGPT Pulse attempted and paused. The paradigm: briefing as front door, structured entity surfaces as drill-down, chat as escape hatch. Our 26-route taxonomy is the wrong paradigm. → demands REBUILD.
4. **Event-sourced/CQRS local data layers.** LiveStore, TanStack DB 0.6, DuckDB-over-SQLite: background pipeline appends; materialized projections serve reads; UI *subscribes* instead of fetching. The senior-architect read of our 8.8s: a missing materialized read layer. → demands REBUILD of the read path — the piece the rejected boundary draft missed.
5. **Divergence check (what greenfield does NOT say):** it does not say leave Tauri 2 / Rust / React / SQLite — both viable 2026 stacks keep them; SQLite single-writer is to be designed around, not escaped. The platform survives unconstrained scrutiny. The read path and surface taxonomy do not. (Also banked as a v2.x lever, not v2.0 scope: on-device enrichment tiering — Apple Foundation Models for classification/extraction, frontier calls for synthesis only.)

The greenfield exercise lands where the journey landed: keep everything below `services/`; rebuild everything between the store and the eyes. Earned conviction, independently derivable.

## §5 — What v2.0 is
**Boundary** (the rejected draft's keep/kill matrices fold in here, now justified by §1–4): substrate crosses — abilities runtime, claims+services, composition model, DB hardening incl. DOS-866, design system, ADR/learnings corpus; app stays the control plane (packaging + push, per the 2026-05-29 adjudication). Shell and read path are born new.

**Three architecture commitments:**
- **A. Briefing-first surface taxonomy.** D-spine briefing as front door (±7-day window), entity surfaces as drill-down, deliberately small page inventory, chat-as-escape-hatch decision explicit. Lists/triage redesigned as consumption surfaces, not database operators.
- **B. Blocks-native rendering as the *only* rendering system.** One display grammar, one feedback path into claim state, salience-driven layout. **Deletion is an acceptance criterion** — the measured precedent (two prior generations left in tree) is the named failure mode.
- **C. CQRS read models.** UI subscribes to materialized projections; no unbounded claim reads, no commits on page load; enrichment persists in capped, phased batches (DOS-866 shape). Build-vs-adopt (owned projection layer on current stack vs LiveStore-class framework) is an L0 decision; the *separation* is the commitment.

## §6 — Costs and risks, measured
~10–15 engineer-weeks of migration surface (audit §6, calibrated against actuals); three block-type families don't exist yet (list, triage/action-dispatch, report); graveyard pattern and parity-trap are documented organizational habits with named mitigations (route-by-route swap is already proven; deletion as AC). Meta-warning honored: this case rests on the scaling chain and the journey's asymmetry, not on last week's incidents — and the moat-validation instrumentation from the examination's product-lens finding rides along (prove the judgment layer is *felt*).
