DailyOS · Abilities Runtime · Wave Plan

Make entity intelligence genuinely substrate-fed.

Close the producer gaps that make MCP and WordPress see less than DailyOS already knows.

This plan turns the producer audit into a full remediation program, not a one-off account-status patch. The goal is to preserve `get_entity_intelligence` as the generic runtime envelope while adding the missing entity-neighborhood readers, producers, MCP projections, trust caveats, and eval gates that let headless surfaces answer real executive-briefing prompts from the claim-backed substrate.

Target: next v1.4.7 remediation train Waves: 5 Parallel agents: 3 peak Status: L0 cycle 1 remediated

Source and scope

The first slice is not the finish line.

The remediation scope is the full producer audit, sequenced so the comparison prompt becomes testable early without losing the rest of the runtime work.

  • Origination: debug-driven extension. The visible symptom is that headless surfaces can identify an entity but cannot compose a complete executive briefing from DailyOS evidence.
  • Scope tier: wave. This touches the ability runtime contract, MCP projection, claim provenance, trust, and production backfill behavior.
  • Threat topology: local-to-local single-user. MCP runs locally under the user's OS/keychain boundary; sensitivity render policy, source hygiene, prompt-injection defenses, and log redaction still apply.
  • Failure trace: dailyos.read.account_status calls get_entity_intelligence for facts/open loops/touchpoints/record, but the handler returns only part of that envelope; the runtime also lacks neighborhood, participation, threads, metadata, and section-caveat producers.
  • Origin audit: .docs/plans/abilities-runtime-producer-audit-2026-05-23.md
  • K-in: ADR-0102, ADR-0128, ADR-0057, ADR-0081, ADR-0088, ADR-0097, ADR-0098, ADR-0093, ADR-0108, ADR-0110, ADR-0111, plus the claim-producer trust audit solution note.
  • Non-goal: do not teach MCP or WordPress to bypass the runtime by reading account-shaped schema fields directly.
  • Architecture constraint: every durable assertion enters the claim substrate with provenance, temporal scope, sensitivity, lifecycle, and trust recomputation.

W2A audit expansion

Inventory evidence that exists but loses meaning before runtime.

The comparison prompt should fail if durable working-state evidence exists in services-owned tables but does not reach get_entity_intelligence with its semantics intact.

  • Account facts: sourced structured fields must promote to claim-backed facts before MCP or WordPress use them.
  • Core entity facts: account, project, person, and future entity scalar fields need a generic sourced-field producer; runtime freshness must degrade from source dates or observation dates instead of rendering as unknown.
  • Stakeholder roles: account-team, owner, relationship-manager, champion, executive-sponsor, and technical-contact semantics must survive generic neighborhood projection instead of collapsing to anonymous stakeholder links.
  • Actions and commitments: local work rows must either surface as bounded internal open-loop evidence or become first-class claims with provenance, source confidence, owner refs, and freshness; they may not disappear from MCP while remaining visible in Tauri.
  • Meetings and transcripts: current linked-entity graph, attendees, captures, transcripts, and summaries need runtime readers/producers; legacy junctions and generated files are fallbacks or artifacts, not authority.
  • Email and content signals: enrichment output that changes account/person/project judgment must be classified as durable producer, read-model producer, or downstream artifact before it ships.
  • Feedback and suppression: tombstones, dismissed links, claim deferrals, and user corrections must affect read-model evidence as consistently as claim-backed facts.

Wave details

Acceptance criteria by wave.

W0 — Contract hardening

Split Linear follow-ups from the audit, assign migration slots if needed, freeze fixture names, and define the producer contract for AI prompt outputs, neighborhood edges, participation rows, section caveats, trust recomputation, and MCP projections.

Pass: L0 approves the wave plan; fixtures avoid customer-specific data; every Glean/local PTY prompt path is classified as durable producer, read-model producer, or downstream report; every producer has a services-owned boundary; every MCP field has render-policy coverage; every durable claim writer names its same-wave trust recomputation path.

W1 — Entity neighborhood

Add a generic read model for hierarchy, explicit entity links, meetings, attendees, people, actions, email threads, and content relationships over existing substrate tables. Add participation summary composition without account-only joins, new canonical graph storage, or MCP schema bypasses. Consolidate queue and manual Glean finalization so the same Glean output runs the same claim, signal, fact-promotion, trust, and export steps.

Pass: account, project, person, and meeting fixtures return bounded relationship edges with source, recency, confidence, inclusion reason, section caveats, and sensitivity-safe subject refs. Default traversal depth is no more than 2, with per-edge caps and truncation metadata. Duplicate attendees collapse by canonical person/email key; internal participants are included only when the subject kind or explicit relationship makes them relevant. Queue and manual Glean refresh produce equivalent claim/signal/fact side effects for the same fixture output.

W2A — Runtime authority seal

Seal the headless comparison path before the Claude Desktop eval: MCP v2 may advertise only registered handlers, generated files and report JSON stay out of runtime authority, and every comparison-critical evidence class is either runtime-backed or explicitly caveated. Add migration 265 as a one-time service-owned runtime evidence backfill request so existing local data can move through producers before the W2 parity check. Add no-bypass tests for stale MCP grants, legacy projection reads, generated artifacts, cached prose, report outputs, stale v1 aliases, and static meeting-content descriptions in the MCP comparison path.

Pass: Claude Desktop sees only tools compiled into the current v2 binary; dailyos.read.account_status output comes from get_entity_intelligence plus registered service-context readers; no W2 comparison fixture can satisfy required sections from entity_assessment, reports.content_json, prep_frozen_json, risk-briefing.json, dashboard.json, dashboard.md, or _today/data/*.json. Missing evidence fails as a section caveat, not as a legacy fallback. Legacy v1 compatibility routes either call the runtime-backed account path or return an explicit unavailable/invalid-arguments payload; hidden static tools and unadvertised raw abilities are not exact-callable by Claude Desktop; they may not silently substitute static rows, raw ability envelopes, or full lists.

W2B — MCP executive briefing

Implement a shared MCP projection for the ability envelope, then make dailyos.read.account_status consume it. Return touchpoints, record entries, relationship participants, section caveats, priorities, trust, freshness, and provenance refs. Add subject resolution for natural names, slugs, and ids.

Pass: the source-safe executive-briefing fixture runs in Claude Desktop, calls the DailyOS MCP tool, and receives enough structured DailyOS output to compare against a broad-corpus answer without direct DB reads or uncaveated derived claims.

W3 — Remaining producers

Fill threads, metadata_proposals, and work/open-loop producer gaps from linked communication, structured source refs, corrections, conflicts, actions, and captured work evidence. Expose or prepare dailyos.read.entity_intelligence over the same projection contract.

Pass: envelope sections are no longer empty by default when relevant evidence exists, deterministic evidence remains a read-model section unless it is a durable assertion, and the generic projection has contract tests for account, project, person, and meeting subjects.

W4 — Trust, health, cleanup

Generalize health story beyond meeting prep, audit section-aware trust/caveats across every producer, validate trust recomputation across claim types, and run source-label cleanup through a service-owned backfill.

Pass: trust bands and caveats reflect facts plus derived sections; source-label cleanup supports dry-run, known-placeholder allowlist, explicit user-approved mutation mode, typed-source-ref derivation, chunked transactions, audit/failure records, and rollback; no legacy placeholder source labels remain in user-visible source summaries after approved backfill.

Producer matrix

Each evidence class gets an owner and a trust rule.

W0 turns this into the Linear issue split. The key rule is simple: deterministic read-model evidence can stay a section, while durable assertions must become claims and trigger trust recomputation in the same wave.

Trust sequencing

Durable producers name the recompute trigger before code starts.

W0 must turn this into per-issue acceptance criteria. The existing services::trust_recompute::recompute_claim_trust_for_subject path is the default; a new trigger is allowed only when the W0 packet proves the existing path cannot cover the producer.

Producer class Recompute trigger Invalidation / failure behavior Required proof
Structured entity facts After claim commit or backfill chunk, call recompute_claim_trust_for_subject before projecting to MCP/WP. Emit ClaimTrustChanged when score changes; failed recompute records a pipeline failure and renders the section as needs_verification with a caveat. entity_fact_write_recomputes_before_projection
Participation assessment claims Counts remain read-model evidence; any influence/relationship assessment claim recomputes trust immediately after write. Unscored assessment is not eligible for top-three influence prose; MCP returns participation evidence plus an unsupported-influence caveat. participation_assessment_requires_scored_claim_or_caveat
Work/risk/priority claims Commitment, risk, and priority claim writers recompute trust in the same service transaction boundary or mark the claim pending recompute. Pending recompute invalidates derived priority sections and projects use_with_caution until trust is current. work_claim_write_updates_priority_caveats
Thread/content summaries Read-model summaries do not score. Any durable summary claim recomputes after sanitizer/provenance attribution succeeds. Prompt-injection sanitizer failure drops the dynamic text, keeps source refs when renderable, and emits a section caveat. thread_summary_poisoned_text_does_not_enter_mcp_payload
AI prompt extraction claims Every Glean/local PTY path classified as a durable producer must recompute after claim/signal commit; report-only prompt outputs never become runtime authority. Missing source metadata marks the affected section use_with_caution or needs_verification; generated JSON/markdown exports are not allowed as a trust shortcut. ai_prompt_producer_requires_services_claim_or_report_only_classification
Glean finalization side effects Queue-worker and manual refresh triggers use the same finalization service, so the same parsed Glean output creates the same claims, signals, fact promotions, and recompute jobs. If one side effect fails, finalization reports the failed class and renders affected sections with caveats rather than silently producing a partial substrate. glean_queue_and_manual_refresh_share_finalization_side_effects
Metadata proposals/conflicts Proposal/conflict claim or record writes recompute trust after source refs and field attribution are attached. Missing source refs fail closed: proposal remains hidden from MCP until provenance is complete. metadata_proposal_requires_source_refs_for_projection

W2A/W2B eval contract

Claude Desktop comparison is a concrete acceptance test.

W2A first proves the MCP comparison path cannot fall back to legacy artifacts or stale tool grants. W2B is done when a source-safe fixture proves that Claude Desktop can ask DailyOS for an executive briefing and receive assessed, provenance-aware evidence that a broad-corpus answer does not have by itself.

  • Fixture prompt: "Please prepare an executive briefing for the Example account. It should include an executive summary/overview of the account and its commercial status with us, current risks and wins and the top three stakeholders by meeting attendance and a two to three line analysis of their influence on the account. Please also include two to three top priorities for this account."
  • Fixture subject: synthetic account with linked people, projects, meetings, actions, source refs, mixed freshness, and at least one caveated/low-trust item. Production subjects are tested only by an approved local run and are not committed to docs, logs, fixtures, or screenshots.
  • Expected tool behavior: Claude Desktop selects the DailyOS MCP tool for personal working context; dailyos.read.account_status resolves the subject, uses the shared runtime projection, advertises that it returns assessed evidence with trust/freshness/provenance refs, and returns a payload under 64 KiB unless truncation metadata is present.
  • W2A authority rule: the comparison path may not read generated entity files, daily briefing JSON, cached report JSON, or legacy intelligence projections as authority. Those paths remain exports, recovery inputs, or downstream artifacts unless a services-owned producer promotes their assertions into claims/signals or bounded runtime evidence.
  • Tool metadata: the MCP v2 tool description, input schema descriptions, result description, and host guidance must tell Claude that DailyOS returns assessed working-state evidence with provenance, not a raw search index. It must state when to call DailyOS, when not to call it, and how to interpret trust bands, freshness, caveats, and source refs.
  • Host-selection fixtures: positive fixture selects DailyOS for personal working-state evidence. Negative fixture avoids DailyOS for broad-corpus, web, or enterprise-search questions that should go to Glean/search instead.
  • Required test names: mcp_v2_tools_list_registered_handlers_only, mcp_comparison_path_rejects_legacy_authority, legacy_query_entity_account_runtime_failure_fails_closed, legacy_entity_list_alias_filter_name_accepts_top_level_query, legacy_entity_list_alias_marks_unknown_args_as_invalid_filter, account_status_exec_briefing_fixture_uses_runtime_projection, account_status_subject_resolution_edges, account_status_host_selection_positive_negative, account_status_presenter_stays_within_mcp_payload_budget_for_large_runtime_text, entity_neighborhood_snapshot_covers_account_project_person_meeting, mcp_projection_redacts_non_renderable_fields, mcp_projection_blocks_prompt_injection_text, and mcp_projection_strips_invisible_text_and_caps_item_size.
  • Negative render fixtures: confidential text, user-only notes, paraphrased private text, attendee names or emails, owner labels, source labels, provenance refs, instruction-like external text, invisible Unicode, poisoned prior intelligence, and hostile thread/calendar text must each prove blocked fields are omitted, sanitized, or replaced with a render-policy caveat.
  • Comparison rubric: pass requires tool selected for the DailyOS-appropriate prompt, all required briefing sections present, no raw DB/schema request, at least five provenance-backed claims or evidence rows, stakeholder candidates sourced from participation, stale/low-trust sections hedged, no prompt-injection instruction carried into the host answer, and broad-corpus answer lacks DailyOS-only working-state evidence. Anything below all required sections or any raw-claim-id/DB-row answer fails W2.
  • Failure examples: returns only claim ids or hashes; omits touchpoints/record/relationships; invents influence without evidence; treats stale or low-trust sections as current; asks the host model to inspect raw DB rows; leaks fields blocked by render policy.
  • W2A failure examples: Claude Desktop sees a planned-but-unregistered v2 tool; a comparison fixture succeeds by reading entity_assessment, reports.content_json, prep_frozen_json, generated dashboard/intelligence files, or _today/data; stale or missing runtime evidence is silently replaced by cached prose; a stale legacy alias returns a full entity list when the caller intended one entity; search_meetings is advertised as discussion-content authority while returning only metadata-safe fields.

Subject resolution

The host model gets clear success and failure shapes.

Input case Required behavior
Exact id or slug Return status: ok, resolution.kind: exact, matched subject ref, match basis, and confidence; continue without clarification.
Exact renderable name Return status: ok, resolution.kind: name when one active subject matches; include renderable display label, match basis, and confidence.
Ambiguous match Return status: clarification_required, resolution.kind: ambiguous, safe candidates[] with subject refs/display labels only when renderable, retryGuidance, and caveats. No raw row dumps.
No match Return status: not_found, resolution.kind: none, retryGuidance, and no broad schema probing.
Inactive, hidden, or blocked by render policy Return status: unavailable, resolution.kind: blocked, redacted/empty candidates, and caveats; do not leak blocked identity or source details.

Release gate

Integrated acceptance criteria.

The full remediation is done only when the runtime can answer the executive-briefing shape without account-only bypasses.

  • get_entity_intelligence returns claim-backed facts, open loops, touchpoints, relationships/participation evidence, threads, metadata proposals, health story, record entries, section caveats, trust, and provenance when supporting evidence exists.
  • MCP and WordPress consume abilities/runtime output, not parallel schema adapters or direct DB joins.
  • Headless comparison paths fail closed with section caveats instead of falling back to generated artifacts, report JSON, cached prose, or stale legacy projections.
  • The same producer/read-model shape works for account, project, person, and meeting fixtures.
  • The host-model comparison prompt can produce a useful executive briefing with commercial status, risks, wins, stakeholder candidates, caveated influence analysis, priorities, trust/freshness language, and source refs.
  • Trust recomputation and section caveats prevent unsupported assertions from rendering as equally certain as source-backed facts.
  • Every durable producer has same-wave trust recomputation; W4 audits and refines trust behavior rather than becoming the first trust gate.
  • Source-label cleanup is service-owned, dry-run first, known-placeholder allowlisted, chunked, audited, reversible, and behind an explicit user-approved mutation gate before touching encrypted production rows. Replacement labels derive only from typed source refs; ambiguous rows fail closed with pre/post counts and partial-failure remediation.
  • All gates pass: cargo clippy -- -D warnings, cargo test, pnpm tsc --noEmit, L2 unanimous, L3 S/P/E, and L5 drift check.

Pacing

No wave starts until the prior wave clears L3 + L5. No agent codes before L0 clears unanimously. Two revision cycles trigger L6 escalation.

Bounding

L2 is bounded by acceptance criteria and ADR contracts. Path-alpha findings go to maintenance unless they violate this remediation's explicit contract.

Migration slots

Reserve slots in W0 only if new persisted schema is required. Prefer read-model producers before adding tables.
