## §0 Origination

**Mixed.** The storage/security half (W1 single-writer, cipher-drop, rebuild, auth right-size) is **debug-driven** — it originates from the 2026-05-28 production DB-loss incident (dev-workflow `pkill` on a hot WAL writer; root-caused in PR #416, isolation in DOS-820/821/822). The judgment half (W2–W4 correction loop, W5 MCP, W6 transcript) is **extension** — it wires already-shipped claim/trust/abilities/salience substrate (ADR-0123/0125/0126/0110/0128) into a visible, measured correction loop.

## §1 Trust topology

**local-to-local single-user.** Every surface in scope (Tauri React `invoke`, MCP loopback, file edits in the user's own workspace) runs as one OS user on one machine inside an already-trusted boundary. Per James (L6, 2026-05-30): the machine is within the trust boundary; the FedRAMP SC-28/SC-13 posture is an artificial construct we are retiring; **content on disk — in the app DB or a downloaded file — carries no additional risk.** Reviewers scope threat models to this topology: do **not** enforce multi-actor gates on the **app/file surfaces** (principal differentiation, cross-actor poisoning, scope-gated redaction of data the user already has filesystem access to). **Carve-out — the MCP channel:** an MCP client (e.g. Claude Desktop) is a *third-party AI consumer* even when same-machine/same-user, and MCP egress sends data to an external model — which is **not** "on disk in our app/file." So ADR-0125's sensitivity gating **stays on the MCP channel**: `Confidential`/`UserOnly` claims never cross MCP. "No scope-gated redaction" applies to local app/file surfaces, not MCP. What still applies regardless of topology: data hygiene (path/slug validation, workspace-root confinement), indirect prompt injection from untrusted *document content* (ADR-0093), and sensitivity redaction in logs/screenshots (ADR-0108).

## North Star

**Headline user outcome:** *"I correct it once, and it stays corrected — everywhere."*

A claim carries provenance and a trust band. The user dismisses, contradicts, or re-scopes it — in the app **or** by editing the claim's readable file — and the system responds: the source's reliability updates, derived claims invalidate, and **what surfaces next visibly changes**, consistently across the macOS app and MCP. Corrections **survive a rebuild** (see W1 rebuild semantics) — a correction that doesn't survive recovery is session state, not a correction.

**Proof obligation (PRODUCT-THESIS).** Every wave either demonstrates its slice of the correction loop —

```
claim (provenance + trust band)
   → user correction (dismiss / contradict / re-scope / edit file)
   → source reliability + derived claims update   ← the propagation/invalidation layer (named in W4)
   → next surfacing reflects the correction, and survives re-enrichment + rebuild
```

— or is **explicitly labeled substrate**. v1.4.9 carries both. **Honest framing (per cycle-1 product-lens):** the storage half is *recovery from the 2026-05-28 incident* (felt pain, real evidence); the judgment half *advances the moat*. Both are real; neither is window dressing.

**Strategic frame.** DailyOS is the personal-**judgment** substrate (claims + trust + abilities + salience + belief revision). Memory is commoditizing; judgment you can trust is the moat, deepened by the daily-correction loop (the me-shape). Per ADR-0135, the primary programmatic surface is **MCP read/write**; the macOS app remains the visual + control-plane surface; net-new surface design defers to v1.5.0. SQLite stays canonical (ACID); readable files are a projection **out**, never files-as-truth.

## Cross-Wave Architectural Decisions

1. **Drop SQLCipher → plain SQLite (L6-approved, supersedes ADR-0092).** Per James 2026-05-30: machines are inside the trust boundary; FedRAMP SC-28/SC-13 + the app-owned-key contract are an artificial construct we retire; on-disk content (app DB or downloaded file) carries no added risk. DOS-831 authors **ADR-0136** (next free — confirmed) superseding ADR-0092 in the ADR-0135/0048 house pattern. ADR-0092 bundles **six** sub-decisions; ADR-0136 must enumerate each as retire-or-keep: **retire** (1) SQLCipher, (2) `0600`/`0700` perms, (3) Time-Machine exclusion, (4) iCloud detection, (5) app-lock-on-idle, as accepted-not-regressed under §1; **KEEP** (6) PII-hygiene-in-logs (= §1's ADR-0108 carve-out — must survive). It also addresses ADR-0092's 2026-04-20 PGLite amendment whose primary "no" rested on the now-retired at-rest contract — noting the amendment's other three legs (alpha Rust embedding, migration-not-foreclosed, features-not-the-bottleneck) are untouched, so retiring the encryption premise *reopens* but does not auto-flip that decision. Author the **820-A DB-mode-isolation ADR** in the same DOS-831 pass (820-A shipped without one; cross-reference ADR-0133/0134 + the `db-lock-storm-class` solution so DB-ownership + DB-mode-isolation read as one substrate). *No fabricated "§D5".*
2. **Cipher-drop is two-phase, hard-ordered: decrypt-then-drop (cycle-2 B-new-2; cycle-3 codex CR).** `sqlcipher_export` is symmetric (the shipping `migrate_to_encrypted` at `encryption.rs:59-100` runs it plaintext→encrypted; Phase 1 mirrors it) but **vanishes once SQLCipher leaves the build** — so the migration cannot defer into the plain build. DOS-831 ships as a **split build with a one-shot decrypt step + sentinel**, not a single PR: **Phase 1** = a still-SQLCipher build runs a **one-shot decrypt command** (open encrypted source `PRAGMA key`, ATTACH plaintext `KEY ''`, `sqlcipher_export('plaintext')`, atomic rename) that **writes a `cipher-dropped` sentinel and exits before any normal open path runs** — so the old auto-encrypt code can't reopen/re-encrypt the freshly-plaintext DB. **Phase 2** = the cipher-dropped build opens plain SQLite gated on the sentinel; **both** auto-encrypt sites (`core.rs:506` AND `:650`) are **deleted, not bypassed**. The plain build must not ship before Phase 1. **Fallback** if the Keychain key is already gone: rebuild-from-canonical (decision 3). Key-derived `local_db_keyed_audit_tag` / `workspace_graph_diagnostic_key_bytes` (`core.rs:299,315`) + `key_provider.rs` retired/re-sourced — DOS-831 scope.
3. **Rebuild preserves corrections via a content-identity correction-journal sidecar (cycle-1 B1 / cycle-2 B-new-1 / cycle-3 dissent).** Markdown is a lossy view of a relational graph and re-enrichment regenerates UUIDs, so prose can't round-trip corrections. W3 (DOS-628) projects a **structured `corrections` sidecar** keyed by the **content-derived semantic identity** — the canonical `compute_dedup_key` shape (`item_hash : subject_ref_compact : claim_type : field_path`, `services/claims.rs:989`; UUID-independent, so it survives re-enrichment) — **not** the raw runtime `dedup_key` column (whose 8 backfill mechanisms compute it differently, `claims.rs:2924`, and whose naive matching resurrects tombstones). It serializes `claim_feedback` (typed FeedbackAction + actor), `claim_state` demotions/tombstones, `claim_contradictions` edges (both endpoints by content-identity + `reconciliation_kind`), supersession. Rebuild (DOS-832): (a) re-enrich → fresh UUIDs; (b) **replay** via `services/claims.rs` `FeedbackAction` (not raw insert), matching by content-identity and **respecting `claim_state` so tombstones are not resurrected**; (c) **non-uniqueness tie-break** (content-identity is not unique — `load_active_claim_by_dedup_key` returns first match): disambiguate edge endpoints by `source_ref` + `observed_at`, and **orphan-when-ambiguous** (logged, never mis-wired or dropped). The *exact* key derivation + edge-resolution tie-break is finalized in the **DOS-832/DOS-628 wave L0 AC** (per the ladder; both feasibility reviewers route it there). New rebuild input → **amend ADR-0048 Principle-4**. DOS-832 depends on W3. This is the buildable form of "corrections survive rebuild."
4. **Files-as-projection, bidirectional via correction only.** W3 projects claims → per-entity markdown **out**; a file edit is a **correction input** routed through `services/claims.rs` as a typed `FeedbackAction` (ADR-0123/0126) — never an in-place claim UPDATE, never a parallel mutation path. Write-back actor = `Actor::User`; path is workspace-root-confined; sensitivity re-validated before write.
5. **Single-process DB ownership + writer-priority lane (647/758).** Consumes ADR-0133 (writer-queue) + ADR-0134 (reader-pool) + the `db-lock-storm-class` solution doc verbatim — no re-derivation. The only hard prerequisite for the loop.
6. **Trust rendering is centralized.** Same provenance + trust-band + sensitivity rendering serves app and MCP (W5 = agent-native parity, not a second renderer; ADR-0105/0108).
7. **MCP writes — reconcile against ADR-0128 §D, don't re-author (cycle-2 K-in/codex).** §5 ("feedback is the only write") covers W5 corrections (dismiss/contradict/re-scope) directly. For `create_action`/`update_action_status` (DOS-169/170): **ADR-0128 Amendment §D (2026-05-19) already authorizes** `dailyos.submit.action` / `dailyos.submit.action_status` (routed through `services::actions` per ADR-0101). So the disposition is **reconcile 169/170 against §D** (confirm §D's submit surface survived the v1.4.4–v1.4.7 reconciliation/cancellation against Linear+code, then consume it) — **not** author a duplicate amendment (which would be mild reinvention). Only if §D's surface was cancelled does a fresh amendment apply.
8. **Migration-slot reservations.** At initial v1.4.9 planning, dev schema head was **v273** (`migrations.rs`) and next free was **v274**. These reservations are **registered schema versions**, not filename prefixes; implementation branches must verify the rebased `migrations.rs` head and filename convention before adding files. Reserve non-overlapping blocks at kickoff (named owner: each wave lead writes confirmed numbers into this plan before any branch opens): **W1b = v274–v277**, **W2 = v278–v279** (auth-overhaul nonce/scope table drops + 510), **W3 = v280–v283** (projection-ledger + corrections-sidecar), **W4 = v284–v289** (`claim_feedback` typing / engagement / review-queue-budget / `deviation_baselines`), **W5 = registered v290** (`mcp_target_handles`), **W6 = v291–v296**. DOS-832 rebuild adds no migration (it replays into the head schema). (cycle-1 C3 + cycle-2 codex; W5 cycle-7 data-migration/K-in reconciliation.)

## Definition of Done

1. **Headline proven + felt:** a correction made in the app, in a readable file, and over MCP each propagates to source reliability + derived claims and **changes a surfacing the user did not directly touch**, **survives re-enrichment and a rebuild**, measured by the DOS-338 cross-surface stickiness metric on real workspace data.
2. **Substrate reset complete:** plain SQLite (superseding ADR landed); encrypted→plaintext migration done; rebuild-from-JSON preserves corrections; single-writer ownership; `replica-refresh` + destructive-command guards (DOS-820 closed); auth right-sized with hostile-input proof + threat-model ADR.
3. **Cross-surface parity:** identical claims + trust rendering + post-correction behavior across Tauri and MCP **for claims that cross MCP** — i.e. parity *modulo* the ADR-0125 sensitivity gate: `Confidential`/`UserOnly` claims are shown in the app but never sent over MCP (§1 MCP carve-out). "Identical" means same rendering + same post-correction behavior for the MCP-eligible set, not that MCP sees everything the app sees.
4. **No stubs/deferrals in shipped waves:** `contradiction.rs`, `render_rules.rs`, `deviation.rs`, `recommendations/eval.rs` real.
5. **Gates green:** `cargo clippy -- -D warnings && cargo test && pnpm tsc --noEmit` (DOS-824 flake tracked separately).
6. **W6 is not a tag-gate.** "Transcript extraction is claim-producing" is W6's DoD, not the version's; if W6 slips, the version still ships on the headline.
