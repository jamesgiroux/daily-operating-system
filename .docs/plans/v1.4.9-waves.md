## North Star

**Headline user outcome:** *"I correct it once, and it stays corrected — everywhere."*

A claim carries provenance and a trust band. The user dismisses, contradicts, or re-scopes it — in the app **or** by editing the claim's readable file — and the system responds: the source's reliability updates, derived claims invalidate, and **what surfaces next visibly changes**, consistently across the macOS app and MCP.

**Proof obligation (PRODUCT-THESIS).** Every wave either demonstrates its slice of the correction loop —

```
claim (provenance + trust band)
   → user correction (dismiss / contradict / re-scope / edit file)
   → source reliability + derived claims update
   → next surfacing reflects the correction
```

— or is **explicitly labeled substrate** (infrastructure with no direct user outcome, justified by what it unblocks). "If a release doesn't move the correction loop, it's substrate maintenance, not product." v1.4.9 carries both: W1–W2 are substrate that the reset requires; W3–W6 carry the headline.

**Strategic frame.** DailyOS is the personal-**judgment** substrate (claims + trust + abilities + salience + belief revision). Memory is commoditizing; judgment you can trust is the moat, deepened by the daily-correction loop (the me-shape). Per ADR-0135, the primary programmatic surface is **MCP read/write**; the macOS app remains the visual + control-plane surface (not deprecated); net-new surface design is deferred to v1.5.0. SQLite stays canonical (ACID); readable files are a projection **out**, never files-as-truth (the adversarial review killed files-as-truth).

## Cross-Wave Architectural Decisions

1. **SQLite stays canonical; encryption is dropped, not the database.** Cipher-drop (W1) is an **ADR-0092 §D5 amendment** (new ADR/ticket): plain SQLite on a FileVault-encrypted volume, replacing SQLCipher. At-rest protection moves to the OS disk boundary, matching the local-same-user threat model.
2. **Fresh-install rebuild, not migration, is the recovery path.** The canonical workspace JSON + re-enrichment rebuilds the DB from scratch (W1). This is what James exercised in the 2026-05-29 incident recovery; W1 makes it a first-class, repeatable path.
3. **Single-process DB ownership + writer-priority lane (647).** Continues the db-throughput W0 work; 758 (McpToolHandler request-scoped DB/services + nested-writer guard) lands here as the handler-side contract.
4. **Files-as-projection, bidirectional via correction only.** W3 projects claims → per-entity markdown **out**; editing a file is a **correction input** that flows back through the claim service — it does not make the file authoritative.
5. **Security right-sized to the OS boundary (W2).** HMAC/pairing/presence-nonce/scope-grant ceremony for local same-OS-user surfaces is stripped (the in-progress auth overhaul). Hostile-input proof (510) is re-scoped to the post-overhaul threat model. (DOS-759/760 already canceled — zero transport-signing remains in code.)
6. **Trust rendering is centralized and identical across surfaces.** The same provenance + trust-band + sensitivity rendering serves the app and MCP (W5 = agent-native parity, not a second renderer).
7. **Migration-slot reservations (mandatory).** W1 and W6 both add migrations. Reserve **non-overlapping** slot blocks at kickoff to avoid the v1.4.1 rebase-renumber loop: **W1 = v274–v283**, **W6 = v284–v293** (current prod schema is 123 on v1.2.2; dev schema head is the reference — confirm the next free slot at kickoff and shift the blocks if needed).

## Wave-by-Wave Breakdown

### W1 — Storage reset & single-writer *(substrate)*

**Goal:** make the DB cheap to rebuild, safe to operate, and owned by a single writer — the durable fix for the dev-workflow-corrupts-prod hazard class (DOS-820).

**Issues:**
- **NEW — cipher-drop (ADR-0092 §D5 amendment):** replace SQLCipher with plain SQLite + FileVault; key-handling code removed; open/rekey paths simplified. *(create ticket)*
- **NEW — rebuild-from-canonical-JSON:** first-class, repeatable fresh-install rebuild from workspace JSON + re-enrichment. *(create ticket)*
- **DOS-647** — single-process DB ownership + writer-priority lane (umbrella; continues db-throughput W0).
- **DOS-758** — McpToolHandler interface refactor (request-scoped DB/services, forbid nested writer calls); decoupled from auth (was 647-B; currently In Review — re-validate against the reset).
- **DOS-823 (820-C)** — `doctor replica-refresh` clone (prod→replica via `run_chunked_backup`, key-to-destination-first, prod opened read-only) + destructive-command guards (`start_fresh_database`, `restore_database_from_backup`). **Completes DOS-820** (820-A/B already merged).
- **DOS-767 / 768 / 770 / 812** — ingestion-hygiene + consolidation carryovers; re-validate against the rebuilt pipeline.

**Proof:** substrate. Demoable: `replica-refresh` clones prod→replica; prod-destroyer commands refuse outside the guard; a from-scratch rebuild reproduces the working DB.

### W2 — Security right-size *(substrate)*

**Goal:** collapse the app-layer auth ceremony to the OS user boundary for local same-user surfaces.

**Issues:**
- **Auth overhaul** — strip HMAC + pairing + presence-nonce + scope-grant for local-to-local same-OS-user; lean on the OS user boundary (continues the in-progress overhaul; verify post-overhaul model before re-adding any gate).
- **DOS-510** — hostile-input / prompt-injection proof gates, **re-scoped** to the post-overhaul threat model (treat hostile content as evidence text only, never as instructions/markers).

**Proof:** substrate. Demoable: local React `tauri::invoke` and WP/MCP loopback reach parity with no signing ceremony; hostile-input fixtures pass.

### W3 — Claims → editable readable files *(first correction-loop slice)*

**Goal:** the reverse leg of bidirectional markdown↔substrate — project claims **out** to per-entity readable files, and accept edits to those files as corrections.

**Issues:**
- **DOS-628** — per-entity claim→markdown projection (out), plus a **file→claim correction write-back** path through the claim service. SQLite stays canonical; the file is a projection + a correction surface, not authority.

**Proof (first loop slice):** edit a claim in its readable file → the claim updates, provenance records the correction, the projection re-renders, and trust/derived state reacts.

### W4 — Judgment moat / correction loop made visible *(HEADLINE)*

**Goal:** the full correction loop, visible end-to-end and **measured**.

**Issues:**
- **DOS-8** — semantic claim feedback via typed `claim_feedback` (dismiss / confirm / contradict / re-scope), reusable across surfaces.
- **DOS-318** — contradiction UX as a review-queue reconciliation flow (`contradiction.rs` is a 1-byte stub today).
- **DOS-443** — review-queue daily budget + prioritization for `needs_user_decision` claims (calm, bounded).
- **DOS-447** — per-`claim_type` low-impact render suppression (`render_rules.rs` stub) so corrections don't turn every uncertainty into homework.
- **DOS-316 + DOS-811** — deviation detection / "what's unusual" briefing section (`deviation.rs` ~6-line stub) + ADR-0125 `expected_presence` registry that feeds it.
- **DOS-338** — **the eval harness that proves the moat** (`eval.rs` stub): usefulness / noise / missed-important + correction-stickiness instrumentation. This is the proof instrument for the headline.
- **DOS-446** — adversarial hundred-claims fixture (privacy, contradiction, correction, wrong-subject, revoked-source, performance).
- **DOS-278** — daily-briefing meeting/readiness count divergence (derive every visible count from one canonical candidate set).
- **DOS-277** — user-edited meeting agenda survives re-enrichment (load-bearing for the rebuild + correction durability).
- **DOS-317** — engagement telemetry → ranking signal (full): reorders surfacing by engagement; privacy-by-design, ranking-not-trust.

**Proof (headline):** a correction in any entry point propagates to source reliability + derived claims and **changes what surfaces next**, with the eval harness (338) measuring stickiness + noise. This is where *"correct once, stays corrected"* is demonstrated.

## The 5-Question Intelligence Loop Integration Check (per new claim/table/surface)

Every new table, claim field, or user-visible intelligence surface in this version answers, before shipping:
1. **Claim model** — represented as a claim (subject attribution, temporal scope, sensitivity, lifecycle), not ad-hoc display data?
2. **Provenance + trust** — how is `source_asof` / source-field attribution captured, and how does it move trust-band rendering (`likely_current` / `use_with_caution` / `needs_verification`)?
3. **Signals + invalidation** — what signals does it emit; which propagation/invalidation paths refresh derived state?
4. **Runtime + surfaces** — which abilities/contexts consume it (`build_intelligence_context()`, `gather_account_context()`, prep outputs, callouts); behavior across Tauri + MCP?
5. **Feedback loop** — how do corrections / dismissals / corroborations / contradictions feed back into claim state + source reliability?

W3–W6 are gated on this check; W1–W2 are substrate and exempt except where they touch claim tables (812).

## v1.4.9 Definition of Done

1. **Headline proven:** a correction made in the app, in a readable file, and over MCP each propagates to source reliability + derived claims and changes the next surfacing — demonstrated with real workspace data and **measured by the DOS-338 eval harness**.
2. **Substrate reset complete:** plain SQLite + FileVault; repeatable rebuild-from-JSON; single-writer ownership; `replica-refresh` + destructive-command guards (DOS-820 closed); auth right-sized with hostile-input proof.
3. **Cross-surface parity:** identical claims + trust rendering + post-correction behavior across Tauri and MCP.
4. **No stubs/TODOs/deferrals:** `contradiction.rs`, `render_rules.rs`, `deviation.rs`, `eval.rs` are real; transcript extraction is claim-producing.
5. **Gates green:** `cargo clippy -- -D warnings && cargo test && pnpm tsc --noEmit`. (Track DOS-824 test-flake separately; it must not be the thing that's red.)
