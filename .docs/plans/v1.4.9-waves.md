> **Status:** DRAFT, L0 cycle 2 (revised against cycle-1 panel). Linear project: `v1.4.9 — Substrate Reset & Judgment Maturation` (`874a7361-3f2e-4448-96bf-4ba600238ee0`).

## §0 Origination

**Mixed.** The storage/security half (W1 single-writer, cipher-drop, rebuild, auth right-size) is **debug-driven** — it originates from the 2026-05-28 production DB-loss incident (dev-workflow `pkill` on a hot WAL writer; root-caused in PR #416, isolation in DOS-820/821/822). The judgment half (W2–W4 correction loop, W5 MCP, W6 transcript) is **extension** — it wires already-shipped claim/trust/abilities/salience substrate (ADR-0123/0125/0126/0110/0128) into a visible, measured correction loop.

## §1 Trust topology

**local-to-local single-user.** Every surface in scope (Tauri React `invoke`, MCP loopback, file edits in the user's own workspace) runs as one OS user on one machine inside an already-trusted boundary. Per James (L6, 2026-05-30): the machine is within the trust boundary; the FedRAMP SC-28/SC-13 posture is an artificial construct we are retiring; **content on disk — in the app DB or a downloaded file — carries no additional risk.** Reviewers scope threat models to this topology: do **not** enforce multi-actor gates (principal differentiation, cross-actor poisoning, scope-gated redaction of data the user already has filesystem access to). What still applies regardless of topology: data hygiene (path/slug validation, workspace-root confinement), indirect prompt injection from untrusted *document content* (ADR-0093), and sensitivity redaction in logs/screenshots (ADR-0108).

## North Star

**Headline user outcome:** *"I correct it once, and it stays corrected — everywhere."*

A claim carries provenance and a trust band. The user dismisses, contradicts, or re-scopes it — in the app **or** by editing the claim's readable file — and the system responds: the source's reliability updates, derived claims invalidate, and **what surfaces next visibly changes**, consistently across the macOS app and MCP. Corrections **survive a rebuild** (see W1 rebuild semantics) — a correction that doesn't survive recovery is session state, not a correction.

**Proof obligation (PRODUCT-THESIS).** Every wave either demonstrates its slice of the correction loop —

```
claim (provenance + trust band)
   → user correction (dismiss / contradict / re-scope / edit file)
   → source reliability + derived claims update   ← the propagation/invalidation layer (named in W4)
   → next surfacing reflects the correction, and survives re-enrichment + rebuild
```

— or is **explicitly labeled substrate**. v1.4.9 carries both. **Honest framing (per cycle-1 product-lens):** the storage half is *recovery from the 2026-05-28 incident* (felt pain, real evidence); the judgment half *advances the moat*. Both are real; neither is window dressing.

**Strategic frame.** DailyOS is the personal-**judgment** substrate (claims + trust + abilities + salience + belief revision). Memory is commoditizing; judgment you can trust is the moat, deepened by the daily-correction loop (the me-shape). Per ADR-0135, the primary programmatic surface is **MCP read/write**; the macOS app remains the visual + control-plane surface; net-new surface design defers to v1.5.0. SQLite stays canonical (ACID); readable files are a projection **out**, never files-as-truth.

## Cross-Wave Architectural Decisions

1. **Drop SQLCipher → plain SQLite (L6-approved, supersedes ADR-0092).** Per James 2026-05-30: machines are inside the trust boundary; FedRAMP SC-28/SC-13 + the app-owned-key contract are an artificial construct we retire; on-disk content (app DB or downloaded file) carries no added risk. DOS-831 authors **ADR-0136** (next free — confirmed) superseding ADR-0092 in the ADR-0135/0048 house pattern. ADR-0092 bundles **six** sub-decisions; ADR-0136 must enumerate each as retire-or-keep: **retire** (1) SQLCipher, (2) `0600`/`0700` perms, (3) Time-Machine exclusion, (4) iCloud detection, (5) app-lock-on-idle, as accepted-not-regressed under §1; **KEEP** (6) PII-hygiene-in-logs (= §1's ADR-0108 carve-out — must survive). It also addresses ADR-0092's 2026-04-20 PGLite amendment whose primary "no" rested on the now-retired at-rest contract. Author the **820-A DB-mode-isolation ADR** in the same DOS-831 pass (820-A shipped without one). *No fabricated "§D5".*
2. **Cipher-drop is two-phase, hard-ordered: decrypt-then-drop (cycle-2 feasibility B-new-2).** `sqlcipher_export` only runs plaintext→encrypted and **vanishes from the build once SQLCipher is dropped** — so the migration cannot be deferred into the plain build. DOS-831 sequences internally: **Phase 1** (build still links SQLCipher, Keychain key available): one-time encrypted→plaintext via a **new decrypting-open helper** — open encrypted source with `PRAGMA key`, ATTACH plaintext target `KEY ''`, `sqlcipher_export('plaintext')`. **Phase 2** (cipher-dropped build): opens plain SQLite; the `is_database_plaintext`→auto-encrypt branch (`core.rs:506,650`) is **deleted, not bypassed** (else a decrypted DB is re-encrypted on next open). The plain build must not ship before Phase 1 runs against the user's encrypted prod DB. **Fallback** if the Keychain key is already gone: rebuild-from-canonical (decision 3). The key-derived `local_db_keyed_audit_tag` / `workspace_graph_diagnostic_key_bytes` (`core.rs:299,315`) + `key_provider.rs` are retired or re-sourced — named in DOS-831 scope.
3. **Rebuild preserves corrections via a stable-key correction-journal sidecar (cycle-1 B1 / cycle-2 B-new-1).** A per-entity markdown file is a *lossy* view of a relational graph, and re-enrichment regenerates claim UUIDs — so projecting prose markdown can't round-trip corrections. Instead W3 (DOS-628) projects, per entity, a **structured `corrections` sidecar** that serializes every correction-bearing row **by stable key** (`dedup_key`/`topic_key` + `source_ref`, never raw UUID): `claim_feedback` (typed FeedbackAction + actor), `claim_state` demotions/tombstones, `claim_contradictions` edges (keyed by both claims' stable keys + `reconciliation_kind`), `superseded_by` chains (by stable key). Rebuild (DOS-832): (a) re-enrich → regenerate agent/system claims with fresh UUIDs; (b) **replay** the journal — match each entry to a regenerated claim by stable key and re-apply via `services/claims.rs` `FeedbackAction` (not raw insert); rehydrate contradiction/supersession edges by resolving both stable keys to new UUIDs; (c) journal entries matching no regenerated claim are **retained as orphan entries (logged), never dropped**. The sidecar is a new rebuild input → **amend ADR-0048 Principle-4 rebuild-source table**. DOS-832 depends on W3. This is the buildable form of "corrections survive rebuild."
4. **Files-as-projection, bidirectional via correction only.** W3 projects claims → per-entity markdown **out**; a file edit is a **correction input** routed through `services/claims.rs` as a typed `FeedbackAction` (ADR-0123/0126) — never an in-place claim UPDATE, never a parallel mutation path. Write-back actor = `Actor::User`; path is workspace-root-confined; sensitivity re-validated before write.
5. **Single-process DB ownership + writer-priority lane (647/758).** Consumes ADR-0133 (writer-queue) + ADR-0134 (reader-pool) + the `db-lock-storm-class` solution doc verbatim — no re-derivation. The only hard prerequisite for the loop.
6. **Trust rendering is centralized.** Same provenance + trust-band + sensitivity rendering serves app and MCP (W5 = agent-native parity, not a second renderer; ADR-0105/0108).
7. **MCP writes — reconcile against ADR-0128 §D, don't re-author (cycle-2 K-in/codex).** §5 ("feedback is the only write") covers W5 corrections (dismiss/contradict/re-scope) directly. For `create_action`/`update_action_status` (DOS-169/170): **ADR-0128 Amendment §D (2026-05-19) already authorizes** `dailyos.submit.action` / `dailyos.submit.action_status` (routed through `services::actions` per ADR-0101). So the disposition is **reconcile 169/170 against §D** (confirm §D's submit surface survived the v1.4.4–v1.4.7 reconciliation/cancellation against Linear+code, then consume it) — **not** author a duplicate amendment (which would be mild reinvention). Only if §D's surface was cancelled does a fresh amendment apply.
8. **Migration-slot reservations.** Dev schema head is **v273** (`migrations.rs`); next free = **v274**. Reserve non-overlapping blocks at kickoff (named owner: each wave lead writes confirmed numbers into this plan before any branch opens): **W1b = v274–v277**, **W2 = v278–v279** (auth-overhaul nonce/scope table drops + 510), **W3 = v280–v283** (projection-ledger + corrections-sidecar), **W4 = v284–v289** (`claim_feedback` typing / engagement / review-queue-budget / `deviation_baselines`), **W6 = v290–v295**. DOS-832 rebuild adds no migration (it replays into the head schema). (cycle-1 C3 + cycle-2 codex.)

### W3 — Claims → editable readable files *(first loop slice)*

**Proof:** edit a claim's readable file → claim updates as a new correction source (immutable-core preserved), provenance records it, projection re-renders, derived state reacts.

### W4 — Judgment moat / correction loop *(HEADLINE)*

One correction invalidates the correct derived claims and re-ranks across both surfaces — changing a surfacing the user did *not* directly edit. Consumes the existing signals/invalidation substrate (ADR-0126 §1/§4/§9 + per-entity invalidation — do not reinvent). This is the irreducible-core dependency for DOS-338's stickiness metric.
- **DOS-8** — semantic claim feedback (the typed `claim_feedback` enum from ADR-0123 — consume, don't redefine).

- **DOS-316 + DOS-811** — deviation / "what's unusual" (ADR-0126 §5: schema-compression must not suppress deviation-flagged claims) + `expected_presence` registry. `deviation.rs` 6-line stub.
- **DOS-338** — eval harness. **Extends the existing `bridges/eval.rs` (404 LOC) + ADR-0110 harness** — not greenfield; the 6-line `recommendations/eval.rs` is the slot. **Stickiness is defined as a cross-surface, post-re-enrichment, indirect-surfacing assertion** (cycle-1 PC-3): a correction the user made once visibly changed a surfacing they did *not* directly edit, and stayed changed after re-enrichment + rebuild. Not internal persistence.
- **DOS-446** — adversarial hundred-claims fixture (uses the ADR-0110 fixture shape).
- **DOS-278** — briefing meeting/readiness count divergence (one canonical candidate set).
- **DOS-277** — user-edited agenda survives re-enrichment — **elevated as the felt-stickiness keystone test** (cycle-1 PC-3).
- **DOS-317** — engagement → ranking. **ADR-0126 §9-mandated** (engagement affects *ranking*, never trust). Product-lens flagged engagement-ranking as feature-gravity-adjacent; kept because it's contract-correct and §9-bounded, but **re-founded toward me-shape signals** (recency-of-correction, staleness, contradiction) over raw click-count where they diverge.

**W4 irreducible core (if the wave compresses — cycle-1 SC-3):** DOS-8 (intake) + the propagation/invalidation deliverable + DOS-277 (felt stickiness) + DOS-338 (measurement). Everything else is enhancement.

**Proof (headline):** a correction in any entry point propagates to source reliability + derived claims, **changes a surfacing the user did not directly touch**, survives re-enrichment + rebuild, and is measured by DOS-338's cross-surface stickiness metric.

## The 5-Question Intelligence Loop Integration Check

Every new table / claim field / user-visible surface answers: (1) claim model? (2) provenance + trust-band movement? (3) signals + invalidation? (4) abilities/contexts consuming it, Tauri + MCP behavior? (5) feedback loop into claim state + source reliability? W3–W6 gated on this; W1–W2 substrate-exempt **except** where they touch claim tables — DOS-812 and **DOS-832 rebuild** (it reconstitutes `intelligence_claims`/`claim_feedback`/contradictions, so the rebuild path runs the 5-question check too).

## Definition of Done

1. **Headline proven + felt:** a correction made in the app, in a readable file, and over MCP each propagates to source reliability + derived claims and **changes a surfacing the user did not directly touch**, **survives re-enrichment and a rebuild**, measured by the DOS-338 cross-surface stickiness metric on real workspace data.
2. **Substrate reset complete:** plain SQLite (superseding ADR landed); encrypted→plaintext migration done; rebuild-from-JSON preserves corrections; single-writer ownership; `replica-refresh` + destructive-command guards (DOS-820 closed); auth right-sized with hostile-input proof + threat-model ADR.
3. **Cross-surface parity:** identical claims + trust rendering + post-correction behavior across Tauri and MCP; sensitivity tiers honored on the MCP write path.
4. **No stubs/deferrals in shipped waves:** `contradiction.rs`, `render_rules.rs`, `deviation.rs`, `recommendations/eval.rs` real.
5. **Gates green:** `cargo clippy -- -D warnings && cargo test && pnpm tsc --noEmit` (DOS-824 flake tracked separately).
6. **W6 is not a tag-gate.** "Transcript extraction is claim-producing" is W6's DoD, not the version's; if W6 slips, the version still ships on the headline.
